## 0. 프로젝트 한 줄 요약

**HazardBot은 위험물 취급구역을 순찰하며 정지 지점마다 위험물을 감지·판정하고, 로봇팔로 직접 제거하는 초동 조치까지 수행하는 AI 패트롤 로봇이다.**

- 판정: 카메라로 물체 색을 확인 → 노란색(산화성 고체류 표현)은 즉시 위험 판정, 빨간색(인화성 액체류 표현)은 가스 센서 3초 정밀검사 후 위험/정상 판정
- 초동 조치: ACT(Action Chunking Transformer) 정책으로 학습된 로봇팔이 위험물을 집어 격리함에 넣고 뚜껑을 닫음
- 하드웨어: RPi(ROS2 오케스트레이션) + ESP_Drive(주행·안전판단) + ESP_Env(가스·화염 센서) + SO-101 로봇팔

### 표지 (분량 제외)

대회 가이드양식 3페이지가 지정한 형식을 따른다. 네 줄 모두 필수다.

```
<부문>        → 자유공모
<작품명>      → HazardBot
<팀번호_팀명> → (미정, §2 참조)
```

디자인은 현재의 `#F5F5F7` 지면 + HazardBot 마크 표지를 유지하되, **위 네 줄이 반드시 들어가야 한다.**
현재 표지의 「개발완료보고서」 태그라인과 팀원 이름 줄을 이 형식으로 대체한다.

### P1. 목차

- 본문 5개 장 구성: ① 개발 개요 ② 개발 환경 ③ 개발 프로그램 ④ 장애요인과 해결 ⑤ 결과물의 차별성·파급력·일정
- 각 장에 해당 페이지 범위 표기

### P2. 개발 배경 · 동기 〔필수항목 1〕

- 반도체 FAB, 정유공장처럼 위험물을 다루면서도 24시간 멈추지 않는 산업현장이 있음
- 사람이 밤낮없이 모든 구간을 지키고 위험물에 직접 다가가 치우는 것은 현실적으로 어려움 — 장시간 반복 감시의 피로, 유해 물질 근접 시 안전 위협
- **동기**: 기존 순찰 로봇은 "발견하고 알리는" 데서 멈춘다. 발견 이후 실제로 치우는 일은 여전히 사람이 위험물에 다가가야 한다는 문제의식
- **비주얼**: 24시간 가동 현장 이미지(야간/연속가동) + 문제 제기 문구

### P3. 개발 목표 · 필요성 〔필수항목 1〕

- **목표**: 위험물을 자동으로 감지·판정하고, 판정 결과에 따라 로봇팔로 초동 조치(제거)까지 수행하는 로봇 개발
- **필요성**: 사람이 직접 접근하지 않고도 지속적인 감시·격리가 가능한 구조. 사람의 유해물질 근접 빈도 자체를 줄이는 것이 목적
- 산업 기준 근거를 명시 — **위험물안전관리법**의 유별 혼재·혼합저장 제한(적색 = 제4류 인화성 액체 / 황색 = 산화성·자기반응성), **KS C IEC 60079-10-1**(폭발위험장소 구분)을 판정 로직 설계 근거로 채택

### P6. 하드웨어 구성 · 전력 계통 〔필수항목 2〕

**하드웨어 4단위**

- **RPi 5**: ROS2로 전체 흐름 조율, 카메라 인식, 대시보드 웹서버
- **ESP_Drive**: TB6612FNG 듀얼 H-브리지 모터 드라이버, TCRT5000 5채널 라인센서, VL53L1X ToF. 정지 상황에서의 안전 우선순위 판단(ESTOP/RPI_TIMEOUT > 장애물·배터리 > 센서오류 > 경고 > 안전 순)
- **ESP_Env**: MQ-2 가스센서 + 화염센서, 3초간 가스 샘플링
- **SO-101 로봇팔(리더-팔로워 구조)**: ACT 정책으로 제어, 노트북 RTX 4060 GPU로 추론

**전력 계통** (기존 P14 내용 통합)

- 3S LiPo 배터리(11.1V, 2200mAh) → 1to3 XT60으로 3개 레일 분배
  - **12V(팔로워)**: 로봇팔 서보 6개
  - **5V_RPi(XL4016 단독)**: RPi 5 전용
  - **12V(주행) + 5V_ESP(XL4015)**: TB6612 모터 드라이버 / ESP_Drive·ESP_Env
- MQ-2 가스센서는 ESP_Env의 5V/VIN에서 급전 — **히터 상시 330mA가 DRIVE 5V를 흔들어 브라운아웃을 일으키므로 급전점을 분리**했다
- ESP_Drive·ESP_Env는 VCC/GND **직결(납땜)** 급전 — 핀소켓은 모터 진동에 빠진다(P16 참조)
- **비주얼**: 배터리 → 3개 레일 → 각 보드 전력 계통도 (`docs/06_firmware/전력계통_실배선_2026-08-28.md` §1)

### P10. 핵심기능① 위험물 판정 로직 〔필수항목 3〕

- 카메라가 정지 지점에서 물체의 색을 확인
- **노란색** = 산화성 고체류 위험물을 표현 → 고체는 가스를 내뿜지 않으므로, 그 자리에 있다는 사실만으로 곧바로 위험 판정
- **빨간색** = 인화성 액체류 위험물을 표현 → 액체는 새어 나올 때만 위험해지므로, 가스 센서로 3초간 정밀검사 후 판정
- **판정은 구역과 무관하다** — 위치가 아니라 내용으로 판정한다는 원칙(2026-08-04 확정)
- 화면 표시 문장(그대로 사용 — `hazard_detector_node.py` 실제 출력):
  - `황색 산화성 고체 감지 — 취급구역 내 위치 자체가 위반`
  - `적색 물질 — 가스 감지. 격납 파손`
  - `적색 물질 — 가스 없음. 격납 유지, 통과`

### P11. 핵심기능① 상세 — GAS_CHECK(가스 정밀검사) 〔필수항목 3〕

- 빨간색 판정 시 `hazard_detector_node`가 `/hazard/gas_check_request`를 발행
- ENV 보드가 3초간(`GAS_INSPECTION_DURATION_MS=3000`) MQ-2 가스센서를 샘플링
- 결과: `DETECTED`(위험) / `CLEAR`(정상) / `ERROR`
- 5초 워치독(`GAS_CHECK_TIMEOUT_S=5.0`)으로 응답 지연 시에도 안전하게 처리
- **비주얼**: 3초 가스게이팅 타임라인 다이어그램

### P12. 핵심기능② ACT 로봇팔 — 학습 〔필수항목 3〕

- ACT(Action Chunking Transformer) 알고리즘으로 모방학습(imitation learning)
- 사람이 리더암으로 직접 시연한 데이터 **100 에피소드**를 학습
- 구성: **적색 50 · 황색 50**, 다섯 위치(중앙/앞좌/앞우/뒤좌/뒤우)에 각 10회씩 배분
- 노트북 RTX 4060 GPU로 학습·추론 — **100,000 스텝 / 5.8 step/s / 4시간 47분 / VRAM 4.4GB(batch_size=8)**
  - 🔴 *2026-09-02 정정.* 종전의 「1.78 step/s · 약 15.6시간」은 **2026-08-18 계획용 벤치마크**였다.
    데이터 수집(8/25 완료) 이전에 잰 값이라 실제 학습과 다르다. 실측 근거는 학습 로그다:

    **3시간 50분 28초 (5.79 step/s)** → 합계 **4시간 47분**.
    체크포인트 mtime(`C:\ACT_data	raining\hazardbot_red_yellow_act_v1\checkpoints/`)도 일치한다.
- 데이터셋 규모: **100 에피소드 · 59,976 프레임 · 30fps** (약 33분 분량, `meta/info.json`)

- **비주얼**: 실제 대시보드 **전체 화면 1장** — 영상 150초 지점

    모두 들어 있다.** EVENT LOG 에 황색 위반 · 적색·가스 없음(통과) · 적색·가스 감지(격납 파손)이
    함께 쌓여 있고, 그 시점 HAZARD LEVEL 은 `L1 GAS_DETECTED`, VISION 색상은 `red` 다.
    세로 크롭 3장은 통합 페이지에 넣으면 글자가 안 읽힐 만큼 작아지는 문제도 있었다.

🔴 **HAZARD LEVEL은 종합 판정이 아니라 가스 지표다.** 황색 산화성 고체를 감지한 프레임에서도 `L0 NORMAL`이고, `L1 GAS_DETECTED`는 적색+가스 검출일 때만 올라간다. **황색 판정의 근거는 VISION 색상값과 EVENT LOG 문장**이지 HAZARD LEVEL이 아니다. 발표 중 "노란색이 즉시 위험이라면서 왜 화면은 L0인가" 질문에 대비할 것.

🔴 **발표 시 주의(내부 참고, 슬라이드에는 안 씀)**: 통합 경로(판정→자동 그립 요청)는 코드는 구현돼 있으나 실물로 끝까지 검증된 적은 없다. 질의응답 대비 필요.

### P17. 작품의 차별성 — 기존 순찰로봇과의 비교 〔필수항목 5 · 🔴 필수〕

심사 배점 **독창성 30점**의 "기존 제품 또는 유사제품과의 차별성" 항목에 직접 대응한다.

**① 감지에서 멈추지 않고 조치까지 간다**

| | 기존 산업용 순찰·보안 로봇 | HazardBot |
|---|---|---|
| 순찰·감시 | ○ | ○ |
| 이상 감지·기록 | ○ | ○ |
| 관제 보고 | ○ | ○ |
| **물리적 초동 조치** | **× (사람이 현장 투입)** | **○ 로봇팔이 격리함에 격리** |

기존 로봇은 "발견하고 알리는" 데서 끝나므로, 결국 사람이 위험물에 다가가야 한다. HazardBot은 판정과 조치가 한 로봇 안에서 닫힌다.

**② 판정이 색상 단일 분류가 아니라 물성 기반 2단 게이팅이다**

- 고체(황색)는 **존재 자체가 위반** → 즉시 판정
- 액체(적색)는 **누출될 때만 위험** → 가스 센서 3초 정밀검사로 2차 게이팅
- 근거를 임의로 정하지 않고 **위험물안전관리법**의 유별 혼재 제한과 **KS C IEC 60079-10-1**에서 가져왔다
- 단순 색상 분류라면 적색 물체를 전부 위험으로 오탐하지만, 이 구조는 "격납이 유지된 적색"을 정상으로 통과시킨다

**③ 조치가 하드코딩 궤적이 아니라 학습된 정책이다**

- 좌표를 고정한 시퀀스가 아니라 사람 시연 100회를 학습한 **ACT 정책** — 물체 위치가 달라져도 대응
- 격리함 정렬을 비전으로 따로 찾지 않고 정책이 흡수한다

### P18. 기술적 우수성 · 완성도 〔필수항목 5〕

심사 배점 **기술성 및 완성도 30점**의 "임베디드SW 기술 적용 여부"에 대응한다.

**① 역할이 분리된 3계층 분산 임베디드 구조**

센서를 "누가 이 데이터로 행동하는가"를 기준으로 3개 감지 계층으로 재편했다.

| 계층 | 주기 | 담당 | 대상 |
|---|---|---|---|
| 실시간 반사 | 20ms | ESP_Drive | 라인센서 · ToF |
| 환경 감시 | 100ms | ESP_Env | MQ-2 가스 · 화염 |
| 인지·학습 | 30fps | RPi / 노트북 | 카메라 · ACT |

**② 정지 권한을 한 곳에 모은 4계층 안전 체계**

- 「모터를 멈추는 것은 DRIVE 뿐」 — 하드웨어 풀다운 / DRIVE 로컬 / RPi / 사람의 4계층
- **하트비트 기반 안전**: STOP 명령이 아니라 **생존 신호**로 설계 → RPi 사망·WiFi 두절·ENV 사망을 **하나의 메커니즘**으로 정지 처리
- **STBY 10kΩ 풀다운 하드웨어 페일세이프**: ESP32가 죽거나 리셋되면 제어핀이 하이임피던스가 되어 **모터가 자동 정지**. 설계 결정을 하드웨어로 뒷받침

**③ 자원 제약을 인정한 설계 선택**

- **전압 피드포워드**: 실제듀티 = 목표듀티 × (12.0 / 측정전압). 엔코더 속도루프 없이 배터리 전압 강하를 보상
- **VL53L1X 논블로킹 읽기** — 블로킹 시 라인 PID 주기가 붕괴함을 규명하고 구조를 바꿈
- 라인 추종 **PD 루프**(KP=60 · KD=25 · 20ms = 50Hz) — 적분항 없음
  - 🔴 *2026-09-02 정정.* 이 값은 `docs/06_firmware/README.md` 기준 **「벤치 방향 검증용
    초깃값」**이고 실전 게인 튜닝은 섀시 트랙 몫으로 남아 있다. 가상 라인 모드로
    조향 방향·비례·이탈 선회는 검증(7/22)했으나 **「안정된 추종을 얻었다」고 쓰면 과장**이다.
    DRIVE 주행이 시연에서 빠진 상태라 더욱 그렇다.

### P19. 파급력 및 기대효과 〔필수항목 6 · 🔴 필수〕

심사 배점 **활용성 20점**("기대효과 및 파급성 / 추후 발전 가능성")에 직접 대응한다.

> ⚠️ **작성 원칙**: 시장 규모·매출 추정 같은 **정량 수치는 근거를 댈 수 없으면 쓰지 않는다.**
> 심사 항목이 요구하는 것은 기대효과·파급성·발전 가능성이지 시장조사 수치가 아니다.
> 근거 없는 숫자는 오히려 신뢰를 깎는다.

**① 활용처**

- 위험물 취급 제조 사업장(반도체 FAB·정유·화학), 화학물질 보관창고, 물류창고 야간 무인 시간대
- 소방·안전관리 초동 대응 보조

**② 기대효과 — 사람이 위험물에 근접하는 횟수 자체를 줄인다**

- 감시의 공백(야간·연휴·교대 사이)을 메움
- 이상 발견 후 사람이 현장에 투입되기까지의 시간 동안 **격리라는 초동 조치가 이미 끝나 있는** 상태를 만듦
- 판정 근거(색상값·가스값·시각)가 EVENT LOG로 남아 사후 확인이 가능

**③ 발전 가능성 — 4개 확장축** (기존 「향후 계획」 내용)

- **위험물 분류 확장**: 현재는 색상 2분류(노랑/빨강) → 용기 라벨의 UN 번호·QR/바코드를 인식해 **MSDS(물질안전보건자료) 연동**으로 분류 체계 확장
- **초동 조치 범위 확장**: 현재는 "집어서 격리함에 넣고 뚜껑 닫기" → 밸브 잠그기, 국소 배기 가동, 흡착제·중화제 살포, 스필 컨테인먼트 전개 등으로 확장
- **온보드 자립 추론**: 현재는 ACT 정책이 노트북 GPU에서 돌고 USB로 팔을 제어한다 → 현장에서는 로봇이 스스로 판단해야 하므로, **온보드 추론의 정지 원인을 규명**하거나 **엣지 NPU 가속기**를 얹어 노트북 없이 도는 구조로 만든다
  - *2026-09-02 교체.* 종전의 「관제·알림 연동(SCADA/DCS)」을 뺀 자리다. 네 축이 전부 범위 넓히기라 **로봇 자체가 자립하는 축이 비어 있었고**, P16에서 노트북 단독 경로로 확정했다고 밝힌 만큼 그 다음 걸음을 여기서 받는 편이 낫다고 판단했다. 차점안은 「방폭·현장 규격 대응」(Ex 등급)이었다
- **전 구역 주행·다중 로봇**: **SLAM 기반 전 구역 주행**으로 확장, 넓은 사업장 대비 **다중 로봇 협업**(구역 분담·작업 핸드오프)

## 5. 발표 준비 메모 (슬라이드 내용 아님)

- **질문 대비 1**: "판정되면 로봇팔이 자동으로 반응하는 걸 실물로 몇 번 확인했나?" → 코드(`arm_act_node.py`)는 구현돼 있으나 이 자동 연동 자체의 실물 성공 사례는 없다는 점을 솔직히 답할 준비. 판정 로직과 파지 정책은 각각 검증됨을 강조.
- **질문 대비 2**: "순찰 주행(이동)은 왜 시연에 없나?" → `doc-framing-no-motor` 원칙대로 "미구현"이 아니라 "이번 촬영 범위에서 제외"로 답변. DRIVE 보드의 안전 우선순위 로직 자체는 구현·설명 가능.
- **질문 대비 3**: "노란색이 즉시 위험이라면서 왜 대시보드는 L0인가?" → HAZARD LEVEL은 종합 판정이 아니라 **가스 지표**다. 황색 판정 근거는 VISION 색상값과 EVENT LOG 문장. (P14)
- **수치 재확인**: 86.7% / 30회 / 근거리 100%는 **ACT 파지**, 판정 로직은 **7회 케이스 확인**(%아님) — P15 참고.
