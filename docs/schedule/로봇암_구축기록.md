## 1. 최종 하드웨어 구성

```
12V 5A 어댑터 ──▶ Waveshare Bus Servo Adapter (A) ──3핀──▶ 팔로워 STS3215 ×6
노트북 ──USB──▶ 동일 어댑터  [COM3, CH343]

12V 5A 어댑터 ──▶ XL4015 (7.4V 강압) ──▶ Bus Servo Adapter (B) ──3핀──▶ 리더 STS3215 ×6
노트북 ──USB──▶ 동일 어댑터  [COM5, CH343]
```

| 항목 | 팔로워 | 리더 |
|---|---|---|
| COM 포트 | **COM3** | **COM5** |
| 전원 | 12V 직결 | **XL4015 7.4V** |
| 실측 전압 | 12.3~12.4V | 무부하 7.43V / 부하 7.36V / 서보 보고 7.3~7.4V |
| LeRobot 타입 | `so101_follower` | `so101_leader` |
| 캘리브레이션 id | `follower_arm` | `leader_arm` |

> 🔴 **리더에 12V 를 물리면 서보 6개가 즉시 파손된다** (₩178,315, 복구 불가).
> 7.4V 라인에 라벨을 붙여 둘 것. COM 번호는 USB 포트를 바꿔 꽂으면 달라지므로
> **전압으로 구분**하는 것이 확실하다 — `check_leader.py --volt-only` 가 7.4V 면 리더다.

### 반이중 버스 원칙

STS3215 는 1선 반이중이라 **마스터는 1개뿐**이다. USB 어댑터가 마스터이므로
**ESP32 를 서보 3핀 버스에 연결하면 통신이 깨진다.** (v5 §2.1)

## 2. 전원 구성 — XL4015 7.4V 레일

되돌릴 수 없는 단계다. **멀티미터 없이 진행하지 말 것.**

1. **입력 극성 측정** — 12V 어댑터 케이블의 어느 심선이 +인지 멀티미터로 확정.
   색(빨강/검정)은 관습일 뿐 근거가 아니다. 배럴잭 케이블은 양쪽 다 검정인 경우가 흔하다.
   저가 XL4015 에는 **역극성 보호가 없어** 뒤집으면 즉시 파손된다.
2. `IN+` / `IN−` 연결
3. **출력에 아무것도 물리지 않은 상태로** 전압 트리머를 돌려 **7.4V** 로 조정
4. **전원 재투입 후 재확인** — 드라이버를 떼는 순간 값이 틀어지는 경우가 있다
5. 출력 극성 측정 → Bus Servo Adapter VIN 연결 → **터미널에서 다시 측정**
6. 그 다음에야 서보 연결
7. 서보 연결 후 **부하 상태 전압 재측정** (7.2~7.45V 정상)

### 트리머 관련 함정

| 증상 | 원인 | 대처 |
|---|---|---|
| 아무리 돌려도 값이 안 변함 | **다회전 트리머** — 전 범위에 10~15바퀴 필요 | 한 방향으로 20바퀴 |
| IN 과 OUT 이 **둘 다 12V** | 강압이 아니라 통과(100% 듀티) 상태 = 트리머가 상한 | **반시계로** 20바퀴 |
| 트리머 2개 | CC/CV 형 | **무부하에서 전압이 변하는 쪽**이 CV |
| 무부하는 정상, 부하 걸면 전압 붕괴 | CC(전류 제한)가 낮게 걸림 | CC 를 시계 방향 끝까지 |

12V 입력에서 **최대 출력은 약 10.5V** 다 (강압에 1.5V 헤드룸 필요). 12V 가 그대로 나오면
조절 가능 범위를 이미 벗어난 것이라 시계 방향으로는 변화가 없다.

> CC 를 최대로 올려도 안전한 이유: 리더암은 텔레옵 내내 **토크가 꺼져 있어**
> (`SOLeader.configure()` 가 `disable_torque()` 호출) 실소모가 1A 미만이고,
> 상위 보호는 XL4015 자체 5A 정격 + 12V 어댑터 보호가 담당한다.
> **CC 를 어중간하게 낮춰 두는 것이 최악** — 보호도 안 되면서 전압만 불안정해진다.

## 3. 서보 ID 부여

출고 기본값은 **전 서보 ID=1** 이다. 6개가 동시에 응답하면 파형이 겹쳐
**버스가 통째로 죽는다** — 스캔 결과가 "응답 없음" 으로 나온다.

> 🔴 이것이 2026-06-15 팔로워에서 몇 시간을 날린 그 증상이다 (`archive/로봇암_초기계획_2026-07.md` §6-1).
> **ID 부여 전이면 무응답이 정상**이다. 배선을 의심하지 말 것.
> 서보를 **하나만** 연결해서 스캔하면 즉시 판별된다.

### 순서 — 끝단에서 베이스 방향

`lerobot-setup-motors` 는 `reversed()` 로 순회한다. 조립된 팔에서 손목 쪽부터
하나씩 떼어내며 진행하면 맞아떨어진다.

| 순서 | 축 | 물리 위치 | ID |
|---|---|---|---|
| 1 | `gripper` | 집게 구동 | 6 |
| 2 | `wrist_roll` | 손목 회전 | 5 |
| 3 | `wrist_flex` | 손목 상하 굽힘 | 4 |
| 4 | `elbow_flex` | 팔꿈치 | 3 |
| 5 | `shoulder_lift` | 어깨 상하 | 2 |
| 6 | `shoulder_pan` | 베이스 회전 (맨 아래) | 1 |

> 🔴 **ID = 물리적 관절 위치**다. 엉뚱한 서보를 물린 채 실행하면 통신은 정상인데
> 관절이 뒤바뀌어 움직이는, 찾기 어려운 고장이 된다.
> 실제로 이번에 첫 시도에서 베이스를 물린 채 `gripper` 를 실행할 뻔했다.
> **ID 부여 후 마스킹테이프로 번호를 붙여 둘 것.**

버스에 서보가 2개 이상이면 `_find_single_motor()` 가 RuntimeError 를 던지므로
조용히 잘못되지는 않는다. STS3215 는 3핀 포트가 2개라 **양쪽 이웃 케이블을 모두 분리**해야 한다.

## 4. 캘리브레이션

`lerobot-calibrate` 는 프롬프트 2개가 한 프로세스에 묶여 있어 단계를 쪼갠
`tools/calibrate_leader.py` 를 사용했다. 내부 동작은 `SOLeader.calibrate()` 와 동일하다.

```
--step raw      Homing_Offset 을 0 으로 지우고 원시 엔코더 범위 측정
--step trace    한 축의 시계열을 기록해 불연속 점프(래핑) 탐지
--step offset   Homing_Offset 을 직접 기록 (래핑 지점 이동용)
--step aim      원시 목표값까지 얼마나 남았는지 표시
--step homing   현재 자세를 2047 로 재정의 (--skip 으로 축 제외 가능)
--step ranges   가동 범위 기록 → 서보 EPROM + JSON 저장
```

### 중간 자세가 핵심이다

> 팔이 쉬는 자세(어깨 처짐 · 팔꿈치 접힘)는 **사실상 그 관절의 기계적 한계**다.
> 거기서 영점을 잡으면 반쪽만 기록되거나 엔코더 경계를 넘어 래핑한다.
> — 2026-06-15 팔로워 캘리브레이션 4회 실패의 원인 (`archive/로봇암_초기계획_2026-07.md` §6-2)

**반드시 원시 범위를 먼저 측정하고 그 한가운데를 중간 자세로 삼을 것.**
`--step aim` 이 축별 허용 오차를 계산해 준다. 허용 폭은 `(4095 - 2×EDGE) - span` 이라
**가동 범위가 좁은 축일수록 넉넉**하다.

### 최종 값 (2026-07-11, leader_arm)

| 축 | ID | homing_offset | range_min | range_max | 범위 | 팔로워 |
|---|---|---|---|---|---|---|
| shoulder_pan | 1 | -1402 | 776 | 3439 | 234.1° | 238° |
| shoulder_lift | 2 | **-1061** | 991 | 3219 | 195.8° | 201° |
| elbow_flex | 3 | 285 | 629 | 2816 | 192.2° | 195° |
| wrist_flex | 4 | 1167 | 762 | 3077 | 203.5° | 204° |
| wrist_roll | 5 | **78** | 0 | 4095 | (연속 회전축) | — |
| gripper | 6 | 31 | 2037 | 3307 | 111.6° | 130° |

**합격 기준: 전 축 `MIN < 2047 < MAX`, 0/4095 미접촉** (wrist_roll 제외).
5축 모두 팔로워 실측치와 일치한다.

### 저장 위치 — 리더와 팔로워가 다르다

```
팔로워: ~/.cache/huggingface/lerobot/calibration/robots/so_follower/follower_arm.json
리더:   ~/.cache/huggingface/lerobot/calibration/teleoperators/so_leader/leader_arm.json
```

팔로워는 **robot**, 리더는 **teleoperator** 로 분류된다. 디렉터리명은 `so_follower` / `so_leader`
로, `so101_*` 은 등록된 별칭일 뿐 실제 클래스명이 경로가 된다.
프로젝트 백업은 `calibration/` 에 있다.

## 5. 🔴 막혔던 지점 — 재발 주의

### 5-1. shoulder_lift 엔코더 래핑

**증상**: 가동 범위가 359° 로 측정됨. 어깨 관절이 359° 돌 수는 없다.

**판별**: `--step trace` 로 시계열을 보면 **한 샘플 만에 4079 → 1 (변화 -4078)** 로 튄다.
연속 추적이면 매끄럽고, 래핑이면 이렇게 점프한다. 이 둘은 대처법이 정반대라 반드시 구분해야 한다.

**원인**: 이 축의 물리적 가동 범위가 **원시 엔코더 0 을 가로지른다.**
`set_half_turn_homings()` 는 `reset_calibration()` 으로 오프셋을 0 으로 만든 뒤
현재 위치를 2047 로 맞추는데, 원시 엔코더 자체가 감기므로 **표준 절차로는 해결되지 않는다.**

**해결**: Feetech 서보는 `Present_Position = Actual_Position - Homing_Offset` 을
**4096 모듈로로 계산**하므로, 오프셋을 바꾸면 **감김 지점 자체가 이동한다.**
관절이 지나가지 않는 구간으로 밀면 사라진다.

```
필요한 오프셋 3035  →  ±2047 한계 초과
                   →  모듈로 등가인 -1061 을 사용 (3035 - 4096)
결과: 범위 1000~3094, 중앙 2047, 양쪽 여유 ~1000
```

> `Homing_Offset` 은 **부호+크기 12비트**라 **±2047 이 한계**다.
> 2048 을 쓰면 `ValueError: Magnitude 2048 exceeds 2047` 이 난다.
> 모듈로 등가값으로 접어 넣으면 된다.

**🔴 재캘리브레이션 시**: `lerobot-calibrate` 를 그냥 돌리면 이 값이 덮어써져 래핑이 재발한다.
반드시 아래를 사용할 것.

```powershell
python tools\calibrate_leader.py --port COM5 --step homing --skip shoulder_lift
```

근본 해결은 어깨 서보 혼을 재장착해 가동 범위를 엔코더 중앙으로 옮기는 것이다.
분해가 필요하므로 이번에는 오프셋 방식을 택했다.

### 5-2. wrist_roll 영점 불일치

**증상**: 회전 **방향**은 같은데 **위치**가 일정하게 어긋난다.
리더 집게가 0° 를 볼 때 팔로워는 147° 를 본다.

**원인**: 나머지 5축은 `range_min~range_max` 가 물리적 가동 한계로 기록되어
정규화 기준이 팔의 구조에 묶인다. 두 팔이 같은 구조면 자동으로 일치한다.
그런데 **wrist_roll 은 연속 회전축이라 LeRobot 이 range 를 0~4095 로 고정**하므로,
정규화 기준점이 **오직 `homing_offset` 하나로** 정해진다.
→ 캘리브레이션을 실행한 순간의 손목 각도 차이가 **그대로 상수 오프셋으로 남는다.**

**해결**: `tools/sync_wrist_roll.py`

1. 두 팔의 손목을 **눈으로 같은 방향**에 맞춘다 (집게가 같은 쪽을 향하게)
2. 측정 → 차이를 카운트로 환산 → 리더 `homing_offset` 보정
3. `--apply` 로 **서보 EPROM + JSON 2곳**에 기록

```
리더 wrist_roll  homing_offset  1745 → 78   (보정 -1667 = -147°)
```

> `homing_offset` 은 `drive_mode` 와 달리 **서보에도 기록되고 `is_calibrated()` 가 대조**한다.
> 서보와 JSON 중 하나만 고치면 다음 연결 때 재캘리브레이션 프롬프트가 뜬다.

**🔴 재캘리브레이션 시 매번 재발한다.** 캘리브레이션 후 반드시 이 도구를 한 번 돌릴 것.

### 5-3. 그리퍼 방향 — 오탐이었음 (조사 완료, 재조사 불필요)

처음에 "그리퍼가 서로 반대방향" 으로 보고되어 `drive_mode=1` 을 적용했으나,
**측정 결과 원래 방향이 맞았다.**

```
리더 닫힘 0.9  ↔  팔로워 닫힘 1.8      → drive_mode=0 에서 이미 일치
```

실제 문제는 5-2 의 `wrist_roll` 이었다. `drive_mode` 는 **원래대로 0** 이다.

참고로 `drive_mode` 는 **호스트 측 JSON 전용 값**이다.

```python
# feetech.write_calibration — Homing_Offset / Min·Max_Position_Limit 만 기록
# feetech.read_calibration  — drive_mode=0 하드코딩
# feetech.is_calibrated     — range·offset 만 비교 (drive_mode 제외)
```

따라서 `drive_mode` 는 JSON 만 고치면 되고 재캘리브레이션 프롬프트도 뜨지 않는다.

### 5-4. PowerShell 스크립트 한글 깨짐

**증상**: `.ps1` 의 `Write-Host` 한글이 깨진다. 파이썬 출력은 멀쩡하다.

**원인**: `powershell.exe`(Windows PowerShell 5.1)는 **BOM 이 없으면 스크립트 파일을
ANSI(cp949)로 읽는다.** 깨짐이 **출력 시점이 아니라 파일 파싱 시점**에 일어나므로
파이썬이 실행 중에 내보낸 문자열은 영향을 받지 않는다.

**해결**: `.ps1` 을 **UTF-8 with BOM** 으로 저장.

| 파일 | BOM |
|---|---|
| `.ps1` (한글 포함) | ✅ **필요** |
| `.py` | ❌ 불필요 |
| `.json` | 🔴 **있으면 파싱 실패** (`Unexpected UTF-8 BOM`) |

> PowerShell 의 `Out-File -Encoding utf8` / `Set-Content -Encoding utf8` 은 5.1 에서
> **BOM 을 붙인다.** JSON 을 쓸 때 이것 때문에 실패한다.

### 5-6. 텔레옵 시작 시 팔로워가 혼자 움직인다 — `Goal_Position` 이 남아 있다

**증상**: 정렬 확인(`check_align.py`)을 **통과했는데도** 텔레옵을 시작하는 순간
팔로워의 특정 축, 특히 **손목이 명령 없이 혼자 움직인다.**

**원인**: 서보의 `Goal_Position` 은 **토크가 꺼져 있어도 마지막 명령값으로 남는다.**
그 사이 팔이 중력으로 처지거나 손으로 옮겨지면 `Goal` 과 `Present` 가 벌어지고,
**토크가 켜지는 순간 서보가 저장된 `Goal` 로 되돌아간다.**

LeRobot 의 `SOFollower.configure()` 는 Operating_Mode·PID·그리퍼 토크제한만 설정하고
**`Goal_Position` 을 동기화하지 않는다.** `connect()` 의 주석이 그 설계를 드러낸다 —
*"We assume that at connection time, arm is in a rest position."*
팔이 마지막 명령 위치에 그대로 있다고 가정하는 것인데, 실제로는 그렇지 않다.

**🔴 정렬 확인으로는 절대 잡히지 않는다.** `check_align.py` 는 `Present_Position` 만
비교하기 때문이다. 두 검사는 서로 다른 것을 본다.

| 검사 | 보는 것 | 막는 사고 |
|---|---|---|
| `check_align.py` | 리더 vs 팔로워의 **Present** | 시작 시 **리더 자세로** 튀는 것 |
| `check_goal.py` | 팔로워의 **Goal vs Present** | 시작 시 **이전 세션 위치로** 되돌아가는 것 |

**실측 (2026-07-10)** — 정렬 확인을 통과한 상태에서도 5개 축이 어긋나 있었다.

| 축 | 현재 | 목표 | 차이 | 튀는 각도 |
|---|---|---|---|---|
| **wrist_roll** | 4032 | 3289 | **-743** | **65°** |
| wrist_flex | 2962 | 2663 | -299 | 26° |
| shoulder_pan | 2457 | 2715 | +258 | 23° |
| shoulder_lift | 1473 | 1626 | +153 | 13° |
| elbow_flex | 3013 | 2900 | -113 | 10° |
| gripper | 1339 | 1325 | -14 | ✅ |

손목이 가장 크게 튄다는 관찰과 정확히 일치한다.

**해소**: 토크를 켜기 전에 `Goal_Position = Present_Position` 으로 맞춘다.

```powershell
python tools\check_goal.py --port COM3 --fix
```

**`teleop.ps1` 에 통합되어 있으므로 별도 실행은 불필요하다.** 순서가 중요하다 —
**정렬 조정이 끝난 직후, 텔레옵 시작 직전**에 실행해야 한다.
그 사이에 팔을 움직이면 다시 벌어진다.

> 매 세션 재발한다. 팔이 처지는 것을 막을 수 없기 때문이다.
> 스크립트를 쓰지 않고 `lerobot-teleoperate` 를 직접 실행할 때는 **반드시 먼저 돌릴 것.**

### 5-7. 🔴 손목 129° 폭주 — DEGREES 모드는 goal 을 잘라주지 않는다 (2026-07-06 해결)

**증상**: §5-6 까지 전부 처리했는데도 텔레옵을 시작하면 팔로워 손목이
리더 명령과 무관하게 **매번 약 129° 회전해 raw 2048 부근(2044~2055)에서 멈췄다.**
그 과정에서 그리퍼 배선이 감기며 과부하가 6회 이상 재발했다.

**원인 사슬** — 전 단계를 설치된 LeRobot 소스에서 확인했다.

1. `so101_follower`/`so101_leader` config 는 **`use_degrees=True` 가 기본값**이다.
   몸체 관절은 ±100 정규화가 아니라 **각도(°)** 로 통신한다.
2. DEGREES 모드는 0° 기준을 **캘리브레이션 창의 중앙**으로 삼고, 읽기·쓰기
   **어디에서도 값을 잘라주지 않는다** (`motors_bus.py` 의 `_normalize`/`_unnormalize`
   DEGREES 분기에는 RANGE 분기에 있는 클램프가 없다).
3. 리더 손목이 창(3201~4001) 밖 raw 977 에 있는 채로 시작 →
   (977−3601)×360/4095 = **−230.7°** → 팔로워 goal = 576−2624 = **−2048**
4. `Goal_Position` 은 sign bit 15 로 인코딩된다: −2048 → **0x8800**.
   서보는 하위 12비트만 취해 **raw 2048** 로 해석하고 그리로 충실히 이동한다.
   575 → 2048 = +1473카운트 = **129.5° — 관측값과 정확히 일치.**

**왜 기존에는 됐나**: 순정 캘리브레이션은 wrist_roll 범위를 0~4095 로 강제해
창 중앙이 2047.5 였고, homing 이 두 팔의 휴식 자세를 2048 근처에 맞춰놨다.
어떤 자세든 각도 값이 온건했다. 좁은 창(±35°) + homing=0 재설계가
0° 기준을 창 중앙으로 옮기면서 **리더가 창 밖에 있으면 즉시 폭주**가 된 것이다.

**check_align 이 못 잡은 이유**: 정규화 값을 [0,1] 로 잘라서 비교했다.
리더 손목이 창 밖 **어디에 있든** −100 으로만 보였고 "35° 회전 ✅" 로 통과시켰다.

**서보 고장 의심은 오진이었다**: 폭주 직후 raw 2055 에서 돌린 위치 유지 시험은
창에서 129° 벗어나 **배선이 감긴 영역**에서의 시험이었다. 케이블 복원력에 맞서
최대 부하(−1000)로 버티다 과부하가 난 것 — 그 위치에선 정상 서보도 그렇게 된다.

**해결 (적용 완료)**

1. `teleop.ps1` 이 `--robot.use_degrees=false --teleop.use_degrees=false` 를 강제한다.
   RANGE 모드는 리더 읽기·팔로워 goal 을 **모두 창 안으로 잘라** 이 경로를 차단한다.
2. `check_align.py` 가 클램프 없이 비교하고, **창 밖 축은 raw 값과 함께 무조건 차단**한다.

**검증 (2026-07-16)**: 30초 완주, 약 60Hz, 오류·재시도 0.
종료 후 wrist_roll = 571 (기준 575, 차이 0.4°). 수정 전에는 매번 2048 이었다.

> 🔴 **`lerobot-record` 와 정책 평가(배포) 실행에도 두 플래그를 반드시 붙일 것.**
> 플래그가 액션 스케일 자체를 바꾸므로 수집·학습·배포가 **같은 모드**여야 한다.
> 플래그 없이 수집한 데이터와 플래그 붙인 배포는 서로 호환되지 않는다.

### 5-8. 손목 가동범위 확장 70° → 221° → **최종 314°** — 위치 한계는 원시 좌표가 아니다 (2026-07-08)

> **최종값은 ±157°(총 314°)** 다. 아래 본문의 221°/±110° 는 같은 날 낮의 중간 결과이고,
> 카메라 장착 후 재측정에서 다시 넓어졌다 (절 끝의 ⚠ 참조). 현행 값은 `calibration/README.md`.

**결과**: 손목 가동범위 **70° → 221°** (3.2배), 중립 기준 **±110° 대칭**.
양팔 정렬 유지, 과부하 없음.

**증상**: §5-7 해결 후 텔레옵은 정상인데 **손목 가동범위가 180° 보다 훨씬 좁았다.**

**원인 — 잘못된 전제가 코드에 박혀 있었다.**
`limit_wrist_roll.py` 는 위치 한계를 **원시 엔코더 기준**이라 보고,
창이 원시 0 을 가로지르면 "min > max 인 뒤집힌 범위가 된다"며 거부했다.
그 제약 때문에 창이 원시 0 을 피할 수 있는 ±35°(176~976) 로 묶였다.

**팔로워 6축을 직접 읽어 반증했다.**

| 축 | homing | 서보 Min~Max | JSON range | 원시로 환산 | 상태 |
|---|---|---|---|---|---|
| shoulder_pan | 1672 | 1151~3856 | 동일 | 2823~**1432** | 원시 0 가로지름 — **정상** |
| shoulder_lift | -1563 | 1462~3746 | 동일 | 3995~**2183** | 원시 0 가로지름 — **정상** |
| elbow_flex | 1496 | 804~3021 | 동일 | 2300~**421** | 원시 0 가로지름 — **정상** |
| wrist_flex | 1999 | 919~3242 | 동일 | 2918~**1145** | 원시 0 가로지름 — **정상** |
| gripper | -1510 | 1313~2793 | 동일 | 3899~**1283** | 원시 0 가로지름 — **정상** |

**5축 모두** 원시 0 을 가로지르는 창으로 처음부터 멀쩡히 돌아가고 있었다.
그리고 서보 `Min/Max_Position_Limit` 이 JSON `range_min/max` 와 **정확히 일치**한다.
JSON 값은 `Present_Position`(= 원시 − Homing_Offset)으로 측정된 것이므로,
**위치 한계는 보고 좌표 기준이다.** 원시 0 가로지름은 애초에 문제가 아니었다.

> 애초에 그럴 수밖에 없다 — shoulder_pan 의 range_max 3856 에 homing 1672 를 더하면
> 5528 로 12비트를 넘는다. 한계가 원시 기준이라면 표현 자체가 불가능하다.

**설계 — 비대칭 창**
실측 가동범위가 영점 기준으로 크게 치우쳐 있다. 영점 대칭으로 잡으면 좁은 쪽에
묶여 손해가 크므로, **양팔 실측의 교집합을 창으로 쓰고 그 중점을 present 2048 에 놓는다.**
양팔이 **같은 폭 · 영점의 같은 상대위치**를 쓰므로 정규화가 1:1 로 대응하고
기존 그리퍼 방향 정렬이 그대로 유지된다. 중점을 2048 에 두면 보고 좌표의
불연속(present 0/4095)이 창에서 가장 멀어진다.

**🔴 측정 기준이 결과를 좌우한다 — 3차까지 계속 늘었다**

| 회차 | 측정 지시 | 팔로워 | 리더 | 교집합 |
|---|---|---|---|---|
| 1차 | "팽팽해지기 **시작**하는 곳까지" | 177° | 184° | 174° |
| 2차 | "뻣뻣한 저항이 **분명한** 곳까지" | 276° | 240° | 227° |
| 3차 | "실제 기계적 **한계**까지" | **332°** | **333°** | **308°** |

1차만 보고 "배선의 물리적 한계가 174° 이므로 180° 는 불가능하다"고 결론지었으나
**완전히 틀렸다.** 같은 하드웨어에서 3차는 308° 가 나왔다.
**"장력이 시작되는 지점"은 물리적 한계가 아니다.**
측정 지시가 모호하면 회차마다 다른 값이 나오고, 그 위에 세운 결론이 통째로 흔들린다.
3차에서 양팔이 332°/333° 로 거의 일치한 것이 실제 한계에 도달했다는 방증이다.

**최종값 (2026-07-08)**

```
교집합(영점 기준)   −2348 ~ +1357        여유 100 적용 → −2248 ~ +1257
창                  present 791 ~ 3305    (±1257 = ±110°, 총 221°)
Homing_Offset       팔로워 −1472 / 리더 1553
영점(그리퍼 정렬 방향) present 2048 = 창 중점 (완전 대칭)
```

창 폭을 정한 것은 배선이 아니라 **"중립 대칭을 유지하는 최대치"** 다.
+ 방향 실측(팔로워 1430 / 리더 1357)에서 여유 100 을 뺀 1257 이 대칭 폭의 상한이다.
이보다 넓히려면 다시 비대칭이 되어(최대 −197°/+110°) 조작감이 나빠진다.

**중심 배치도 함께 고쳤다.** 상한에 걸려 교집합보다 좁은 창을 쓸 때 중점을
교집합 중점에 두면 중립이 창 한쪽으로 몰린다 (실제로 −140°/+39° 로 갈렸다 —
총 180° 인데 한쪽은 39° 밖에 못 도는 셈). **중점을 중립에 최대한 가깝게 클램프**하도록
바꿔 같은 폭에서 −119°/+61° 가 되었고, 3차 측정 후에는 완전 대칭이 되었다.

**검증 ① 각도별 정착 부하 (`--profile`)** — 18° 씩 나가며 각 지점을 유지하는 힘

| 각도 | +18° | +53° | +88° | +110° | −18° | −53° | −88° | −110° |
|---|---|---|---|---|---|---|---|---|
| 정착 부하 | −56 | −52 | −60 | −96 | +64 | +52 | +48 | +84 |

**전 구간 44~96 (한계의 10% 미만).** 끝단에서도 배선이 뻣뻣해지지 않는다.

> 이 측정이 필요했던 이유: `--goal-test` 에서 최대 부하 **548** 이 나와 중단 임계값 600 에
> 근접했다. 그러나 그것은 1242카운트를 **한 번에 가속**한 탓이고, 정착 부하는 낮았다.
> 텔레옵은 60Hz 로 조금씩 추종하므로 프로파일 쪽 조건에 해당한다.
> **순간 최대 부하만 보고 판단하면 안 된다** — 자세를 유지하는 힘이 실사용 부하다.

**검증 ② 창 끝단 추종 (`--goal-test`)**: ±109° 왕복 전 구간 도달, 오차 ≤28카운트.

**검증 ③ 텔레옵 30초**: 1567 루프, 재시도 0, **과부하 0**.

어제 −1000 포화로 과부하 났던 그 서보다. §5-7 의 "서보 고장" 오진이 완전히 반증됐다.

**도구에서 잡은 버그 2개**

1. **영점 기준이 밀린다.** `measure()` 가 영점을 "창 중점"으로 가정했는데,
   §5-8 에서 창을 영점 비대칭으로 잡은 뒤로는 성립하지 않는다. 한 번 적용한 뒤
   다시 측정하니 팔로워 기준이 raw 576 → 105 로 **471 카운트 어긋났고**, 그대로
   진행했으면 양팔 정렬이 41° 깨질 뻔했다.
   → 정렬 영점을 **원시 엔코더 값**으로 `calibration/wrist_zero.json` 에 고정했다.
   창이나 `Homing_Offset` 을 바꿔도 이 값은 건드리지 않는다.

2. **고정 시간 대기가 오탐을 만든다.** 목표를 쓰고 1.5초 뒤 판정했는데,
   저속(400카운트/초) 설정에서 960카운트 이동에는 2.4초가 걸린다.
   **아직 이동 중인 것을 "추종 실패"로 판정**했다 (오차 +350, 그러나 부하는 +136 뿐).
   → **멈출 때까지 관찰**하는 방식으로 교체했다 (도착·정지·과부하·시간초과 구분).
   부하가 낮은데 목표에 못 미치면 막힌 것이 아니라 이동 중이다.

3. **검증이 창 안쪽만 봤다.** `--goal-test` 가 창의 90% 지점까지만 왕복해,
   정작 텔레옵이 명령할 수 있는 **끝단**을 확인하지 않았다.
   → 끝단에서 15카운트 안쪽까지 시험하도록 바꿨다.

**재측정 절차 (손목 카메라 장착 후 반드시 실행)**

```powershell
python tools\widen_wrist_roll.py --measure --arm follower --seconds 50
python tools\widen_wrist_roll.py --measure --arm leader   --seconds 50
python tools\widen_wrist_roll.py --plan --max-half 1257
python tools\widen_wrist_roll.py --apply --arm follower --max-half 1257
python tools\widen_wrist_roll.py --apply --arm leader   --max-half 1257
python tools\widen_wrist_roll.py --profile   --max-half 1257   # 각도별 정착 부하
python tools\widen_wrist_roll.py --goal-test --max-half 1257   # 끝단 추종
.\teleop.ps1 -Seconds 30
```

🔴 `--max-half` 는 `--plan` 이후 **모든 단계에 같은 값**을 넘겨야 한다. 값이 다르면
계획이 달라져 양팔에 서로 다른 창이 적용되고 손목 방향이 어긋난다.

> 🔴 `limit_wrist_roll.py` 는 이 잘못된 전제를 아직 담고 있다. **쓰지 말 것.**
> 손목 범위 작업은 `widen_wrist_roll.py` 를 쓴다.

> ⚠ **이 절의 ±110°(총 221°) 값은 2026-07-08 밤에 갱신됐다.** 손목 카메라 장착 후
> 재측정하여 창을 **±157°(총 314°, `--max-half 1788`)** 로 넓혔고, 창 중심을 정렬 영점이
> 아니라 **기본위치(영점 −44°, `follower_home.json`)** 에 뒀다 — 시작 자세 기준 양방향
> 대칭이 되도록. Homing 팔로워 −1968 / 리더 1057, 창 260~3836. 전 구간 정착 부하 ≤48,
> 끝단 추종 오차 ≤8카운트, 텔레옵 60초 무결 확인. 현행 값은 `calibration/README.md` 가 기준.

> PowerShell 은 **따옴표로 시작하는 줄을 문자열로 해석**한다.
> 맨 앞의 `&`(호출 연산자)를 빠뜨리면 `UnexpectedToken` 이 난다.
> **따옴표를 쓰면 `&` 도 쓴다**고 외워 둘 것.

### 🔴 시작 전 자세 정렬

텔레옵은 시작하는 순간 **팔로워 토크를 켜고 리더 자세로 추종**시킨다.
두 팔이 크게 어긋나 있으면 그 순간 급격히 움직여 3D 프린팅 파츠나 기어에 충격이 간다.

```powershell
python tools\check_align.py --leader COM5 --follower COM3
python tools\check_goal.py  --port COM3 --fix     # §5-6 — 정렬 조정 후, 시작 직전
```

`teleop.ps1` 은 두 검사를 순서대로 돌리고, **정렬에 실패하면 텔레옵을 시작하지 않는다.**

```
[1/3] 자세 정렬 확인          리더 vs 팔로워 Present  — 실패 시 중단
[2/3] Goal_Position 동기화     팔로워 Goal ← Present   — 자동 교정
[3/3] 텔레옵 시작
```

wrist_roll 은 가동범위 판정에서는 제외하되 **회전 각도로 따로 본다** (45° 초과 시 불합격).
손목 카메라·그리퍼 배선이 지나는 축이라 꼬임 위험이 있기 때문이다.

### 6-1. 🔴 Smart App Control — 모든 `lerobot-*` 명령이 막힌다 〔2026-06-10〕

**증상**: `teleop.ps1` 의 `[1/4]~[3/4]` 는 전부 통과하는데 `[4/4]` 에서만 실패한다.

```
'lerobot-teleoperate.exe' 프로그램을 실행하지 못했습니다.
애플리케이션 제어 정책에서 이 파일을 차단했습니다
```

**원인**: Windows 11 **Smart App Control 이 Enforce 상태**다
(`HKLM:\SYSTEM\CurrentControlSet\Control\CI\Policy` → `VerifiedAndReputablePolicyState = 1`).
pip 이 `Scripts\` 에 만드는 콘솔 스크립트는 **서명 없는 작은 `.exe` 런처**라 평판 검사에서 걸린다.
`[1/4]~[3/4]` 가 통과한 이유는 그것들이 `python.exe`(서명됨) 직접 호출이기 때문이다.

**대처**: `.exe` 를 쓰지 않고 **같은 진입점을 모듈로 부른다.**

```powershell
# 막힘
& "...\Scripts\lerobot-teleoperate.exe" <args>

# 통과
& "...\python.exe" -m lerobot.scripts.lerobot_teleoperate <args>
```

진입점 대응은 `site-packages\lerobot-0.4.4.dist-info\entry_points.txt` 에 있다.
`lerobot-<이름>` → `lerobot.scripts.lerobot_<이름>` 규칙이 전부 동일하다.

| 명령 | 모듈 |
|---|---|
| `lerobot-teleoperate` | `lerobot.scripts.lerobot_teleoperate` |
| `lerobot-record` | `lerobot.scripts.lerobot_record` |
| `lerobot-train` | `lerobot.scripts.lerobot_train` |
| `lerobot-find-port` | `lerobot.scripts.lerobot_find_port` |
| `lerobot-calibrate` | `lerobot.scripts.lerobot_calibrate` |
| `lerobot-find-cameras` | `lerobot.scripts.lerobot_find_cameras` |

> 🔴 **Smart App Control 을 끄지 말 것.** 한 번 끄면 **Windows 재설치 전에는 다시 켤 수 없다.**
> 끄는 것은 이 문제의 해법이 아니다 — `-m` 우회로 기능 손실 없이 해결된다.
>
> 🔴 **`teleop.ps1` 만 고쳐서는 부족하다.** 데이터 수집(`lerobot-record`)과 학습(`lerobot-train`)이
> 같은 벽에 부딪힌다. 수집 당일에 발견하면 그날을 잃는다 — 스크립트를 새로 쓸 때마다 `-m` 으로 쓸 것.

**COM 포트 확인**


```
⑧ 중간 자세 조준           calibrate_leader.py --step aim
```

## 10. 학습 환경 벤치마크 (2026-07-28)

하드웨어 완성 전에 **학습 파이프라인만 먼저 검증**했다.
연산 특성은 카메라가 무엇을 보는지와 무관하므로, 섀시·환경 없이도 측정 가능하다.
버릴 데이터 3 에피소드(15초 ×3)를 녹화해 400 step 을 돌렸다.

### 환경

```
GPU            NVIDIA GeForce RTX 4060 Laptop, 8GB
torch          2.10.0+cu128   torchvision 0.25.0+cu128   CUDA 12.8
ACT 파라미터    51,597,190 (52M)   chunk_size=100   ResNet18
```

> **"`pip install lerobot[feetech]` 는 CPU 빌드 torch 를 설치한다"** 함정은 이미 회피된 상태다
> (`+cu128` 확인). §11 참조.

### 실측

| 항목 | 값 |
|---|---|
| 처리량 | **1.78 step/s** (400 step / 3분 44초) |
| GPU 연산 `updt_s` | 0.399 ~ 0.511 |
| 데이터 로딩 `data_s` | 0.011 ~ 0.016 (평시) / **0.389 (스파이크)** |
| VRAM | **4,459 / 8,188 MB** (batch_size=8) |
| GPU 사용률 | 평균 85.4%, 최대 100% |
| GPU 온도 | **77~85°C** |
| loss | 14.463 → 2.762 (단조 감소, `grdn` 270→81) |

### 결론

**1. 🔴 100,000 step ≈ 15.6 시간 — 학습 1회가 하룻밤이다.**
W3 일정의 실질 제약이 된다. v5 §6 참조. **재학습 기회는 1~2회뿐이다.**

> 🔴 **2026-08-04 이후 이 제약이 2배가 됐다.** 대상이 2개가 되면서 **정책도 2개**가 되었고
> (v5 §5.2 머리 블록), 두 학습은 같은 GPU 를 쓰므로 **순차 실행 = 15.6h × 2 ≈ 31시간**이다.
> 병렬로 돌릴 수 없다 — VRAM 은 남아도 GPU 가 이미 85% 사용 중이라 둘을 얹으면 둘 다 느려진다.
>
> - **재학습 기회는 사실상 1회**로 봐야 한다
> - **수집 순서는 황색(종이컵) 먼저.** 시간이 부족해지면 적색만 프리셋으로 내려도
>   영상의 핵심 컷(분할화면)이 살아남는다
> - **8/15 Go/No-Go 는 대상별로 판단**한다 (둘 다 Go / 한쪽만 / 둘 다 No-Go)

**2. VRAM 은 여유가 있다.** 8GB 중 4.4GB. `batch_size` 를 16으로 올릴 수 있으나
GPU 가 이미 85% 사용 중이라 처리량 개선폭은 크지 않을 것이다.

**3. `torchcodec` 은 현재로선 불필요하다 — 단 실데이터에서 재확인할 것.**
평시 `data_s` 는 전체의 3% 에 불과하다. 다만 3 에피소드짜리 캐시된 데이터셋에서도
**간헐적으로 0.389 까지 튄다.** 100 에피소드에서는 이 스파이크가 잦아질 수 있다.
→ **실제 수집이 10 에피소드쯤 모였을 때 이 벤치마크를 다시 돌려 `data_s` 를 확인할 것.**
   3% 가 30% 로 뛰면 그때 `torchcodec` 을 검토한다.

**4. 파이프라인 자체는 건강하다.** loss 단조 감소, gradient norm 안정화, NaN·발산 없음.
(2.4 에포크만 돌린 것이라 수렴 판단은 불가)

### 실행 명령

```powershell
& "C:\Users\sehi5\miniconda3\envs\lerobot\Scripts\lerobot-train.exe" `
  --dataset.repo_id=local/<이름> --dataset.root="<경로>" `
  --policy.type=act --policy.device=cuda --policy.push_to_hub=false `
  --output_dir="<출력경로>" --job_name=<이름> `
  --steps=100000 --batch_size=8
```

> 🔴 **`--policy.push_to_hub` 도 기본값이 `True` 다.** (`lerobot-record` 의 `--dataset.push_to_hub` 에 이어 두 번째)
> `repo_id` 가 없으면 실행 자체가 거부되어 사고는 막히지만, 학습 명령에도 반드시 붙여야 한다.
>
> `wandb` 는 기본 비활성(`enable=False`)이라 외부 전송이 없다.

### ⚠ 데이터 수집은 단일 시리얼 글리치에 취약하다

벤치마크용 녹화 중 아래로 세션이 통째로 중단됐다.

```
teleop.get_action() → sync_read("Present_Position")
ConnectionError: Failed to sync read on ids=[1..6] after 1 tries.
[TxRxResult] There is no status packet!
```

**`after 1 tries` — 재시도가 없다.** 시리얼 타임아웃 한 번에 녹화 전체가 죽는다.

재현 조건이 갈렸다.

| `--dataset.streaming_encoding` | 결과 |
|---|---|
| **on** (+`encoder_threads=2`) | **4초 만에 중단** |
| **off** | 3 에피소드 **완주** |

실시간 인코딩 스레드 + 이미지 라이터 스레드 8개(카메라당 4개 기본)가 CPU 를 경합하면
시리얼 읽기가 타임아웃 창을 놓치는 것으로 보인다. **각 조건 n=1 이라 확정은 아니다.**

**대응**
- 실제 수집 시 `streaming_encoding` 사용은 **신중히**. 켤 경우 짧게 시험해 안정성 먼저 확인
- **10 에피소드씩 나눠 녹화할 것.** 50~100 개를 한 번에 돌리다 90번째에서 끊기면 그때까지가 날아간다
- 불안정하면 `--dataset.num_image_writer_threads_per_camera` 를 4 → 2 로 낮춰 볼 것

## 12. RPi 배포 준비 (✅ **`rpi_check.py` 실행 완료** — 잔여는 동결 후 JSON 재배포)

> 2026-06-09 에 진우에게 보낸 요청 문서(`HazardBot_RPi_로봇암_연동요청.md`)의 실행 절차다.

> 🔵 **2026-08-03 정정.** RPi 실물은 진우가 보유 중이고, **ESP32 ↔ RPi 연결·통합도 진우가 직접 진행한다.**
> 따라서 이 절은 **승환이 원격 접속해서 하는 작업이 아니라, 진우에게 넘기는 절차서**다.
> **SSH 접속 정보는 받지 않아도 된다** — 아래 §12-5 참조.
>
> 아래 명령들은 여전히 유효하다. 실행 주체만 바뀐다 —
> `scp` 로 파일을 옮기는 대신 진우가 저장소에서 바로 받아 쓰면 된다.
> 아키텍처 결정(arm_bridge 재사용)은 v5 §2.1 에 반영됐고, 경위는 `archive/로봇암_초기계획_2026-07.md` §8 에 있다.

### 12-1. 목적

팔로워암 6축이 **RPi 에서** 읽기·쓰기 되는지 확인한다. 노트북에서는 이미 검증됐다.

### 12-2. 🔴 진우가 알아둬야 할 3가지

**① ROS2 스택을 끌 필요 없다.**
`arm_bridge` 는 TCP 소켓만 열어둘 뿐 서보 버스를 안 건드린다. 대시보드가 돌아가도 무관하다.
단, **`arm_controller` 는 실행하지 말 것** — `/arm/command` 로 6축 각도가 날아오면 ACT 와 겹친다.

**② LeRobot 은 격리 venv 에 깐다 — ROS2 를 안 건드린다.**

```bash
python3 -m venv ~/lerobot-venv        # ← --system-site-packages 절대 금지
source ~/lerobot-venv/bin/activate
pip install "lerobot[feetech]"
```

- Ubuntu 24.04 는 시스템 파이썬이 `externally-managed` 라 `pip install` 이 **거부된다.** venv 필수
- `--system-site-packages` 를 붙이면 **ROS2 의 opencv/cv_bridge 와 충돌**해 `vision_node` 가 죽을 수 있다
- 용량 2~3GB, RPi 에선 설치에 10~20분

**③ 카메라는 건드리지 않는다.**
`camera_ros`/libcamera 가 CSI 를 점유 중이므로 **`--skip-cameras`** 로 돌린다. 진우 스트리밍은 영향 없다.

### 12-3. 배선

```
[12V 어댑터] ──▶ [서보 버스 어댑터 VIN(나사단자)]
                        ├── USB ──▶ [RPi 5 USB 포트]
                        └── 3핀 ──▶ [팔로워암 서보 체인]
```

⚠️ **서보 12V 를 RPi 에서 뽑지 말 것.** RPi 5 는 5V/5A 이고 서보 6개는 순간 수 A 를 먹는다.
어댑터는 Waveshare Bus Servo Adapter (A), CH343 칩 — RPi 커널에 드라이버 내장이라 `/dev/ttyCH343USB0` 등으로 잡힌다.

### 12-4. 실행

```bash
# 노트북 → RPi 파일 2개 전송
scp tools/rpi_check.py <계정>@<IP>:~/
scp calibration/follower_arm.json <계정>@<IP>:~/.cache/huggingface/lerobot/calibration/robots/so_follower/

# RPi 에서
sudo usermod -aG dialout $USER      # 1회. 실행 후 재접속해야 적용됨
source ~/lerobot-venv/bin/activate
python rpi_check.py --skip-cameras                # 읽기 전용
python rpi_check.py --skip-cameras --move-all     # 6축 소폭 구동
```

## 부록. 왜 `lerobot-calibrate` 를 직접 쓰지 않았는가

`lerobot-calibrate` 는 한 프로세스 안에서 `input()` 프롬프트 2개
(중간 자세 → 전 축 훑기)를 순차로 요구한다. 사람이 터미널 앞에 붙어 있어야 하고,
**중간에 검증할 수 없다.** 실제로 §5-1 의 래핑은 표준 절차를 그대로 따랐다면
"캘리브레이션은 성공했는데 팔이 이상하게 움직인다" 로 나타났을 것이다.

단계를 쪼갠 덕분에 각 단계 결과를 확인하고 문제를 국소화할 수 있었다.
`calibrate_leader.py` 의 내부 호출은 `SOLeader.calibrate()` 와 동일하므로
**결과물의 형식과 의미는 표준 절차와 완전히 같다.**
