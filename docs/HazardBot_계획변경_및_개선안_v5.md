### 손목 캘리브레이션 재측정 완료 (6/12 밤) — 동결 직전 상태

**손목 카메라 장착 → 재측정 → 검증까지 끝났습니다.** 우려했던 가동범위 축소는 없었고
(케이블이 도달 범위를 거의 안 깎음), 오히려 창을 **±157°(총 314°)** 로 넓혔습니다.

- 창 중심 = **기본위치**(정렬 영점 −44°, 카메라 각도에 맞춰 6/12 확정) → 시작 자세에서 양방향 대칭
- `Homing_Offset` 팔로워 −1968 / 리더 1057, 창 260~3836 (양팔 동일)
- 검증: 전 구간 정착 부하 ≤48(한계의 5%) · 창 끝단 추종 오차 ≤8카운트 · 텔레옵 60초 무결

**남은 동결 조건** — 아직 "최종 동결"이라 부르지 않는 이유:

```
섀시 조립 → 팔 장착 (🔴 손목 케이블 라우팅 변경 금지·혼 분해 금지) → 프론트·CSI 장착
→ Max_Torque_Limit·Acceleration 설정(5.7) → 캘리브레이션 동결 선언 → 수집 시작
```

섀시 장착에서 손목 케이블을 다시 만지면 재측정(1~5)이 재발합니다. 라우팅을 건드리지
않으면 지금 좌표계가 그대로 동결본이 됩니다. ACT 는 캘리브레이션된 좌표계를 학습하므로
**동결 후 변경 = 수집 데이터 전량 무효** — 이 원칙은 그대로입니다. 상세 순서는 5.7.

**🔴 함정 — 보유한 12V 5A 어댑터로는 3S 충전이 안 된다**

2. **전류** — 2C 충전은 출력 55W, 효율 85% 감안 시 입력 65W = **12V 에서 5.4A**. 5A 어댑터로는 부족하다.

→ **AC 내장형을 사면 두 문제가 동시에 사라진다.** DC 입력형을 살 경우 15V 이상·6A 이상 어댑터를 별도 확보해야 하므로 부품이 늘고 이득이 없다.

> | 개발·벤치 | 12V 5A 어댑터 (보유) | 5V → RPi USB-C |
> | 시연 | 3S LiPo 9.9~12.6V | 〃 |
>
> 어댑터 부하는 5V·3.5A ≈ 17.5W → 12V 환산 **약 1.5A**. 5A 어댑터에 여유가 크다.
>
> **이득은 비용이 아니라 리스크다.** 두 단계의 전원 경로가 같아지므로
> 벤치에서 통과한 `vcgencmd get_throttled` 결과가 시연에서도 유효하다.
> ① 로 벤치를 검증하면 **시연 전원은 검증되지 않은 채로 남는다.**
>
> 🔴 **XL4015 로 RPi 를 돌리는 안은 채택하지 않는다.** 이유가 셋이다.
> ① 보유 2대가 **이미 배정**돼 있다 — `#A = 7.4V 리더암 전용`(트리머 잠금, **재조정 금지**),
> `#B = 5.0V AMR 전용`. ② 비동기식이라 표기 5A 의 실사용이 **3~4A** 인데 RPi 연속이 3.0~3.5A,
> 피크 4.5A 라 마진이 없다. ③ 과도응답이 느려 ACT 추론의 계단 부하에서 언더볼티지가 난다.
> — §1 ⑥ 이 「XL4015 는 2개로 충족」이라고 못박은 것도 RPi 몫을 ⑦ 에 넘겼기 때문이다.

```
3S LiPo 11.1V ─ XT60 (수동 분리점) ─┬─ STS3215 ×6 ────── 직결 (12V 정격)
                               ├─ TB6612FNG → JGA25-371 ─ 직결
                               ├─ 【DFR0753】 5V → RPi 5 (USB-C 입력)   ← ⑦
                               └─ 【XL4015 #2】 5V → ESP32 ×2 + 센서
```

**RPi 5 실부하 (이 구성 기준)**

| 부하 | 5V 전류 |
|---|---|
| SoC — ACT 추론 4코어 | 2.0~2.4A |
| 액티브 쿨러 | 0.1~0.2A |
| USB 카메라 ×2 | 0.4~0.5A |
| CSI 카메라 (보드 급전) | 0.25A |
| Bus Servo Adapter + microSD | 0.15A |
| **연속** | **약 3.0~3.5A** (피크 4.5A) |

**선정 근거** — 입력 6~14V 가 3S 전 구간(9.9~12.6V)을 덮고, **서보 18A 피크로 배터리가 9.1V까지 처져도** 하한에 여유가 있다. 동기식이라 효율 >96%, 리플 <30mV. 8A 정격의 44% 만 쓰므로 표기가 낙관적이어도 안전하다.

>
> 「SMD 납땜이 부담스러우니 XL4015 처럼 쓰기 편한 것」을 찾아본 결과다.

> - **XL4016 (터미널블록형, ~₩5,000)** — 국내 판매글이 「동기식」으로 표기하나 **오표기다.**
>   외부 쇼트키를 쓰는 **비동기식**이라 XL4015 를 기각한 이유가 그대로 남는다
> - **Pololu D36V50F5** — 보호 회로가 유일한 장점인데 **₩64,000** 이라 기각
> - **UBEC 8A** — 무납땜은 매력적이나 **DFR0753 보다 비싸고**(₩25,000), 출력 정확도·리플이 미공개다.

> UBEC 은 받아서 재봐야 안다.

**🔴 SMD 실장형이다 — 납땜 필요**
터미널블록·핀헤더가 없고 **기판 가장자리 캐슬레이션(반홀) 패드**뿐이다.
패키지에 모듈 1개만 들어 있고 커넥터류는 일절 없다.
DFRobot 공식 설명도 *"can work as an SMD element to be directly soldered onto PCB"* 다.

- 만능기판에 먼저 실장한 뒤 **굵은 선을 기판 쪽에서** 뽑을 것
- 납땜 후 **에폭시/글루건으로 스트레인 릴리프 필수** — 주행 진동으로 접합부가 갈라지면 시연 중 RPi 리부팅
- **예비 1개를 함께 살 것.** SMD 납땜 실패 대비

#### 🔵 납땜 난이도의 실체 — 패드 크기가 아니라 **열용량** 〔2026-08-03 조사〕

**실제 작업은 「전선 4가닥」이다.** `VIN · GND · VOUT · GND` 에 굵은 선을 붙이는 것뿐이고,
부품을 얹는 작업이 아니다. 캐슬레이션(반홀)은 인두로 손납땜이 되는 형태다 — ESP32 모듈이 같은 방식이다.

어려운 이유는 따로 있다. **8A 급 전력 패드는 내부 구리 면적이 넓어 인두 열을 빨아먹는다.**
일반 30W 연필팁으로는 납이 녹지 않고, 계속 지지다가 **기판을 태운다.** 실패는 대부분 여기서 난다.

| 항목 | 요구 |
|---|---|
| 🔴 **인두 출력** | **60W 이상**. 온도조절식이면 350~380℃ |
| 🔴 **팁 형상** | **치즐/베벨(굵은 것)**. 연필팁은 열전달 면적이 부족하다 |
| 플럭스 | 필수 — 열전달이 빨라져 체류 시간이 준다 |
| 장소 | 러닝팩토리(학교 실습장) — **이용 가능 시간이 곧 리드타임**이다 |

**작업 순서**

1. 전선 끝을 **먼저 주석도금(tinning)** — 반홀에 대고 지지는 시간을 줄인다
2. 패드에 **플럭스**를 바른다
3. 인두를 대고 **3~5초 안에** 끝낸다. 안 녹으면 인두가 부족한 것이지, 더 지진다고 되지 않는다
4. 🔴 **폐기판에 반드시 먼저 연습할 것.** ~~예비 1개는 실패 대비지 연습용이 아니다~~
   → **8/3 결정으로 예비가 없어졌다.** 실전이 곧 첫 시도가 되면 안 된다 (§3 2차 주문 블록)
5. **에폭시/글루건 스트레인 릴리프**

> 🔲 **선행 확인: 러닝팩토리 인두기가 60W 이상인가** — **강희 담당, 시점 미정** 〔8/3〕.
> **부품이 먼저 도착할 수 있는데, 확인 전에는 인두를 대지 않는다.** 예비가 없다.
> 30W 급뿐이면 이 부품을 포기하고 **Hobbywing UBEC 8A**(₩25,000, 엑스캅터, 무납땜)로 간다.

> 입력 상한 12.6V 가 3S 만충과 같아 마진이 0 이다. **차선책이지 동급이 아니다.**

## 2. 계획서 v4.4 대비 변경점

### 2.1 로봇암 제어 방식 (가장 큰 변경)

| 항목 | v4.4 계획 | v5 실제 |
|---|---|---|
| 제어 주체 | ESP32 #2 UART2 (GPIO16/17) | **RPi 5 + USB Bus Servo Adapter** |
| 파지 방식 | 프리셋 자세 + Load 임계값 휴리스틱 | **ACT 학습 정책 (모방학습)** |

| 데이터 경로 | RPi → TCP → ESP32 #2 → UART → 서보 | **RPi → USB → 서보** (홉 감소) |

**🔴 반이중 버스 원칙**: STS3215는 1선 반이중입니다. **마스터는 1개만.** USB 어댑터가 마스터인 이상 **ESP32 #2를 서보 3핀 버스에 연결하면 통신이 깨집니다.**

**진우 코드 영향 최소화**: `arm_bridge`(TCP:5001)는 **그대로 재사용**합니다. ESP32 #2가 있던 클라이언트 자리에 RPi 내부 프로세스 `arm_act_node`가 붙습니다. 프로토콜(`<GRIP,CLOSE,80,CS>`), `/arm/servo_feedback`, FSM 모두 유지.

### 2.2 카메라 구성 (1대 → 3대)

| 카메라 | 부착 위치 | 역할 | ACT 입력? |
|---|---|---|---|
| CSI NoIR v2 | 섀시 | 대시보드 + HSV 위험물 감지 | ❌ |
| **SO-ARM 2MP USB** | **팔로워 손목** | 근접 정렬·파지 | ✅ |
| **Innomaker 720P USB** | **섀시** | 접근 궤적·전체 상황 | ✅ |

- **학습 카메라 = 추론 카메라 원칙**: USB 2대는 녹화(노트북) 후 **그대로 RPi로 옮겨** 사용.
- **손목만 팔에, 프론트·CSI는 섀시에.** 프론트를 섀시에 붙여야 팔 베이스 기준 상대 위치가 유지됩니다.

- **udev 규칙으로 카메라 고정 심볼릭 링크**(`/dev/cam_wrist`, `/dev/cam_front`) 필수 — 부팅마다 인덱스가 바뀌면 정책이 오작동합니다.

**3S 유지 근거** (4S 검토 후 기각):
- 배터리 감시 분압 33kΩ/10kΩ은 12.6V→2.93V 설계. **4S 만충 16.8V면 3.9V로 ESP32 ADC 한계(3.3V) 초과** → 회로 재설계 필요

- 마감 6주 전 12V/10A급 벅 신규 도입은 일정 리스크

## 4. ESP32 재분할 — 판단과 권장안

### 판단: **찬성. 단, 분할 기준을 바꿔야 합니다.**

제안하신 "#1 = 주행+라인센서 / #2 = 나머지 센서 전부"는 방향은 맞지만 **VL53L1X를 옮기면 안 됩니다.**

**지금 해야 하는 이유**: 진우 자료 기준 **ESP32 #1/#2 펌웨어는 아직 미작성**입니다. 배선·코드가 없으니 **재분할 비용이 사실상 0**입니다. 펌웨어를 쓰기 시작하면 비싸집니다.

### 권장 분할 — 기준은 "실시간 주행·안전" vs "환경 감지"

**ESP32 #1 = 주행 보드**
| 대상 | 인터페이스 | 이유 |
|---|---|---|
| TB6612FNG (JGA25-371 ×2) | PWM/DIR | 실시간 PID — 적합성 판정 완료(§3.1), **STBY 는 GPIO 로** |
| 5채널 IR 라인센서 (TCRT5000) | **디지털 5핀** (G13·18·19·23·32) | 라인트레이싱 루프. **A0 아날로그가 아니라 채널별 디지털 출력**이었다 (2026-07-21 실물 확인) |
| **VL53L1X ToF** | I2C | **장애물 회피는 로컬 반응 필요** |
| 배터리 전압 감시 | ADC1 (33k/10k, 기존 유지) | 과방전 차단 |

**ESP32 #2 = 안전·환경 보드**
| 대상 | 인터페이스 | 이유 |
|---|---|---|
| MQ-2 / MQ-135 | ADC1 (**5V→3.3V 분압 필수**) | 히터 상시 300mA |
| MLX90614 | I2C (0x5A) | 열원 감지 |
| KY-026 | GPIO (D0) | 화염 감지 |
| WS2812B NeoPixel | RMT (800kHz) | **RPi GPIO로는 타이밍 불가** |
| 능동 부저 | GPIO | 경보 |
| ~~서보 전원 차단 릴레이/MOSFET~~ | ~~GPIO~~ | **철회 (2026-06-12)** — 조달 제외, §5.3 참조 |

### 왜 VL53L1X는 #1에 남기는가
장애물 회피는 **로컬 제어 루프**입니다. #2로 옮기면 경로가
`ESP32#2 → WiFi → RPi → WiFi → ESP32#1`
이 되어 **안전 기능이 무선에 의존**하게 됩니다. 반면 MQ/MLX/KY-026은 100ms 주기 감지 센서라 RPi 경유(~5ms)로 충분합니다 — 계획서도 이미 팔 정지를 RPi 경유로 설계했습니다.

### 재분할의 실질 이득

1. **ADC 노이즈 격리 (가장 큰 이득)** — 모터 PWM과 MQ 아날로그 입력이 **다른 보드·다른 접지**로 분리됩니다. ESP32 ADC는 노이즈에 약해서, 같은 보드에 모터 스위칭이 있으면 가스값이 흔들립니다. 계획서도 "ESP32 ADC 비선형성"을 ⚠중간 리스크로 잡아뒀는데, 이 분리가 근본 대책입니다.
2. **타이밍 격리** — 계획서가 v4.0에서 단일 MCU를 버린 이유가 "Core 1에 센서(100ms)+모터(50ms) 혼합 → 타이밍 간섭"이었습니다. 이제 **모터 PID가 Core 1을 독점**합니다. 라인트레이싱 품질이 올라갑니다.
3. **펌웨어 단순화** — 복잡한 1개 대신 **단순한 2개**. 디버깅이 쉬워집니다.
4. **ADC1 채널 여유** — #1은 2채널(라인+배터리), #2는 2~3채널(MQ×2, KY-026 AO). 양쪽 모두 여유. (WiFi 사용 시 ADC2 사용 불가 제약 충족)

### 통신 구조 변경 (진우 작업, 최소 범위)

| 채널 | 포트 | 클라이언트 | 명령 |
|---|---|---|---|
| `amr_bridge` | 5000 | ESP32 #1 | `<MOVE>` `<STOP>` `<SENS>`(ToF+IR) `<BATT>` |
| `arm_bridge` | 5001 | **`arm_act_node`** (RPi 내부) | `<ARM>` `<GRIP>` `<SFBACK>` |
| **`sensor_bridge`** (신규) | **5002** | ESP32 #2 | `<GAS>` `<TEMP>` `<LED>` `<BUZZ>` |

**하위 영향 없음**: `/amr/gas`, `/amr/temp` 토픽은 그대로 발행되고 발행 주체만 바뀝니다. `hazard_detector`, `mission_orchestrator`, 대시보드는 **수정 불필요**.

## 5. 기존 계획보다 나은 제안

### 5.1 ⭐ 컴플라이언스를 버리지 말고 ACT와 **결합**

계획서 최대 차별화 포인트가 "STS3215 Load 센싱 컴플라이언스 파지"인데, ACT로 갈아타면서 이걸 잃으면 **심사 서사가 약해집니다.** 그런데 버릴 필요가 없습니다.

**ACT는 위치 명령을 냅니다. 힘 제어가 아닙니다.** 그러니:

```
ACT 정책 ──(관절 목표 위치)──▶ [Load 세이프티 클램프] ──▶ 서보
                                       ▲
                              STS3215 Load 실시간 읽기
                              (RPi가 같은 USB 버스로 직접)
```

- 정책이 궤적·파지 시점을 만들고,
- **RPi가 그리퍼 Load를 폴링해 임계값(소프트 40%/하드 80%) 초과 시 즉시 클램프.**
- RPi가 이미 버스 마스터라 **추가 하드웨어 없이 구현 가능**합니다.

**결과**: "학습된 정책 + 실시간 부하 안전장치" — 계획서의 종이컵 시연(★★★)을 그대로 살리면서 ACT를 얹습니다. **둘 중 하나가 아니라 둘 다.**

### 5.2 ⭐ 하이브리드 데모 — 프리셋과 ACT를 **비교 시연** 〔🔴 **2026-08-01 갱신 — 아래 블록 먼저 읽을 것**〕

> ## 🔴 현행 확정값 〔2026-08-01〕
>
> **두 대상 모두 ACT** 입니다. 「빨강=프리셋 / 노랑=ACT」는 **더 이상 임무 구성이 아닙니다.**
>
> | | 폐기된 배치 | **현행** |
> |---|---|---|
> | 빨간 블록 | 프리셋 | **ACT** (전용 정책) |
> | 노란 종이컵 | ACT | **ACT** (전용 정책) |
> | 정책 수 | 1개 | **2개 — 통합하지 않는다** (§6) |
> | 수집·학습 | 1벌 | **2벌**, 15.6h × 2 ≈ **31h** 순차 |
> | 프리셋의 자리 | 임무 안 | **임무에서 빠지고**, 심층 구간의 **분할화면 비교**로만 등장 |
>
> **이건 방향 전환이 아니라 아래 §「2단계 폴백 + 상방」에 이미 적혀 있던 상방을 실행한 것입니다** —
> *"컵 성공률 양호 → 블록 ACT 추가(상방, 선택)"*. 폴백 구조도 그대로 살아 있습니다:
> **8/15 Go/No-Go 를 대상별로 판단**해, 한쪽만 부진하면 **그 대상만** 프리셋으로 내립니다.
>
> **아래 본문은 판단 근거의 기록으로 남깁니다.** 여전히 유효한 것과 아닌 것:
>
> - ✅ **색 → 취급 등급 → 파지력 상한** 축은 그대로 유효합니다 (Load 클램프)
> - 🔴 **형상 → 제어 방식(프리셋/ACT)** 축은 **소멸**했습니다. 둘 다 ACT 이므로 형상이 방식을 가르지 않습니다.
>   형상은 이제 **어느 정책을 로드할지**만 가르고, 그 선택조차 형상이 아니라
>   **정지점 순번**으로 합니다 (`firmware/구역_마커_설계.md` §6)
> - 🔴 **"데이터 수집량 절반 / 학습 난이도 하락"** 이득은 소멸했습니다.
>   다만 난이도는 **통합 정책이 아니라 정책 2개**를 택해 되돌렸습니다 —
>   각 정책이 자기 대상 하나만 보므로 색으로 분기할 일이 없습니다.
>   **비용은 난이도가 아니라 시간으로 나옵니다.** 그래서 **수집 순서는 황색 먼저**입니다
> - ✅ **비교 시연이라는 서사**는 살아 있습니다. 위치만 임무 구간 → 심층 구간으로 옮겼습니다
>
> 관련: `demo_video_scenario.md` §5.2 · §7 / `로봇암_카메라_구성정리.md` §7.3 / 아래 §6

ACT는 고위험입니다(데이터 50~100+ 에피소드, 학습 수렴, sim2real). 마감 5.7주에 전부를 걸면 안 됩니다.

**데모의 두 물체를 나눠 씁니다.**

| 물체 | 방식 | 근거 |
|---|---|---|
| 빨간 정형 블록 | **프리셋 + 포즈테이블** (v4 방식) | `minAreaRect`로 각도가 **결정론적**으로 나옴. 강체·형상 고정 → ACT를 써도 나아질 여지가 없음 |
| 노란 종이컵 (비정형) | **ACT 학습 정책** | "몇 mm 닫을지"가 자세마다 달라 **규칙화가 실패하는 지점**. 학습이 실제로 이기는 유일한 곳 |

**타협이 아니라 물체 성질에 맞춘 배치입니다.** 이게 "왜 두 방식을 섞었나"에 대한 답입니다.

**이득 4가지**:
1. **데이터 수집량 절반** — 태스크 1개만 학습하면 됨
2. **학습 난이도 자체가 하락** — ACT가 컵만 보므로 **색으로 물체를 구분할 필요가 없어짐** (카메라 문서 §7.3). 1과 곱해져 체감 차이가 큼
3. **데모 리스크 분산** — ACT가 실패해도 미션은 완주
4. **심사 서사 강화** — "프리셋 vs 학습 정책" **비교 시연**은 단독 시연보다 설득력이 높습니다. 영상 제출이므로 **split-screen 동시 비교**까지 가능(§9.1)

#### ⭐ 확정 근거 — 폴백을 남기면 ACT 단독의 이득이 소멸합니다

ACT 단독(블록도 ACT)을 검토했으나, 최대 이득이 **"캘리브레이션·IK를 안 만들어도 됨"**이었습니다. 그런데 IK 폴백을 유지하기로 결정한 이상:

```
폴백 유지 → 프리셋 경로를 어차피 만든다
          → 프리셋이 있는데 블록을 ACT로 잡을 이유가 없음
            (데이터 2배 + 성공률은 오히려 낮을 수 있음)
          → 하이브리드가 자연스러운 귀결
```

ACT 단독이 의미를 가지려면 폴백을 버려야 하는데, D-95에서 감당하기 어렵습니다. **확정합니다.**

#### ⭐ 색과 형상의 역할 분리 — 설계 근거 완결

5.9에서 노랑을 "취급주의 등급"으로 재정의했지만, **규격이 정당화하는 건 "부드럽게 잡아라"이지 "학습으로 잡아라"가 아닙니다.** 프리셋+Load 클램프로도 소프트 그립은 됩니다. 따라서 *"왜 노란 물체만 학습으로 잡나?"*의 진짜 답은 색이 아니라 **형상**입니다.

**두 축을 명시적으로 분리합니다:**

```
색   →  취급 등급  →  파지력 상한 (안전 규격, Load 클램프 임계)   ← 5.1 / 5.9
형상 →  기하 특성  →  제어 방식 (프리셋 / ACT)                  ← 5.8
```

| 물체 | 색 → 등급 | 형상 → 방식 |
|---|---|---|
| 빨간 블록 | 신속격리 → 파지력 상한 높음 | 정형 → **프리셋** |
| 노란 컵 | 취급주의 → **soft 40% 클램프** | 비정형 → **ACT** |

- 5.8의 형상 특징이 **장식이 아니라 모드 선택의 실제 근거**가 됩니다.
- 심사 방어 완결: *"색은 안전 등급을, 형상은 제어 방식을 결정합니다."*
- **"빨간 종이컵이 오면?"** → 색이 파지력을, 형상이 방식을 정하므로 **각 축이 독립적으로 결정**됩니다.
- 구현은 기존 요소의 조합이라 **추가 비용 0** (5.8 형상 판정 + 5.1 Load 클램프를 서로 다른 축에 연결).

#### 확정해도 문은 닫히지 않습니다 — 2단계 폴백 + 상방

```
확정: 빨강 = 프리셋 / 노랑 = ACT
   ├─ W3 컵 성공률 양호 → W4에 블록 ACT 추가 (상방, 선택)   ← ✅ 8/1 이 갈래로 진입
   └─ W3 컵 성공률 부진 → 컵도 프리셋 + Load 클램프로 후퇴 (2차 폴백, v4 원방식)
```

> 🔵 **상방 갈래를 이미 탔습니다.** 현재 위치는 「블록 ACT 추가」 이후이고,
> 폴백은 **대상별로** 남아 있습니다 — 8/15 Go/No-Go 에서 부진한 대상만 프리셋으로 내립니다.

블록 ACT 추가는 **파이프라인 재사용**이라 추가 비용이 수집뿐입니다. 지금 확정해도 상방은 열려 있습니다.

### 5.3 ⭐ ESP32 #2 = 환경·경보 보드 (하드웨어 차단 계층 **철회**)

계획서/LeRobot 문서는 ESP32 #2를 "폴트 시 서보 토크 OFF" 워치독으로 뒀는데, **이제 ESP32 #2는 서보 버스에 접근할 수 없어 토크 OFF를 못 합니다.**

당초 v5 는 이를 **릴레이/MOSFET 로 서보 전원을 물리 차단**하는 방식으로 대체할 것을 제안했으나,
**2026-06-12 결정으로 릴레이·킬스위치·인라인 퓨즈를 모두 조달 대상에서 제외**했습니다.

**대신 「서보 자체 보호」로 간다 — 이것이 릴레이보다 낫다**

릴레이는 **사후 대응**(위험해지면 전원을 끊음)이고, 서보 레지스터 제한은 **사전 봉쇄**(애초에 위험한 동작을 못 냄)다.
그리고 이 제한들은 **각 서보의 자체 MCU 가 강제**하므로 RPi·버스·WiFi 어느 것이 죽어도 살아 있다 — 릴레이가 커버하려던 시나리오를 전부 덮으면서, **18A 경로에 새 고장점을 만들지 않는다.**

| 보호 | 레지스터 | 막는 것 | 상태 |
|---|---|---|---|
| 가동 범위 | `Min/Max_Position_Limit` (EPROM) | 팔이 갈 수 있는 **공간** | ✅ **적용됨** (§5-8, 손목 기본위치 중심 ±157°) |
| **최대 토크** | `Max_Torque_Limit` / `Torque_Limit` | 팔이 낼 수 있는 **힘** | 🔴 **미적용 — 수집 전 설정 필수** |
| **가감속** | `Acceleration`, `Goal_Velocity` | 팔이 낼 수 있는 **속도** | 🔴 **미적용 — 수집 전 설정 필수** |

> 🔴 **"ACT 가 미쳐서 팔이 어디로든 날아간다"는 시나리오는 이미 봉쇄돼 있다.**
> §5-7 의 손목 129° 폭주가 커진 이유는 **그때 손목 창이 0~4095(한 바퀴)라 실질적 한계가 없었기** 때문이다.
> 지금은 6축 전부 `Min/Max_Position_Limit` 이 서보 EPROM 에 걸려 있어, 정책이 어떤 값을 뱉어도 서보가 자기 한계에서 자른다.

**최대 토크가 핵심이다.** 종이컵을 집어 들 만큼만 허용하면, 그 팔은 손가락을 다치게 할 수도 소품을 부술 수도 없다.
**가감속 제한도 반드시 같이** 건다 — 느린 팔이라야 사람이 XT60 을 뽑을 시간이 생긴다. 순간적으로 튀는 팔은 수동 계층이 무의미하다.

**설정값은 측정해서 정한다** (손목 범위를 `--profile` 로 잡았던 것과 같은 방식):

```
1. 종이컵 파지·들기를 텔레옵으로 수행하며 Present_Load 기록 (0~1000 스케일)
2. 실측 최대 부하의 약 1.5배를 Max_Torque_Limit 으로 설정
3. 그 값으로 파지가 여전히 되는지 재확인
4. Acceleration 은 텔레옵 실사용 값에 맞춰 상한 고정
```

⚠ 레지스터 정확한 명칭은 설치된 LeRobot 의 feetech control table 에서 확인할 것.

**최종 안전 구성**

| 계층 | 주체 | 동작 | 한계 |
|---|---|---|---|
| **0차** | **서보 자체** | **범위·토크·가감속 제한 (EPROM/RAM)** | 동작을 막지 못함, 힘·범위만 제한 |
| 1차 | RPi | 소프트웨어 토크 OFF (버스 마스터) | RPi·버스·WiFi 가 살아 있어야 동작 |
| 2차 | 사람 | XT60 커넥터 직접 분리 | 사람이 그 자리에 있어야 함 |

**운용 규칙** (수동 계층이 실제로 작동하기 위한 전제)

- 배터리 XT60 을 **팔 작업반경 밖, 손이 바로 닿는 위치**에 배치 (W2 섀시 조립 시 확정)
- 소품 재배치·로봇 이동·촬영 테이크 사이에는 **반드시 배터리 분리**
- 매 촬영 전 **배선 피복 손상·압착 육안 점검**, 12~14AWG 로 여유 있게 배선 (퓨즈가 없으므로)

> **이 판단이 성립하는 조건**: 라이브 시연이 없어 **항상 사람이 옆에 있고**, 리치 20cm·페이로드 300g 의 소형 팔이며,
> 런타임이 23분이다. 무인 상시가동 설비였다면 릴레이가 정답이다.

⚠ **제출물 표현 주의.** PPT·보고서·산출물 #8(Fault Isolation 매트릭스)에서 **"3계층"이라고 쓰면 사실과 다릅니다.**
"소프트웨어 차단 + 수동 분리의 2계층" 으로 기술하고, MCU 분리에 의한 **Fault Isolation(장애 전파 차단)** 쪽을
어필 포인트로 삼는 편이 정확합니다 — 그건 릴레이 없이도 성립합니다.

### 5.3.1 🔴 모터 정지 권한 — **DRIVE 단독** 〔확정 2026-08-03〕

오래 열려 있던 「v9 안전 상태기계의 정지 권한」 항목의 결론이다.

#### 결론

> **모터를 멈추는 것은 DRIVE 뿐이다. ENV 도 RPi 도 「요청」만 한다.**

근거가 셋인데, **셋 다 이 프로젝트가 이미 내린 판단의 재적용**이다.

| # | 근거 |
|---|---|
| 1 | **물리적으로 DRIVE 만 가능하다.** TB6612 의 `STBY(G4)` 와 PWM·방향 6핀이 전부 DRIVE 에 있다. 다른 보드에 「권한」을 줘도 결국 DRIVE 에게 부탁해야 하므로 **권한 분산은 이름뿐**이다 |
| 2 | **전례 ①** — §5.3 에서 ESP32 #2 를 서보 워치독으로 쓰려다 **「서보 버스에 접근할 수 없다」**는 이유로 철회했다. 모터도 같은 구조다 |
| 3 | **전례 ②** — §4 에서 ToF 를 ENV 로 옮기지 않은 이유가 **「안전 기능이 무선에 의존하게 된다」**였다. 정지 권한을 무선 건너편에 두면 그 판단을 스스로 뒤집는 셈이다 |

#### 하드웨어가 이미 페일세이프다

만능기판 설계에 **`STBY` 10kΩ 풀다운**이 들어가 있다 (`만능기판_이전_가이드.md` §배선표).
TB6612 의 STBY 는 내부 풀다운이 없어 플로팅이면 불확정인데, 이 저항 때문에

> **ESP32 가 죽거나 리셋되면 G4 가 하이임피던스 → 풀다운이 STBY 를 LOW 로 → 모터 정지.**

즉 **DRIVE 자신의 고장은 부품 하나로 이미 커버돼 있다.** 이건 우연이 아니라 설계된 것이고,
「정지를 DRIVE 에 두는」 결정을 뒷받침한다.

#### 정지 요청은 4계층으로 받는다

| 계층 | 주체 | 조건 | 경로 | 시간 상수 |
|---|---|---|---|---|
| 0 | **하드웨어** | ESP32 사망·리셋 | STBY 10k 풀다운 | 즉시 |
| 1 | **DRIVE 로컬** | ToF 장애물, 라인 이탈, 배터리 저전압, (스톨 — 예약) | 자체 배선 | ms |
| 2 | **RPi** | 미션 정지, E-Stop, **ENV 폴트 중계**, 비전 교차검증 불일치 | WiFi TCP (`amr_bridge`) | 100ms~ |
| 3 | **사람** | XT60 수동 분리 | 물리 | — |

#### 🔴 계층 2 는 「명령」이 아니라 「생존 신호」로 구현한다

**`STOP` 을 보내서 세우는 방식으로 만들면 안 된다.** 그 명령이 유실되거나 보낸 쪽이 죽으면 정지가 안 된다.

> **RPi 가 주기적으로 하트비트를 보내고, DRIVE 는 그것이 끊기면 선다.**

이러면 **RPi 사망 · WiFi 두절 · ENV 사망**(→ RPi 가 하트비트를 끊음)이
**전부 하나의 메커니즘으로** 정지된다. v9 의 `RPI_TIMEOUT` 이 이미 이 구조이므로 **계승하면 된다.**

#### ENV 는 정지 권한을 갖지 않는다

- ENV 는 **판정을 하지 않기로 이미 확정**됐다 — 원시값·이동평균만 보내고 구역별 임계 분기는 RPi 가 한다
- **판정하지 않는 보드가 정지 권한을 가질 수는 없다.** 두 결정이 일관된다
- 가스·화염은 100ms 급 감지라 RPi 경유로 충분하다. §4 가 MQ·KY-026 을 ENV 에 둔 근거와 같다

#### 🔲 함께 정할 것 — `RPI_TIMEOUT` 3초는 길다

v9 의 3초는 **정지 상태 기준으로 잡힌 값**으로 보인다. 주행 중 3초면 통로 폭 1200mm·코너 R500 인 세트에서 상당 거리를 간다.

다만 **경로가 WiFi 라 짧게 잡으면 오작동(nuisance trip)이 난다.** 이 긴장이 실제 설계 문제다.

| 안 | 내용 | 평가 |
|---|---|---|
| **A (채택)** | 타임아웃을 **1초 전후**로 낮추고, 물리 안전은 **ToF 로컬**에 맡긴다 | 배선 변경 없음. WiFi 두절은 「충돌」이 아니라 「미션이 눈감고 진행됨」이라 1초면 충분 |
| B | DRIVE↔RPi 를 **USB 시리얼 직결**로 바꾸고 300ms | 더 견고하나 배선·전원 검증이 추가된다. RPi USB 는 카메라2+서보어댑터=3 이라 1포트 남고, SS34 덕에 USB+VIN 동시 급전도 안전하다 |

**A 로 가고 B 는 열어둔다.** 실제 충돌 안전은 이미 계층 1(ToF)이 로컬로 잡고 있고,
녹화 영상이라 재촬영이 가능하다. B 는 A 에서 오작동이 실측될 때 꺼낸다.

### 5.4 ⚠ NoIR 카메라의 색상 문제 — **조기 검증 필요**

계획서 비전 차별화는 **HSV 빨강/노랑 분류**인데, 보유 카메라는 **NoIR(적외선 필터 없음)**입니다. NoIR는 화면이 전반적으로 **붉게** 뜹니다 — 하필 **빨강 vs 노랑 구분**에 가장 나쁜 왜곡입니다.

**지금 해야 할 일**: 시연 조명 아래에서 **빨강/노랑 물체를 NoIR로 찍어 HSV 분리가 되는지 이번 주에 테스트.**

| 결과 | 대응 |
|---|---|
| 분리 잘 됨 | 계획서 그대로 (추가 비용 0) |
| **색 분리는 애매하나 형상 특징으로 보완 가능** | **5.8의 색+형상 AND 조건으로 커버 → 추가 구매 불필요** |
| 색·형상 모두 불충분 | 정색 USB 웹캠 1대 추가 구매 (~₩20,000) → vision_node 전용 |

> 5.8이 신설되면서 중간 분기가 생겼습니다. **색 분리만 보고 웹캠을 사기 전에 형상 특징을 먼저 확인하세요.**

> ACT용 USB 2대는 이미 용도가 확정돼 있어 전용할 수 없습니다(V4L2는 한 프로세스만 open 가능). 프레임 브로커를 만들면 ROS2/venv 격리가 깨지므로 **카메라를 하나 더 사는 게 싸고 안전**합니다.

### 5.5 IK(`arm_controller`) 우선순위 하향 → 진우 시간 확보

진우 자료의 "링크 길이 L2/L3/L4 실측 필요"는 **ACT 경로에서는 불필요**합니다. 다만 5.2가 **확정**되어 **정형 블록용 프리셋 경로로 계속 쓰이므로 삭제하지 않습니다.**

- **우선순위**: 정밀 IK 구현 → **포즈 테이블(고정 자세 몇 개) 수준으로 축소**
- 블록이 **ZONE2의 정해진 구역**에 놓이므로 위치 변동이 작습니다. **포즈 테이블 몇 개 + HSV 중심 보정**으로 충분합니다.
- 확보된 시간은 `sensor_bridge` 신설 + 대시보드 + 통합 테스트로

> 🔴 **이 경로는 8/15 No-Go 시 유일한 폴백입니다.** 삭제하면 그 시점부터 캘리브레이션을 처음 만들어야 하고, 시스템 완성 데드라인(8/23)까지 8일뿐입니다.

### 5.6 RPi 5 ACT 추론 — Action Chunking이 실현 가능성의 핵심

ACT(~52M)를 RPi 5 CPU에서 30Hz로 돌리는 건 어렵습니다. **하지만 ACT는 원래 그렇게 안 돌립니다.**

- ACT는 **chunk_size=100** — 추론 1회가 **미래 100스텝의 동작**을 한꺼번에 냅니다.
- 30Hz 제어 기준 **1회 추론 = 3.3초 분량**. 즉 **추론이 1Hz여도 30Hz 제어가 가능**합니다.
- 이게 RPi 배포를 성립시키는 핵심입니다.

**검증 항목** (배포 전 필수):
- [ ] RPi 5에서 ACT 1회 추론 지연 실측 (목표 < 1초)
- [ ] 이미지 해상도 하향(224 이하) 시 지연·성공률 트레이드오프
- [ ] USB 카메라 2대 동시 캡처 대역폭 (640×480/30fps 권장)
- [ ] 필요 시 ONNX 변환 / 양자화

#### 🔵 정책 2개는 **동시 상주**시킨다 〔확정 2026-08-03〕

대상이 2개가 되면서 정책도 2개가 됐다 (§5.2). 둘을 어떻게 다룰지 두 안이 있었다.

| | 순번 받고 로드 | **동시 상주 (채택)** |
|---|---|---|
| 메모리 | 약 207MB | **약 414MB** |
| 정지 후 첫 추론 | microSD 에서 207MB 로드 — **수 초** | 로딩 없음 |
| 위험 | 정지점마다 로딩 지연이 붙는다 | 없음 |

**메모리가 문제가 되지 않는다.** ACT 51,597,190 파라미터 × 4바이트(fp32) ≈ **207MB**,
2개면 **약 414MB**. RPi 5 는 **8GB** 라 ROS2 스택과 카메라 버퍼를 얹어도 여유가 크다.

> **동시에 「추론」하지는 않는다.** 상주만 시키고 실행은 정지점 순번에 따라 하나씩이다.
> 따라서 **CPU·발열 예산은 정책이 1개일 때와 같다.** 늘어나는 것은 메모리뿐이고, 그게 남는다.

🔴 **워밍업 추론을 정책마다 1회씩 미리 돌려둘 것.** PyTorch 는 첫 추론에서 지연 초기화와
캐시 미스가 겹쳐 유독 느리다. 미션 시작 전에 더미 입력으로 한 번씩 돌려놓지 않으면,
**첫 파지에서만 지연이 튀어** 「목표 <1초」를 그 순간에 놓친다.

### 5.7 ⭐ 데이터 수집 순서 — **섀시가 크리티컬 패스**

가장 흔한 실수: **섀시가 완성되기 전에 데이터를 모으고, 나중에 다시 모으는 것.**

ACT는 학습 때와 추론 때의 **카메라-팔 상대 위치가 같아야** 합니다. 그런데 최종 형태는 팔과 프론트 카메라가 **모두 섀시 위**입니다. 따라서:

### 5.8 ⭐ 위험물 분류 견고화 — 색 단독 → **색 + 형상 다중 특징**

**v4 설계는 HSV 색상만으로 분류했습니다.** 빨강 = 화재위험물, 노랑 = 일반폐기물(→ 5.9에서 **취급주의 등급**으로 재정의 확정). 그게 전부입니다.

**문제**: 색은 형상의 **대리 지표**일 뿐입니다.

```
색      →  물체      →  형상        →  파지 전략
빨강    →  블록      →  정형 강체   →  프리셋
노랑    →  종이컵    →  비정형      →  ACT
```

이 연결은 **데모 소품을 그렇게 골랐기 때문에** 성립합니다. 색이 형상 정보를 담고 있어서가 아닙니다. 빨간 종이컵을 놓으면 즉시 깨집니다.

**실제 위험 — 5.4가 여기로 전파됩니다**:

```
NoIR 붉은 편향 → 노란 컵을 빨강으로 오인 → 프리셋 강파지 → 컵 찌그러짐
                                              ↑ 계획서 ★★★ 차별화 파괴
```

**색 판정 실패 = 파지 전략 오선택**입니다. 그리고 이 문제는 **ACT 단독으로 가도 사라지지 않습니다** — 정책 2개를 스위칭하는 구조라면 어느 모델을 쓸지 고르는 데 여전히 분류가 필요합니다. **분류 견고성은 하이브리드/ACT 단독 두 설계 모두의 전제입니다.**

**해결 — `minAreaRect`를 이미 계산 중이므로 형상 특징은 거의 공짜입니다.**

| 특징 | 계산 | 정형 블록 | 종이컵 |
|---|---|---|---|
| 면적 | `contourArea` | 크기 차이가 나면 가장 강한 단일 지표 | |
| **채움률(extent)** | `area / (w×h)` | 사각형 ≈ **0.95+** | 원형 ≈ **0.78** |
| **원형도** | `4πA / P²` | 정사각 ≈ 0.785, 길쭉하면 더 낮음 | 원 ≈ **1.0** |
| 종횡비 | `w / h` (minAreaRect) | 블록 비율 고정 | ≈ 1 |

> 🔴 **위 수치는 "위에서 내려다본(top-down)" 기준의 참조값입니다. 그대로 임계값으로 쓰면 안 됩니다.**
>
> 프론트 카메라는 카메라 문서 §9 기준 **아래로 15~30°** — 거의 측면에 가까운 시점입니다. **이 각도에서 종이컵은 원이 아니라 사다리꼴로 보입니다.** 채움률이 0.85~0.9까지 올라가 블록(0.95+)과의 격차가 위 표보다 훨씬 좁아집니다.
>
> → **실제 임계값은 5.4 테스트에서 프론트 카메라 실제 각도로 측정해 뽑으세요.**

- 구분 대상이 **2개뿐**이므로 임계값 몇 개로 충분. 추가 연산·추가 센서 **없음**.
- 색과 **AND 조건**으로 묶어 색 단독보다 견고하게.
- ⚠ **채움률과 원형도는 강하게 상관된 지표입니다**(정사각형에서 둘 다 0.785 대비). 4개처럼 보이지만 실질 정보량은 **면적 + 형상 1종** 수준으로 보는 게 안전합니다.
- 보조 지표: **손목 카메라 근접 뷰** — 그리퍼 파지 지점을 내려다보는 각도라 **위 top-down 수치가 실제로 성립하는 유일한 시점**입니다. 프론트 판정이 애매하면 접근 후 손목 뷰로 재확인하는 2단 판정이 유효합니다. VL53L1X ToF 높이는 위치 의존적이라 보조.

**불일치 시 폴백 — 보수적으로**:

```
색 판정 ─┐
         ├→ 일치   → 해당 모드 진입
형상 판정 ┘
         └→ 불일치 → 소프트 모드(ACT/저파지력) 또는 FSM SKIP
```

> **손실이 비대칭이기 때문입니다.** 최악은 컵을 블록으로 오인해 강파지하는 것이고, 반대 방향(블록을 조심스럽게 잡기)은 느릴 뿐 실패가 아닙니다. 판단을 한쪽으로 기울이는 게 맞습니다. FSM의 `RETRY(3회) → SKIP`을 그대로 재사용합니다.

**5.4 테스트와 함께 진행**: NoIR 색상 테스트를 할 때 **형상 특징값도 같이 찍으세요.** 같은 촬영이고 임계값을 그 자리에서 뽑을 수 있습니다. 형상 특징이 받쳐주면 **정색 웹캠 추가 구매를 피할 수도 있습니다.**

**심사 효과**: "HSV 색상 분류" → **"색상 + 형상 특징 다중 분류, 불일치 시 안전 측 폴백"**. 구현 비용 0인데 설계 근거가 생깁니다. 규격 근거는 5.9 참조.

### 5.9 ⭐ 산업현장 환경 구성 — 안전표지 규격 기반

목표: 데모 환경을 **실제 산업현장과 유사하게**. 영상 인상을 크게 좌우하는데 비용은 낮습니다.

#### 실제 표준 (산업안전보건법 안전보건표지)

| 구분 | 색 | **형상** | 용도 |
|---|---|---|---|
| 금지 | 빨강 (7.5R 4/14) | **원 + 사선** | 화기엄금, 출입금지 |
| 경고 | 노랑 (5Y 8.5/12) | **삼각형** | 인화성물질, 위험 |
| 지시 | 파랑 | 원 | 보호구 착용 |
| 안내 | 초록 | 사각형 | 비상구, 대피소 |

**⭐ 규격 자체가 색과 형상을 이중으로 씁니다.** 색각이상자와 조명 열화 상황에서도 판별되게 하기 위해서입니다.

> **5.8의 "색 + 형상 다중 분류"는 임시방편이 아니라, 국제 안전표지 규격이 채택한 것과 같은 원리입니다.**
> 심사 답변: *"안전표지 규격이 색과 형상을 이중 부호화하는 것과 같은 이유로, 인식도 색과 형상을 함께 봅니다."*

또한 KOSHA 색채는 **고채도·고명도 대비로 설계**된 색입니다(멀리서 빨리 보이라고). **현실성과 검출성이 충돌하지 않습니다.**

#### ⭐ 색의 의미 재정의 〔**확정**〕 — 서사만 바뀌는데 설계 완성도가 오릅니다

| | v4 정의 | 판정 |
|---|---|---|
| 빨강 | 화재위험물 | 규격 부합 ✅ |
| 노랑 | **일반폐기물** | 규격에 근거 없음. 노랑은 "경고/주의" ❌ |

**확정 정의**:
```
빨강 = 인화성 물질 (화기엄금)   → 신속 격리 등급
노랑 = 취급주의 물질            → 파손 위험 용기, 저파지력 필수
```

이 재정의의 진짜 이득:

```
[기존] 노랑 → 종이컵 → 비정형 → 소프트 그립   (우연한 연결)
[확정] 노랑 = 취급주의 등급 → 소프트 그립      (규격이 요구하는 것)
```

색이 **물체 종류**가 아니라 **취급 등급**을 나타내면, 색으로 파지 전략을 정하는 게 **논리적으로 정당**해집니다. 5.8이 지적한 "우연한 1:1" 약점이 해소됩니다. *"빨간 종이컵이 오면요?"* → *"빨강은 신속 격리 등급이므로 규격상 강파지가 맞습니다."*

**같은 하드웨어, 같은 코드. 정의만 바뀝니다.**

> ⚠ 단, 5.2의 축 분리와 함께 읽어야 합니다. **색은 파지력 등급까지만 정하고, 제어 방식(프리셋/ACT)은 형상이 정합니다.**

「센서 퓨전 — MQ 비율 + **구역 컨텍스트**」와 §9.1 큐시트의 「ZONE3 같은 값 다른 판정」이
근거 없이 떠 있었습니다. 아래로 확정합니다.

| 구역 | 성격 | 로봇의 임무 | 표시 이름 |
|---|---|---|---|
| **ZONE 1** | **비위험 구역** — 가스가 있어서는 안 되는 곳 | 순회 점검 + **이상 시 원인 회수 (파지)** | 일반구역 |
| **ZONE 2** | **취급·보관 구역** — 위험물을 다루는 곳 | 위험물 회수 (파지) | 취급구역 |
| **ZONE 3** | **위험 구역** — 가스 존재를 전제로 설계된 곳 | 점화원 감시 | 위험구역 |

근거는 가스 위험 장소의 국제 구분 체계입니다 (**KS C IEC 60079-10-1**, 아래 인용 원칙 참조).

#### 구역별 판정 매트릭스 — 같은 값, 다른 판정

**핵심은 방향이 직관과 반대라는 점입니다.** 위험 구역에서 가스는 정상이고, 비위험 구역에서 가스는 비상입니다.
위험 구역의 안전 개념 전체가 *"가스는 있다고 가정하고 점화원을 제거한다"* 이기 때문입니다.

| | 가스 검출 (MQ) | 화염 검출 (KY-026) |
|---|---|---|
| **ZONE 1** 비위험 | 🔴 **경보 — 격리 실패** | 🟠 화재 경보 |
| **ZONE 2** 취급 | 🟡 주의 | 🟠 화재 경보 |
| **ZONE 3** 위험 | 🟢 정상 범위 | 🔴🔴 **EMERGENCY — 폭발 위험, 즉시 후퇴** |

이 정의로 §9.1 큐시트의 ZONE3 두 장면(컨텍스트 판정 10s → 화염 EMERGENCY 15s)이
**하나의 논리로 연결됩니다.** *"가스는 봐줬는데 불꽃은 못 봐준다 — 여기가 위험 구역이라서."*
ZONE1 의 「센서 퓨전 L0→L2」도 *"가스가 있으면 안 되는 곳에서 검출됐다"* 로 상승 근거가 생깁니다.

> **🔵 ZONE1 에 파지가 추가되었습니다 〔2026-08-01〕**
>
> 위 표의 ZONE1 임무가 「순회 점검·기준값 확인」에서 **「순회 점검 + 이상 시 원인 회수」** 로 넓어졌습니다.
> 시연에서 **빨간 정형 블록을 ZONE1 에 배치**하기 때문입니다.
>
> 근거는 서사가 아니라 논리입니다 — 지금까지 ZONE1 비트는 **경보에서 끝나고 아무 조치가 없었습니다.**
> 가스가 있어서는 안 되는 곳에서 검출됐다면 **원인을 제거하는 것이 다음 행동**입니다.
> 회수를 붙여야 *"검출 → 조치"* 로 장면이 닫힙니다.
>
> 구역 성격의 재정의가 아닙니다. ZONE1 은 여전히 비위험 구역이고, 파지는 **정상 업무가 아니라
> 이상 대응**입니다. ZONE2 의 파지(정상 회수 업무)와 성격이 다릅니다.
> 상세 배치는 `demo_video_scenario.md` §5.2.

> **🔵 코드 식별자는 `ZONE1/2/3` 을 그대로 둡니다.** 바뀌는 것은 **표시 이름뿐**입니다.
> - 임무가 선형(1→2→3)이라 숫자가 순서 정보를 담고 있고, 정지점 마커도 순번 기반입니다
> - enum·대시보드 라벨·`mission_orchestrator` 상태명을 건드리지 않아 **진우 작업량이 0** 입니다
> - 명판·자막·나레이션·PPT 에만 서술 이름(일반/취급/위험구역)을 씁니다

#### 4계층 구현

**계층 1 — 파지 대상 물체**
- 표준 색채(빨강/노랑) **고채도 유지** (도색 또는 컬러 테이프)
- 형상은 현재대로 (블록 = 각진 것, 컵 = 원통)

**계층 2 — 라벨 (현장감의 대부분이 여기서 나옴)**
- **GHS 픽토그램 스티커**: 흰 바탕 + 빨간 마름모 테두리 + 검은 그림 (인화성=불꽃, 급성독성=해골)
- 또는 **NFPA 704 다이아몬드** (파랑/빨강/노랑/흰색 4분할 + 0~4)
- UN 번호 라벨

> ⚠ **픽토그램을 인식 대상으로 삼지 마세요.** OCR·패턴인식은 D-95 범위 밖입니다. 라벨은 **시각적 현장감 전용**, 인식은 5.8의 색+형상으로 갑니다. 심사 질문 시 "확장 항목"으로 답합니다.

**계층 3 — 바닥·구역**

| 실제 현장 | HazardBot 적용 | 색 |
|---|---|---|
| 통로 구분선 | **AMR 주행 라인** | **검정** (확정) |
| 위험구역 경계 | ZONE 3 (화염 구역) | **검정/흰색 사선** — 단 **바닥이 아니라 우드락 기둥 표면**에 (2026-08-17 변경, 아래 참조) |
| 주의 구역 | 작업 구역 표시 | **검정/흰색** |
| 정지점 마커 | AMR 정지 지점 | **검정** — 주행 라인과 같은 테이프 (`firmware/구역_마커_설계.md`) |

- **AMR 주행 라인 = 검정 테이프 (확정).** 5ch IR 센서는 색이 아니라 **반사율**을 보므로 흰 바닥 + 검은 라인이 표준입니다.

**🔴 바닥에는 빨강·노랑 테이프를 쓰지 마세요.**

프론트 카메라 화각에 바닥이 들어오면 **HSV 마스크가 바닥 테이프를 물체로 오검출합니다.**

| 바닥 색 | 결과 |
|---|---|
| 노랑 | 노랑 마스크에 통로선이 통째로 잡힘 → 종이컵 오검출 |
| **빨강** | **빨강 마스크에 ZONE3 경계선이 잡힘 → 빨간 블록 오검출** |

현장의 위험 구역 줄무늬는 **노랑/검정**이 표준이고, 빨강/흰색 사선은 "비워 둘 것"(소방설비·배전반 앞)에 가깝습니다. **어느 쪽도 쓸 수 없습니다** — 위 표대로 노랑·빨강 모두 HSV 마스크와 충돌하기 때문입니다. **검정/흰색 사선으로 대체합니다.** 시각적으로 "경고 구역"으로 읽히면서 마스크와 충돌하지 않습니다. 현장감 손실은 계층 2(라벨)·계층 4(소품)가 보완합니다.

#### 🔵 위험구역 경계 = 우드락 기둥 〔변경 2026-08-17〕

경계를 **바닥 테이프에서 우드락 수직 구조물로** 바꿉니다. 사선 무늬는 그대로 쓰되 **기둥 표면**에 넣습니다.

**바꾼 이유**: 사선 테이프가 주행 라인을 가로지르면 **라인센서가 정지점 마커로 오인**합니다. 사선이라 검정이 끊겼다 이어져 가짜 마커가 연속으로 터집니다. 경계가 수직 구조물이 되면 이 위험이 원천 제거되고, **로봇이 읽는 것(바닥 가로선)과 사람이 보는 것(수직 경계·명판)이 분리**됩니다. 현장에서도 로봇 측위 체계와 안전 표시 체계는 서로를 읽지 않습니다.

부수 효과로 현실성도 올라갑니다 — 실제 방호 기둥의 줄무늬와 같은 형태가 됩니다.

| 기준 | 값 | 근거 |
|---|---:|---|
| 게이트 개구부 | **800mm 이상** | 좁으면 VL53L1X가 기둥을 장애물로 읽고 정지합니다 (빔 폭 = 0.48×거리). §4의 「라인 중심↔고정 장애물 400mm」와 일치 |
| 기둥 높이 | 300~400mm | 저각 촬영(400~600mm)에서 뒤쪽 동작을 가리지 않는 높이 |
| 상단 가로대 | **없음** | 문틀 윗변이 있으면 카메라 시야를 가로지릅니다 |

> 🔴 **바닥에 판재를 깔지 마세요.** 라인센서 동작 범위가 **3~10mm**라, 5T 판재가 라인 근처 바닥을 5mm 높이면 7mm로 맞춰둔 센서가 2mm가 되어 포화합니다. 경계를 포함한 모든 구조물은 **세우는 형태**로만 만듭니다.

상세 제작 기준은 `demo_set_build_plan.md` §5.3·§10.4, 마커 검출 설계는 `firmware/구역_마커_설계.md` 참조.

- **파지 대상 물체만 빨강·노랑을 독점**하게 유지 — 이게 색 기반 판정의 전제입니다.
- 추가 안전장치: 프론트 카메라 **ROI를 작업공간 높이로 제한**하면 바닥이 마스크에서 아예 빠집니다. (테이프 색 제한과 **병행**하세요. ROI만 믿으면 카메라 각도 조정 때 깨집니다)
- **AMR이 따라가는 선이 "산업 현장 통로선"이 됩니다** — 라인트레이싱이 시나리오상 필연이 됩니다.

**계층 4 — 배경 소품**
- 미니 안전콘, 소화기, 안전표지판, 드럼통

```

| 프론트 화각 **밖** | 자유롭게 — 영상 와이드샷에만 등장 |

손목 카메라는 물체에 근접해 배경 영향이 적으므로, 사실상 **프론트 화각만 관리하면 됩니다.**

#### 🔵 ACT 정책은 **하나** — 황색 변형체만 〔확정 2026-08-07〕

**2026-08-01 의 「대상별 정책 2개」를 대체합니다.** 그때 준비해 둔 폴백(*"시간이 부족하면
블록만 프리셋으로 내린다"*)을 **폴백이 아니라 기본 계획으로 승격**한 것입니다.

| 대상 | 처리 | 근거 |
|---|---|---|
| **적색 강체** | **비전 오프셋 보정 + 프리셋** | 파지 중 형상이 변하지 않는다 → 받침으로 **자세·높이가 확정**되어 남는 자유도가 **x·y 둘뿐** → 프론트 카메라로 중심을 재어 프리셋 포즈에 오프셋을 가산하면 된다. **학습할 것이 없다** |
| **황색 변형체** | **ACT** | **파지가 곧 형상을 바꾼다** → 받침이 통하지 않고, **형상이 매번 달라 파지점이 위치의 함수로 정해지지 않는다** → 오프셋을 더하는 것으로 풀리지 않는다 |

**근거가 일정이 아니라 물리입니다.** 「학습은 불확실성이 있는 곳에만 쓴다」는 이 문서가
pick/place 를 가른 원칙과 같습니다 — 목적지는 기하가 확정돼 드럼 입구(물리 지그)로 흡수하고,
물체 위치는 불확실해 ACT 로 흡수합니다.

**일정상의 이득은 결과이지 이유가 아닙니다.**

| | 정책 2개 (구) | **정책 1개 (신)** |
|---|---|---|
| 학습 | 15.6h × 2 = **31h 순차** | **15.6h** |
| 수집 | 두 벌 | 한 벌 |
| 8/15 이후 **재학습 여유** | **1회** | **2~3회** |
| 실패 가능 지점 | 2 | 1 |

> 🔴 **성립 조건 두 가지 — 하나만으로는 적색 파지가 성립하지 않습니다.**
>
> **① 누출 방지 받침** (`demo_set_build_plan.md` §7.1.1) — 용기를 똑바로 세우고 높이를 고정합니다.
> 남는 자유도를 **x·y 둘로 줄이는 것**이 역할이지 산포를 흡수하는 것이 아닙니다.
>
> **② 비전 오프셋 보정 — 🔴 진우 신규 작업.**
> 정지 산포는 받침으로 없어지지 않습니다. 받침은 바닥에 있고 팔은 차체에 붙어 있어,
> 차체가 20mm 덜 서면 팔 기준으로 20mm 어긋납니다. 그리퍼 여유는 십수 mm 수준이라
> 산포가 「양호」(±30mm) 로 나와도 순수 프리셋은 빗나갑니다.
>
> ```
> 프론트 카메라가 적색 원통 검출  →  화면 중심 대비 픽셀 오프셋
>         ↓  1회 캘리브레이션으로 고정된 변환 (픽셀 → 팔 기준 mm)
>    x·y 오프셋  →  프리셋 포즈에 가산  →  파지
> ```
>
> `vision_node` 가 이미 색+형상으로 적색을 검출하므로 **새 인식이 아닙니다.**
> 학습도 데이터도 없는 고전 기하 계산이고, 산업에서 부르는 이름은 **VGR** 입니다.
>
> 🔵 **발표에서 오히려 대비가 선명해집니다** — 강체는 *산업 표준 방식(비전 보정 + 프리셋)*,
> 변형체는 *아직 열린 문제(학습된 정책)*. 「학습은 불확실성이 있는 곳에만 쓴다」가
> 두 대상에서 각각 다른 답으로 나타납니다.

> 🔴 **프리셋을 먼저 세울 것.** 적색 프리셋은 데이터도 학습도 필요 없고,
> `arm_controller` 에 놓기 프리셋(`OVERPACK_DRUM`·`HAZMAT_STORAGE`)이 이미 동작합니다.
> 이것이 서면 **임무 전 구간이 찍히는 상태**가 확보되고, 그 위에 ACT 를 얹게 됩니다.
> **만들어지지 않은 폴백은 폴백이 아닙니다.**

정책이 하나여도 **구역 분리는 그대로 유지**합니다. 같은 장면에 두 물체를 나란히 놓으면
*"지금 무엇을 잡아야 하는가"* 가 화면상 모호해지고, 다른 대상이 손목 카메라에 들어오면
학습 때와 입력이 달라집니다. 처리 방식 선택은 **정지점 마커 순번**이 하므로 새 인식이 필요 없습니다.

#### 🔵 ③ 이 왜 핵심인가 — 정밀 주행 대신 ACT 가 흡수합니다

로봇은 **엔코더가 없어 자기가 얼마나 이동했는지 모릅니다.** "물체까지 30cm 전진" 같은 명령 수단이 없습니다.
ToF 로 닫는 방법도 작은 물체에는 통하지 않습니다 — VL53L1X 는 27° 원뿔 안의 **가장 가까운 것**을 보므로
300mm 에서 빔 폭이 144mm 라 뒤쪽 벽·기둥이 먼저 잡히고, 센서 높이가 대상과 다르면 아예 보이지 않습니다.

그래서 접근을 **두 단계로 나눕니다.**

| 단계 | 담당 | 정밀도 |
|---|---|---|
| 작업 위치까지 | **정지점 마커 2단 정지** (`firmware/구역_마커_설계.md` §6) | 대략 |
| 마지막 수 cm | **ACT (손목 카메라)** | 정밀 |

즉 **차체가 정확히 설 필요가 없습니다.** 마커에서 몇 cm 어긋나 서도 팔이 손목 카메라를 보고 보정합니다.
그것이 ACT 를 쓰는 이유입니다.

→ 따라서 ③ 의 **하한**은 임의로 정하는 것이 아니라 **정지점 산포 실측에서 나옵니다.**
정지 산포가 ±3cm 로 측정되면 데이터는 **최소한 ±3cm 범위**를 덮어야 합니다.
`demo_set_build_plan.md` §13.2 의 「마커 정지 산포 ×10 측정」이 이 값의 선행 조건입니다.

#### 🔵 ③ 의 범위는 산포가 아니라 **팔 도달 범위** 기준으로 잡습니다 〔확정 2026-08-01〕

산포(±3cm)는 **실패하지 않기 위한 최소값이지 목표값이 아닙니다.**
수집 범위는 제약이 아니라 **선택**이며, 넓게 모으면 정책이 그 범위 전체에서 파지합니다.

| | 좁게 (산포만) | **넓게 (채택)** |
|---|---|---|
| 범위 | ±3cm | **팔 도달 범위의 상당 부분** (섀시 장착 후 실측) |
| 비용 | 최소 에피소드 | **에피소드 수만 증가.** 새 하드웨어·새 코드 0 |
| 학습 시간 | — | 스텝 수 설정이라 크게 늘지 않음 |
| 답할 수 있는 질문 | 없음 | *"물체 위치가 바뀌면?"* → **화면으로 답** |

**왜 이렇게 바꾸는가 — 마커 방식의 약점을 정면으로 메웁니다.**

마커 정지는 *"물체 위치가 달라지면 못 잡는 것 아닌가"* 라는 지적을 받습니다.
정확히는 **마커가 고정하는 것은 차체이지 물체가 아닙니다.** 물체 가변성은 팔이 담당하고,
그 담당 범위가 곧 ③ 의 수집 범위입니다. 좁게 잡으면 이 반론에 답할 수단이 사라지고,
넓게 잡으면 **입증**으로 바뀝니다.

비전으로 차체를 물체까지 접근시키는 대안보다 강합니다 — 저쪽은 *"물체를 찾아간다"* 는 **주장**이고,
이쪽은 *"위치가 달라도 잡는다"* 는 **입증**입니다. 심사에서 둘의 무게는 다릅니다.

→ 영상 증거 컷으로 연결됩니다: **같은 물체를 3곳에 놓고 3번 다 성공**
(`demo_video_scenario.md` §8 SCENE-09 증거 후보 1순위).

> **한계는 한계대로 답합니다.** 팔 도달 범위를 벗어나면 파지할 수 없습니다.
> *"도달 범위 밖 대상에 대한 차체 재접근은 확장 항목"* — 진입 조건 확인,
> GHS 등급 주장을 다룬 방식과 같은 선입니다.

**전방 카메라 인식은 영상 증거로만 씁니다.** 대시보드에 "위험물 식별됨"이 뜨는 컷은 확보하되,
**주행 판단에는 쓰지 않습니다.** 인식이 틀리거나 WiFi 가 지연돼도 로봇은 마커에서 정상적으로 멈춥니다.
ToF 는 여기서 **안전 인터록**입니다 — 앞에 아무것도 없으면 팔을 뻗지 않습니다.

### ⭐ 8/15 Go/No-Go 기준

**판단**: 이 시점에 **실기에서 ACT 파지가 1회 이상 성공**했는가? — 🔴 **대상별로 따로 판단합니다.**

| 결과 | 조치 |
|---|---|
| **둘 다 Go** | 두 파지 모두 ACT (`demo_video_scenario.md` §5.2) |
| **한쪽만 Go** | 성공한 대상만 ACT, 실패한 대상은 **프리셋 + 포즈테이블 폴백**. 영상 분할화면은 성공한 대상으로 구성 |
| **둘 다 No-Go** | **전량 폴백** (정밀 IK 아님 — 5.5). 종이컵은 v4 방식인 **프리셋 + Load 클램프**로 처리. ACT는 "데이터셋 + 학습 곡선" 을 **연구 성과로 발표**에 포함 |

**대상별 판단이 핵심입니다.** 정책을 둘로 나눈 이유가 여기서 회수됩니다 — 통합 정책이었다면
한쪽이 안 되는 순간 전량 폴백밖에 없습니다.

No-Go여도 손해가 아닙니다. LeRobot 데이터셋과 학습 결과 자체가 **기술 깊이 어필 자료**가 됩니다.
영상의 「학습 파지 심층」 30초도 데이터셋·학습 곡선으로 채워져 **비지 않습니다.**
다만 **폴백을 8/15에 결정**해야 리허설 시간이 남습니다.
