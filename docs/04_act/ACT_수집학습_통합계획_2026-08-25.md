## 0. 결론 요약

- 8/22 시도는 **실패**했다. 텔레옵 연결 로그(`SOLeader connected` 등)는 떴지만 **팔로워암이 실제로 움직이지 않았다** — 연결 성공 ≠ 텔레옵 성공. 원인 진단 전이므로 재발 가능성을 배제할 수 없다.

- 사용자 결정: 8/22 도구는 **그 컴퓨터에서 직접 복사**해 가져온다 (git pull이나 재작성이 아님).

## 2. 버전 불일치(0.4.4 vs 0.6.1)가 실제로 영향을 주는 지점

8/22 작업기록 §7.1에 이미 한 번 걸렸던 사례가 있다 — `--dataset.display_data=true`(0.6.1 문법)가 실제로는 최상위 옵션 `--display_data=true`여야 했다. **이런 CLI 플래그 이름·위치 차이가 버전마다 있다.** 그대로 복사한 `record_act.ps1`을 이 노트북에서 돌리면 같은 종류의 오류가 다시 날 가능성이 높다.

**대응**: lerobot을 0.6.1로 올리지 않는다 (이 노트북은 이미 검증된 0.4.4 + CUDA 조합이라 마감 10일 전에 버전을 흔드는 리스크가 더 크다). 대신:

```powershell
$py = "C:\Users\sehi5\miniconda3\envs\lerobot\python.exe"
& $py -m lerobot.scripts.lerobot_record --help
```

로 0.4.4의 실제 `lerobot_record` 플래그 목록을 먼저 뽑아, `record_act.ps1` 안의 `--dataset.*` / `--display_data` 류 인자를 이 노트북 버전에 맞게 하나씩 대조·수정한다.

## 5. 하드웨어 진단 — 수집 재개 전 필수 (이 노트북 기준)

8/22 작업기록 §14의 진단 순서를 이 노트북 값(COM3/COM5, 인덱스는 재확인)으로 그대로 적용한다. **연결 로그만 보고 건너뛰지 말 것 — 8/22 실패의 핵심 교훈이다.**

1. 팔로워암 전원 꺼진 상태로 시작
2. 남아있는 이전 파이썬 프로세스 없는지 확인 (`Get-Process python -ErrorAction SilentlyContinue`)
3. 장치관리자에서 COM3/COM5 그대로인지 확인
4. 팔 주변 비우기
5. `tools/check_home.py --port COM3` — 읽기 전용 확인
6. `tools/check_align.py --leader COM5 --follower COM3`
7. `tools/check_goal.py --port COM3 --fix`
8. 데이터 저장 없이 `teleop.ps1` 짧게 실행
9. **팔로워암이 리더암 6축을 실제로 따라 움직이는지 사람이 눈으로 확인** — 8/22는 이 단계를 건너뛴 게 아니라 여기서 실패를 확인하고도 본 수집으로 넘어갔던 게 문제였다
10. 정상 종료 후 토크 해제 확인
11. 그 다음에만 pilot 1개 → 배치 1

## 6.8 🔴 학습 중 데이터 무결성 버그 발견·수정 (2026-08-24)

`lerobot-train` 시작 직후(스텝 100~400 내) `FrameTimestampError`로 반복 크래시. 근본 원인 진단 후 수정 완료, 학습 재시작함.

**근본 원인**: 오늘까지 배치1·배치2 사고 복구 때 썼던 "메타데이터 수술" 패턴 — `meta/episodes/*.parquet`와 `info.json` 카운터만 고쳐서 문제 에피소드를 "삭제"하고, 실제 `data/*.parquet`/영상 바이트는 손대지 않고 그대로 둠(§ 위쪽 6.6/6.7 서술 그대로) — 이게 조용히 반쪽짜리였다. **학습 시 `LeRobotDataset`을 episode 필터 없이 전체 로드하면 그 "삭제된" 행들이 다시 이어붙는다** — 남은 행이 유효한 `episode_index` 값을 그대로 갖고 있어서 필터링되지 않기 때문. 그 결과 이후 모든 프레임의 전역 위치가 밀리면서, ACT의 액션 청크(chunk_size=100)가 에피소드 경계에서 클램핑될 때 엉뚱한 위치의 영상 프레임을 가리키게 됨.

- 감사 결과: `data/*.parquet` 실제 행 67,610개 vs `info.json` 선언 59,976개 — **유령 행 7,634개**, 파일 3곳(`file-001.parquet` 1049행/에피소드2, `file-002.parquet` 5914행/에피소드3~8, `file-004.parquet` 671행/에피소드19)에 분산돼 있었음. 전부 오늘 이전 크래시·중복촬영 복구 잔재
- 조치: 전체 데이터셋 백업(`C:\ACT_data\act_red_yellow_v1_prehostrowcleanup_backup_20260826_033306`) 후, 각 인증된 `meta/episodes`의 (episode_index → chunk/file) 매핑과 실제 파일 위치가 불일치하는 행만 골라 pyarrow로 제거. 이후 `data/*.parquet` 총 행수 정확히 59,976, `index` 컬럼이 0~59975 빈틈없는 연속열임을 확인
- 검증: 59,976 프레임 전체를 실제 학습과 동일한 조건(ACT delta_timestamps, `num_workers=4`, batch_size=8)으로 1회 전수 디코딩 — 오류 0건 (365초, 164 frames/s)
- **`tools/check_act_dataset.py`에 재발 방지 체크 추가** — `_validate_raw_data_row_count()`: `data/*.parquet` 실제 행수를 세어 `info.json`의 `total_frames`와 비교. 기존 검증은 `meta/episodes` 장부만 봐서 이 버그를 두 번이나(8/25 최초 완료 시, 8/26 재검증 시) 놓쳤었음
- 🔵 **교훈**: 앞으로 에피소드를 "삭제"하는 메타데이터 수술을 할 땐 `meta/episodes` 카운터 수정에서 끝내지 말고, 반드시 `data/*.parquet`에서도 해당 행을 물리적으로 제거할 것. 영상(`videos/*.mp4`)은 타임스탬프 범위로 조회되므로 이 문제와 무관 — 안 지워도 안전

학습 재시작: `train_log2.txt`, 3000+ 스텝 통과, ~6 step/s 안정적 진행 확인.

### 🔵 홈 자동 복귀 — 리더암이 필요 없어졌다 (2026-08-28)

리더암 필요 여부를 소스에서 확인한 결과:

| 상황 | 리더암 | 근거 |
|---|---|---|

→ 그래서 `rollout_act.ps1` 을 **시행 1회 = `lerobot_record` 프로세스 1회(에피소드 1개) + `go_home`** 구조로 바꿨다. lerobot 의 다회 에피소드 모드를 쓰지 않는다.

- ✅ **리더암 연결이 아예 필요 없다** — 검증에도, 시연 영상 촬영에도. 화면에 리더암이 없으니 텔레옵으로 오해받을 여지도 없다

- ✅ 부수 효과: `go_home` 이 끝나면 `Goal == Present == 홈` 이라 다음 토크 인가 시 튐이 없다
- 대가는 시행당 프로세스 재시작 오버헤드 약 30초뿐 (물체 재배치 시간과 겹치므로 실질 손해 없음)

🔴 **`go_home.py` 의 안전 설계 — 고치더라도 이 3가지는 유지할 것**:
1. **한 번에 점프시키지 않는다.** 코사인 이징(시작·끝 속도 0)으로 나눠 보낸다. `check_goal` 실측에서 194° 벌어진 축이 있었는데, 그 거리를 순간 이동으로 명령하면 서보가 최대 속도로 튄다
2. **어떤 경로로 끝나든 전 축 토크를 끈다** (`finally`, 축별 개별 `try`). STS3215 는 `Goal_Position` 쓰기만으로 토크가 켜지고, 목표에 못 닿으면 과부하로 죽는다 (2026-07-28 wrist_roll 사망)
3. **180° 이상 벌어져 있으면 `--force` 없이 거부한다.** 정상적인 롤아웃 종료 자세라면 그렇게 벌어질 수 없다 → 홈 파일이나 팔 상태 이상 신호

실측 검증(2026-08-28): 3° 복귀 → 전 축 도착, 토크 전 축 0, `check_goal` 통과. 이어서 실제 롤아웃 종료 자세(`shoulder_lift` **171°**, `elbow_flex` 166° 떨어진 상태)에서도 전 축 정상 복귀 확인.

🔴 **`MAX_SAFE_DIFF` 를 2048(180°)로 되돌리지 말 것.** 위 실측에서 **정상적인** 종료 자세가 1949 카운트(171°)였다 — 180° 상한이면 시행마다 아슬아슬하게 걸려 30회 검증 도중 가짜 거부로 루프가 멈춘다. 그래서 3000(264°)으로 올렸다. 거리 자체는 이징이 안전하게 처리하므로 이 상한의 목적은 "먼 거리 차단"이 아니라 "말이 안 되는 값 차단"이다.

### 🔴 녹화 종료 시 토크가 풀려 팔이 처지던 문제 (2026-08-28 수정)

사용자 육안 관찰: *"뚜껑 닫기 이후 토크가 한 번 꺼졌다가 홈 자세로 복귀한 거 같아."*

- 원인: `so_follower.py:226` — `disconnect()` 가 `disable_torque_on_disconnect`(기본 `True`)를 그대로 따른다. 녹화 프로세스가 끝나는 순간 토크가 풀려 **팔이 중력으로 처지고**, 그 다음에야 `go_home` 이 새 프로세스로 붙어 **처진 자세**부터 복귀를 시작했다
- 위험: 처지는 순간 팔이 격리함·뚜껑을 칠 수 있고, 복귀 시작 자세가 매번 달라진다
- 조치: `rollout_act.ps1` 이 `--robot.disable_torque_on_disconnect=false` 를 붙인다 (CLI 수용 확인 완료). 녹화가 토크를 켠 채 끝나고 `go_home` 이 실제 최종 자세에서 이어받는다
- 🔴 **그래서 `go_home` 호출은 반드시 `finally` 안에 있어야 한다.** 녹화가 실패·예외로 끝나도 `go_home` 이 실행되어야 토크가 풀린다. `go_home` 자체도 `finally` 로 토크를 끄므로 이중 보호다
- `-NoHome` 일 때는 이 플래그를 붙이지 않는다 (토크를 켠 채 방치하면 안 되므로 lerobot 기본 동작 유지)
- 🔵 아래 "조기 종료" 작업으로 **이 플래그 자체가 불필요해져 제거했다** — 복귀가 `robot.disconnect()` 보다 먼저, 같은 프로세스 안에서 끝나므로 팔이 처질 구간이 없다

### 🔵 조기 종료 + 같은 프로세스 내 복귀 (2026-08-28)

사용자 지적: *"뚜껑 닫은 후 멈춰있다가 홈 자세로 복귀까지의 시간이 좀 길어. 뚜껑닫기 완료 후 0.5초 정도 정지해있다가 바로 복귀하도록 해줘."*

**`tools/run_lerobot_record_patched.py`** 신규. 설치된 lerobot 은 건드리지 않고 두 개만 몽키패치한다:
- `predict_action` → 정책이 내놓은 액션을 정지 감지기에 흘려보낸다
- `init_keyboard_listener` → `events` 를 dict 서브클래스로 바꿔, `exit_early` 조회 시 정지 판정을 반영한다 (`record_loop` 이 매 프레임 이 값을 읽는다 — 루프 본문을 복사하지 않아도 되는 이유)

그리고 `record_loop` 의 `finally` 에서 **같은 프로세스의 `robot.bus` 로 바로 복귀**한다. `save_episode`(영상 인코딩)보다 먼저라 팔이 즉시 움직인다. 별도 `go_home` 프로세스 기동 비용(파이썬 + lerobot import + 버스 연결)이 사라졌다.

🔴 **임계값은 추측이 아니라 실측 3회의 기록된 action 을 재생해 정한 것이다** (`still_threshold=0.4`, 프레임당 6축 절대변화 합):

| 구간 | 프레임당 변화 (평균/최대) |
|---|---|
| 활발한 동작 (~14.5초) | 3.2 ~ 5.6 / 최대 17 |
| 느린 정렬 (14.5~16.5초) | 0.4 ~ 2.3 |
| 16.5초 마지막 움직임 | 최대 5.6 ~ 6.8 |
| **17.0초 이후 진짜 정지** | **0.13 ~ 0.24 / 최대 0.5** |

- 3회 모두 **17.0초부터 정지**로 일관됐고, 감지기는 17.27초에 발동한다 = 정지 시작 후 0.27초. 요청한 "0.5초 정지"와 맞는다
- **`still_threshold` 를 0.2 로 낮추지 말 것** — 재생 검증에서 ep1 이 **미발동**했다. 0.4 가 정지(≤0.24)와 느린 정렬(≥0.4) 사이에 놓인 값이다
- 🔵 정지 구간에도 **3.3초 주기로 스파이크**(최대 2.7~4.3)가 있다 — ACT 청크 크기 100프레임 ÷ 30fps = 3.33초, 청크 경계의 불연속이다. `still_seconds=0.5`(15프레임)면 스파이크 사이에 충분히 들어가지만, 이 값을 3초 이상으로 키우면 **영영 발동하지 않을 수 있다**
- `min_seconds=8` 이전에는 발동하지 않는다 (정책이 느리게 시작하는 경우 보호). 정책이 8초 이후 얼어붙으면 조기 종료되는데, 그건 이미 실패한 시행이므로 오히려 시간 절약이다

`rollout_act.ps1` 은 복귀 후 `check_home.py` 로 **밖에서 한 번 더** 확인한다 — 다음 시행이 홈에서 시작하지 않으면 결과가 오염되므로.

**다음 단계**: 조합 10가지 × 3회 = 30회 검증 → 성공률·실패 단계 기록 → 문서화

## 6.9 🔴 체크포인트 저장 시 심볼릭 링크 권한 크래시 (2026-08-26)

`train_log2.txt` — 스텝 20,000(첫 체크포인트 저장 시점)에서 크래시. 데이터 문제 아님 — 그 전까지 20,000스텝을 5.85 step/s로 완전히 안정적으로 통과함.

- 원인: `lerobot/utils/train_utils.py`의 `update_last_checkpoint()`가 매 체크포인트마다 `checkpoints/last` 심볼릭 링크를 무조건 생성 시도. Windows에서 심볼릭 링크 생성은 관리자 권한 또는 "개발자 모드" 활성화가 필요한데 이 노트북엔 없음 → `OSError: [WinError 1314] 클라이언트가 필요한 권한을 갖고 있지 않습니다`
- 체크포인트 본체(`checkpoints/020000/`)는 심볼릭 링크 시도 **이전에** 이미 정상적으로 다 저장돼 있었음 — 데이터 손실 없음
- `last` 심볼릭 링크는 순수 편의 기능. 실제 재개(`--resume=true`)는 `--config_path`로 특정 체크포인트의 `pretrained_model/train_config.json`을 직접 지정하는 방식이라 이 링크에 의존하지 않음 (`lerobot/configs/train.py` 확인)
- 조치: `tools/run_lerobot_train_patched.py` 신규 작성 — `update_last_checkpoint`를 몽키패치해서 심볼릭 링크 실패 시 경고만 남기고 계속 진행하도록 함. 설치된 lerobot 패키지 자체는 건드리지 않음
- 재개 명령: `--resume=true --config_path="...\checkpoints\020000\pretrained_model\train_config.json"` — 스텝 20,000부터 정확히 이어짐(진행바가 "80000"으로 표시 = 100000-20000), 옵티마이저·스케줄러 상태도 함께 복원 확인
- 🔵 **앞으로 `lerobot-train`을 돌릴 땐 항상 `tools/run_lerobot_train_patched.py`를 통해 실행할 것** (`tools/run_lerobot_module.py lerobot.scripts.lerobot_train` 대신) — 안 그러면 `save_freq`(기본 2만 스텝)마다 이 크래시가 반복됨
