## 2. 🔴 지금 장비 없이 되는 것 — 우선순위 순

**RPi 5 와 NoIR 만으로 아래가 전부 진행된다.** 팔·AMR 을 기다릴 이유가 없다.

| 순위 | 항목 | 왜 지금인가 |
|---|---|---|
| 1 | **ACT 추론 지연 벤치마크** (더미 가중치) | 프로젝트 최대 리스크(**RPi 가 ACT 를 감당하는가**)를 푸는 항목. 미달 시 대안(ONNX·양자화·컴퓨트 승급)에 시간이 필요하다 |
| 2 | **NoIR 빨강/노랑 HSV 분리 테스트** | **미실행 상태.** 실패하면 정색 웹캠 추가 구매가 발생한다 — 늦게 알수록 비싸다 |
| 3 | **DRIVE → RPi 정지점 순번 메시지 형식 확정** | ACT 정책 선택 전체가 대기 중. **연결은 못 해도 규격은 지금 정한다** |
| 4 | **DFR0753 ×1 발주** + 부속 | 없으면 배터리 주행이 안 돼 연속 시연을 못 찍는다 |
| 5 | **LeRobot 격리 venv 설치** | 1번의 선행 조건 |
| 6 | **ROS2 노드 구현 · 코드 상수 개명** | 하드웨어 무관. 명명은 **구현 착수 전**에 끝내야 한다 |

### 2-1. ACT 추론 벤치마크 — 학습 완료를 기다리지 말 것

**더미 가중치로 측정 가능하다.** 카메라도 팔도 필요 없다 — 입력 텐서를 더미로 만들면 된다.

| 측정 항목 |
|---|
| 1회 추론 지연 (**목표 <1초**) |
| 제어 루프 주파수 (Hz) |
| 해상도별 지연 — 640×480 / 224 이하 |
| CPU 온도 · 스로틀링 (`vcgencmd measure_temp`, `get_throttled`) |
| **정책 2개 동시 상주 시 실제 메모리(RSS)** — 계산상 약 414MB |

미달 시 순서: **해상도 하향(224 이하) → ONNX 변환 → 양자화**.
해상도 하향은 성공률과 트레이드오프이므로 **지연과 성공률을 같이** 봐야 한다.

#### 🔴 5V 3A 어댑터로 측정할 때 — 결과 해석이 갈린다

RPi 5 공식 권장은 **5V 5A** 다. `5V 3A` 는 SoC 풀로드(2.0~2.4A) + 쿨러 + microSD 를 합치면
**마진이 0.3~0.7A 밖에 없어 스로틀링이 걸릴 수 있다.**
그러면 *"RPi 가 느리다"* 와 *"전원이 모자랐다"* 를 구분할 수 없다 — **거짓 음성**이다.

🔴 **`vcgencmd get_throttled` 를 반드시 병행 기록할 것.** 그 값에 따라 결론이 갈린다.

| `get_throttled` | 지연 | 해석 |
|---|---|---|
| **`0x0`** | **<1초** | ✅ **합격 확정.** 더 나쁜 전원 조건에서 통과했으므로 DFR0753 을 붙이면 나아질 뿐이다. **재측정 불필요** |
| `0x0` | >1초 | ⚠ **RPi 성능 부족 확정.** 전원 탓이 아니므로 바로 대안 검토로 넘어간다 |
| 언더볼티지 비트 | — | 🔴 **값 무효.** 12V 소스 + DFR0753 확보 후 재측정 |

**세 갈래 중 두 갈래는 5V 3A 에서도 결론이 난다. 12V 를 기다릴 이유가 없다.**

> 🔵 **1초여도 된다.** ACT 는 `chunk_size=100` 이라 **추론 1회가 미래 100스텝**을 낸다.
> 30Hz 제어 기준 **1회 = 3.3초 분량**이므로 **추론이 1Hz 여도 30Hz 제어가 성립**한다.
> 이것이 RPi 배포를 성립시키는 핵심 논리이고, 심사에서 *"RPi 로 52M 모델이 됩니까"* 를 받으면 이렇게 답한다.

### 2-2. NoIR 색 분리 테스트 — **1차는 아무 빨강·노랑 물체로**

- 대상: **빨강 vs 노랑** 구분. NoIR 은 IR 필터가 없어 **빨강이 전체적으로 번진다**
- 🔵 **실제 시연 물체(적색 강체 · 황색 종이컵)는 아직 확정·조달되지 않았다.**
  **손에 잡히는 아무 빨간 물체와 노란 물체로 먼저 해볼 것.** 실물을 기다릴 이유가 없다 —
  이 테스트가 보는 것은 **NoIR 센서 자체의 적·황 분리 능력**이라 대상이 달라도 대부분 드러난다

#### 🔴 결과 해석은 비대칭이다

| 결과 | 판정 |
|---|---|
| **분리 안 됨** | ✅ **결론이 선다.** 임의 물체로도 안 되면 실물로도 안 된다 → **정색 웹캠 1대(~₩20,000) 추가 구매**를 바로 결정 |
| **분리 됨** | ⚠ **잠정.** 실물 재질·채도가 다르면 달라질 수 있다 → **실제 물체 + 촬영 조명**으로 재확인 후 임계 확정 |

**즉 1차 테스트의 값어치는 「불가」를 조기에 잡아내는 데 있다.**
웹캠을 사야 한다면 그 사실을 지금 아는 것이 8월 말에 아는 것보다 훨씬 싸다.

#### 형상 특징값은 실물이 필요하다

- **면적 · 채움률 · 원형도**는 물체마다 값이 다르므로 **임의 물체로 재면 의미가 없다**
- 1차는 **색만** 본다. 형상 측정은 실제 대상이 조달된 뒤에 한다
- 최종 3분기 판정: 색만으로 충분 / 색 + 형상으로 커버 / 둘 다 불충분 → 웹캠 구매

> 🔴 **임계값은 조명에 통째로 딸려 간다.** 최종 HSV 임계는 **촬영에 쓸 조명 아래**에서 잡아야 한다
> (수집 조명 = 촬영 조명 원칙). 1차 테스트 값을 그대로 코드에 박아두지 말 것.

### 2-3. 순번 메시지 규격

- 순번은 **모듈로 4 순환값** — 정지점 = 3구역 + 충전 스테이션 분기점
- **분기점은 카운트하되 정차하지 않는다.** 세지 않으면 다음 마커가 어느 구역인지 식별 불가
- 정책 2개(적색 블록용 / 황색 종이컵용) 중 무엇을 로드할지가 이 값으로 결정된다
- **DRIVE 가 승환에게 있으므로 실연결은 §4 로 미룬다. 규격 합의만 지금 한다**

## 3. 전원 — 부품 도착 후

> **선행 조건: 인두기 60W 이상 확인** (강희 담당, 시점 미정).
> 🔴 **확인 전 납땜 착수 금지 — 예비가 없다.**

| 단계 | 내용 |
|---|---|
| 준비 | **60W 이상** 인두, **치즐/베벨 팁**, 350~380℃, 플럭스 |
| 연습 | 🔴 **폐기판 선행 연습 필수** |
| 납땜 | 전선 **선(先) 주석도금** → 플럭스 → **3~5초 내 완료**. 안 녹으면 인두 출력 부족이다 |
| 고정 | 🔴 **에폭시/글루건 스트레인 릴리프** — 진동 파단 시 **시연 중 RPi 리부팅** |

**난이도의 실체**: 패드가 작아서가 아니라 **8A 급 전력 패드라 인두 열을 빨아먹기 때문**이다.
30W 급으로는 납이 녹지 않고 기판만 태운다. 미달 시 **Hobbywing UBEC 8A**(₩25,000, 무납땜)로 전환.

### 결선·설정

- 🔴 **GPIO 5V 핀 급전 금지** — 내부 보호 회로를 우회한다. **USB-C 입력만**
- `config.txt` → **`usb_max_current_enable=1`** (또는 EEPROM `PSU_MAX_CURRENT=5000`)
  미설정 시 USB 총 전류가 **600mA** 로 제한되어 카메라 2대 동작 불가
- 출력단에 **`2200µF/25V`**(보유분) 병렬
  🔴 **연결 순서**: 충전된 대용량 캡이 달린 상태로 USB-C 를 꽂으면 RPi 입력 캡(0V)으로 한꺼번에 방전된다.
  **USB-C 를 먼저 연결 → 그다음 컨버터 입력에 전원 인가.** 뺄 때는 반대
  🔲 ⌀13×25mm 급이라 키가 크다 — **눕혀서 글루건·케이블타이로 진동 고정**

### 🔵 지금 가능한 부분 검증 — 🔴 **단, 12V 소스가 있어야 한다**

전부하 검증(§4)은 팔·USB 카메라가 있어야 하지만, **그 둘 없이도 대부분 확인된다.**
다만 **DFR0753 자체가 12V 입력을 필요로 하므로**, 5V 3A 어댑터만으로는 이 검증도 시작할 수 없다.

```
CPU 4코어 풀로드 + NoIR 스트리밍 상태로 10분
watch -n1 vcgencmd get_throttled   →   0x0 유지
```

실부하 3.0~3.5A 중 **SoC 가 2.0~2.4A 로 최대 항목**이므로, CPU 풀로드만으로도 상당 부분 걸러진다.
여기서 언더볼티지가 뜨면 **전부하에서는 확실히 탈락**이므로 즉시 대체품으로 간다.

- 🔴 **수집 이후에 캘리브레이션이 바뀌면 데이터셋이 통째로 무효**가 된다

### ✅ 통합 방식 = **C 안 확정** 〔2026-08-03〕

**ESP↔RPi 연결을 진우가 직접 하기로 했으나 DRIVE 가 승환에게 있어** 세 안을 검토했다.

| 안 | 내용 | |
|---|---|---|
| A | DRIVE 를 진우에게 전달 | 승환의 라인 튜닝이 멈춘다 — 기각 |
| B | 모여서 한 번에 통합 | 통합 시점에 이 방식으로 |
| **C** | **순번 메시지 규격만 먼저 합의**, 통합은 섀시 완성 후 | ✅ **채택** |

규격만 정해지면 진우는 §2 를 전부 진행할 수 있고, 승환은 라인 튜닝을 계속한다.
**통합은 어차피 섀시가 나온 뒤 실제 배선으로 해야 한다** — 지금 합쳐도 다시 뜯는다.

🔲 **통합 시점 = 섀시(Waffle Plate) 완성 직후.** 그때 모여서 한 번에 붙인다.
그전까지 진우가 할 일은 **순번 메시지 규격 합의** 하나다 (§2-3).

## 5. 확정 사항 — 참고

### 모터 정지 권한 = DRIVE 단독 〔2026-08-03 확정, v5 §5.3.1〕

TB6612 의 `STBY` 와 PWM 이 전부 DRIVE 에 결선되어 **물리적으로 DRIVE 만 정지가 가능**하다.
ToF 를 DRIVE 에 남긴 근거(**「안전 기능이 무선에 의존하면 안 된다」**)가 정지에도 그대로 적용된다.

| 계층 | 주체 | 조건 |
|---|---|---|
| 0 | 하드웨어 | ESP32 사망·리셋 → **STBY 10kΩ 풀다운**이 자동 정지 |
| 1 | **DRIVE 로컬** | ToF 장애물 · 라인 이탈 · 배터리 저전압 |
| 2 | **RPi** | 미션 정지 · E-Stop · ENV 폴트 중계 · 비전 교차검증 불일치 |
| 3 | 사람 | XT60 수동 분리 |

🔴 **계층 2 구현 원칙 — `STOP` 명령이 아니라 하트비트.**

RPi 가 주기 신호를 보내고 **DRIVE 는 신호가 끊기면 정지**한다.
명령 방식은 **명령이 유실되거나 송신측이 죽으면 정지가 성립하지 않는다.**
하트비트 방식이면 **RPi 사망 · WiFi 두절 · ENV 사망이 단일 메커니즘**으로 처리된다.
v9 의 `RPI_TIMEOUT` 이 이미 같은 구조이므로 계승하면 된다.

- **진우가 결정할 값은 하트비트 주기 하나** — 통상 타임아웃의 **1/3 이하**
- 타임아웃(3초 → 1초 전후)은 DRIVE 펌웨어(승환)가 실측으로 확정한다
- **ENV 는 정지 권한을 갖지 않는다** — 판정을 하지 않는 보드이므로 일관된다

### ACT 정책 구성

- **정책 2개를 동시 상주**시킨다 (약 414MB / 8GB). 정지점마다 로드하지 않는다
- 🔴 **미션 시작 전 정책별 워밍업 추론 1회.** 미실행 시 **첫 파지에서만** 지연이 튄다
- 동시에 **추론**하지는 않으므로 **CPU·발열 예산은 정책 1개일 때와 동일**하다. 늘어나는 것은 메모리뿐

### 기타 주의

- 🔴 **`arm_controller` 는 실행하지 말 것** — `/arm/command` 로 6축 각도가 날아오면 ACT 와 겹친다.
  `arm_bridge` 는 TCP 소켓만 열 뿐 서보 버스를 건드리지 않으므로 켜둬도 무관
- 카메라는 `camera_ros`/libcamera 가 CSI 를 점유 중 → LeRobot 쪽은 **`--skip-cameras`** 로 실행
