## 0. 배경

원래 이번 세션은 순찰 시나리오(파지 제외) 중 미완성이던 두 가지 — ① NoIR 카메라 색상+가스 판정, ② 대시보드 화면 — 를 마무리하는 작업으로 시작했다. 대시보드 코드는 다 고쳤는데, RPi에 배포하려는 시점에 SSH 로그인이 막혀서(비밀번호 불명) 진행이 안 됐다. 그래서 "일단 파지 노트북 시연을 진행하겠다"는 사용자 판단에 따라 `rollout_act.ps1` 쪽 작업으로 전환했다.

## 1. RPi 대시보드 정리 (코드 완료, 배포 안 됨)

### 1.1 요청 내용

1. NoIR 카메라로 물체 감지 후 노란색이면 무조건 위험물, 빨간색은 가스 누출 시에만 위험물로 판단
2. 대시보드에 위험물체 판단 / NoIR 카메라 화면 / "노란색이면 ~한 위험물이다, 빨간색은 가스 누출 시 ~한 위험물이다" 형태의 문장이 보이게

### 1.2 확인된 것 — ①은 이미 구현·실기 검증 완료 상태였다

`vision_node.py`(HSV 색상 검출) + `hazard_detector_node.py`(v11 이벤트식 판정 — 노랑=무조건 L3, 빨강=GAS_CHECK 결과에 따라 L3/L0)가 이전 세션에 이미 완성돼 있었고, 노랑 감지 → L3 판정까지 실기 로그로 검증된 상태였다. 오늘 새로 할 일은 ②(대시보드)뿐이었다.

### 1.3 변경한 파일

**`ros2_ws/src/hazardbot_dashboard/hazardbot_dashboard/dashboard_node.py`**
- `/env/gas_result`(v11 GAS_CHECK 응답: zone/result/baseline/minimum_raw/weak_percent) 구독 추가 — 기존엔 아예 구독하지 않고 있었다
- 파지 미션 시절 3구역 연속-MQ-임계값 매트릭스(`zone_thresholds`) 데이터 제거 — 지금 쓰는 v11 이벤트식 판정과 개념이 안 맞음

**`ros2_ws/src/hazardbot_dashboard/templates/index.html`**
- "위험물체 판정" 카드로 확장 — `/hazard/detected`의 `detail` 문장(예: "황색 산화성 고체 감지 — 취급구역 내 위치 자체가 위반")을 그대로 노출, 색상 배지(●빨강/●노랑) 추가
- "가스 정밀검사(GAS_CHECK)" 카드 신규 — zone/판정(DETECTED·CLEAR·ERROR)/baseline/최저원시값/약화율 표시
- 구식 "구역별 판정 매트릭스" 카드·JS, 서보 피드백 카드, GRIP/TRANSPORT/ISOLATE 배지 스타일(파지 미션 잔재) 제거
- NoIR 카메라(`/video`)는 그대로 유지

### 1.4 배포 못 함 — SSH 로그인 실패

`hazardbot@hazardbot.local` 비밀번호를 몰라 로그인 불가. 키 인증으로 전환하려 했으나(`~/.ssh/id_ed25519` 이미 존재, comment `hazardbot-claude`), `authorized_keys` 등록 자체가 최초 1회는 비밀번호 인증이 필요해서 막혔다.

**다음에 AP 연결되면 할 일** (비밀번호 확보 전제):
```bash
# 1. 키 등록 (최초 1회, 비밀번호 필요)
cat ~/.ssh/id_ed25519.pub | ssh hazardbot@hazardbot.local \
  "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"

# 2. 잔여 프로세스 정리
ssh hazardbot@hazardbot.local "pkill -f amr_bridge_node; pkill -f sensor_bridge_node; pkill -f dashboard_node; pkill -f hazard_detector_node; pkill -f vision_node; pkill -f camera_node"

# 3. 파일 전송
scp ros2_ws/src/hazardbot_dashboard/hazardbot_dashboard/dashboard_node.py \
    hazardbot@hazardbot.local:~/ros2_ws/src/hazardbot_dashboard/hazardbot_dashboard/dashboard_node.py
scp ros2_ws/src/hazardbot_dashboard/templates/index.html \
    hazardbot@hazardbot.local:~/ros2_ws/src/hazardbot_dashboard/templates/index.html

# 4. 빌드 + 재기동
ssh hazardbot@hazardbot.local "cd ~/ros2_ws && source /opt/ros/jazzy/setup.bash && colcon build --symlink-install --packages-select hazardbot_dashboard"
ssh hazardbot@hazardbot.local "cd ~/ros2_ws && source install/setup.bash && ros2 launch hazardbot_dashboard hazardbot_patrol_demo.launch.py"
```
검증 순서: 노랑 물체 → 판정 카드 문장 확인 / 빨강(가스 有·無 각각) → GAS_CHECK 카드 zone·판정 확인.

**RPi 재부팅 후라면 먼저**(AP IP는 재부팅마다 초기화됨):
```bash
sudo ip addr add 192.168.4.1/24 dev wlan0   # RPi 로컬에서
```

## 2. 노트북 ACT 롤아웃 — 홈 자세 반복 드리프트 문제

### 2.1 증상

`.\rollout_act.ps1` 실행 시 preflight `check_home.py`가 `wrist_roll`에서 반복적으로 80° 이상 벗어남을 보고. "지금 자세가 기본 자세다, 이걸로 다시 저장해달라"는 요청이 세션 중 네 번 있었고, 그때마다 `wrist_roll` 값이 크게 요동쳤다:

| 시점 | shoulder_pan | shoulder_lift | elbow_flex | wrist_flex | **wrist_roll** | gripper |
|---|---:|---:|---:|---:|---:|---:|
| 세션 시작(원본) | 2459 | 1479 | 3015 | 2664 | **1032** | 1329 |
| 1차 재저장 | 2464 | 1476 | 3014 | 2693 | **1933** (+901) | 1333 |
| 2차 재저장 | 2461 | 1481 | 3013 | 2704 | **1015** (-918) | 1335 |
| 3차 재저장 | 2456 | 1488 | 3013 | 2716 | **1966** (+951) | 1337 |
| 4차 재저장(최종) | 2454 | 1494 | 3013 | 2728 | **1024** (-942) | 1337 |

`shoulder_pan`/`shoulder_lift`/`elbow_flex`/`gripper`는 세션 내내 ±10카운트(1° 이내)로 안정적이었던 반면, `wrist_roll`만 매번 80~85° 규모로 왔다갔다했다. `wrist_roll`은 연속회전축이라 중력으로 돌아갈 자연스러운 쉬는 자세가 없다(`check_home.py` 자체 주석) — 시행 사이 물체를 손으로 빼거나 팔을 만지는 과정에서 실제로 돌아가고 있을 가능성을 제기했으나, **원인은 세션 내에서 확정하지 못했다.** 🔲 다음에 재현되면 시행 사이 손목을 건드리는지 직접 관찰 필요.

현재(최종) 값은 `calibration/follower_home.json`에 저장돼 있고, 백업본들은 `calibration/follower_home.backup_*.json`으로 남아 있다.

### 2.2 별개로 찾은 구조적 버그 — "복귀했는데 시작 때랑 다르다"

`check_goal.py --fix`는 홈으로 되돌리는 게 아니라 **그 순간의 (드리프트된) 현재 위치를 그대로 새 기준으로 인정**하는 스크립트(토크 켜질 때 안 튀게 하는 용도)다. `rollout_act.ps1`이 매 시행 전 이걸 먼저 불렀는데, 그 앞의 "물체 배치 후 Enter" 대기 구간(토크 꺼진 상태) 동안 밀린 위치를 그대로 받아들이고 시작해버리는 구조였다.

**수정** (`rollout_act.ps1`): 매 시행마다 `check_goal.py` 전에 `go_home.py`(1초, 코사인 이징)를 추가로 넣어서, 대기 구간에 밀린 위치를 실제 저장된 홈으로 능동 복귀시킨 뒤 시작하도록 고쳤다.

### 2.3 성능 저하 의심 — 진단 결과

"검증 때보다 파지 성능이 떨어진 것 같다"는 우려에 대해, 학습 데이터셋(`C:\ACT_data\act_red_yellow_v1`)의 실제 에피소드 시작 프레임(`observation.state`, 정규화값)과 최종 홈 자세를 직접 비교했다:

| 축 | 학습 데이터 평균 (±표준편차, n=3 에피소드) | 세션 중 확인 시점 값 | 편차 |
|---|---|---:|---|
| shoulder_pan | -2.77 ± 0.64 | -3.66 | ~1.4σ |
| shoulder_lift | -98.54 ± 0.70 | -97.72 | ~1.2σ |
| elbow_flex | 99.43 ± 0.04 | 99.28 | 미미 |
| wrist_flex | 47.42 ± 3.43 | 54.71 | **~2.1σ (가장 큼)** |
| wrist_roll | -56.43 ± 1.31 | -58.22 | ~1.4σ |
| gripper | 1.33 ± 0.03 | 1.49 | 미미 |

**결론**: 홈 자세 편차 자체는 (wrist_flex가 제일 크지만) 극단적인 수준은 아니라서, 단독으로 큰 성능 저하를 설명하긴 어려워 보인다. 프로젝트 문서(`docs/03_scenario_demo/demo_video_scenario.md`)에 이미 "조명·배치가 세션 간에 바뀌면 성공률이 다시 달라진다"는 기록이 있어, **조명/물체 배치(근거리·원거리) 차이가 더 유력한 가설**이다. §2.1의 `wrist_roll` 반복 드리프트가 실제 원인일 가능성도 배제 못 함. 🔲 미해결.

### 2.4 파지 시작까지 과정 최소화

Rerun Viewer(`--display_data=true`)는 유지한 채로:
- `check_cameras.py` 고정 5초 대역폭 테스트를 preflight에서 제거 — 카메라 1대(손목)만 쓰므로 원래 목적(2대 동시 대역폭 경합 검증)에 해당 없음. 필요하면 별도로 `python tools\check_cameras.py --bandwidth <index> --seconds 5` 실행
- 시행 전 `go_home.py` 대기시간 2초 → 1초
