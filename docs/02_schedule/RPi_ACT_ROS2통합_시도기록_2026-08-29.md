## 0. 배경 — 왜 이 작업을 시작했나

8/28 통합 리허설(주행→감지→ACT→격리) 가능 여부를 점검하다가, `arm_act_node.py`가 `POLICY_PATHS: None` 더미 폴백 상태 그대로라는 걸 발견했다. 30회 검증(86.7%)에서 쓴 ACT 파이프라인(`rollout_act.ps1`)은 ROS2를 전혀 거치지 않는 완전히 별도 경로였다 — `mission_orchestrator`가 실제로 정책을 실행하는 것처럼 설계돼 있었지만 그 연결이 한 번도 만들어진 적이 없었다. 이걸 실제로 연결해보기로 했다.

---

## 1. 확인된 구조적 사실 3가지 (작업 시작 전 조사)

**① `arm_bridge`/`arm_controller`가 가정하는 하드웨어가 실물과 다르다.** 둘 다 "ARM ESP32 #2"가 서보를 구동하고 TCP로 중계한다고 짜여 있었는데, 실제로는 **RPi가 USB로 서보 버스를 직결**한다(README 상시주의 규칙과 일치, ESP32 #2는 애초에 존재하지 않는 설계였다).

**② ACT 정책은 "파지"만 하지 않는다.** 학습된 태스크가 "집기 → 이동 → 격리함에 넣기 → 뚜껑 닫기"를 한 에피소드로 묶어 학습됐다. 그래서 `arm_controller`의 별도 "놓기" 프리셋 이동은 ACT 뒤에 실행하면 안 된다 — `mission_orchestrator`의 `TRANSPORT` 상태를 건너뛰어야 한다.

**③ 자동 성공/실패 판정이 없다.** 30회 검증 때도 사람이 영상 보고 판정했다. ACT 통합 후에도 "에피소드가 정상 종료됐는가"만 자동으로 알 수 있고, 파지 성공 여부는 여전히 사람이 봐야 한다.

## 2. 만든 것 — 최종 상태

### 2.1 `mission_orchestrator_node.py` — GRIP→REPORT 직결

`/arm/act_result` 구독 + `act_result_cb` 추가 (완료 시 `TRANSPORT` 생략하고 `GRIP→REPORT→PATROL`). 기존 서보 피드백 기반 판정(`feedback_cb`)은 "ESP32 #2가 실존하지 않아 죽은 코드"라는 설명과 함께 남겨둠(삭제 안 함). 전체 패치는 `ACT_ROS2통합_진우_2026-08-29.md` §2.2 참고.

이후 진우가 `RETURN`/`IDLE`/`/mission/start` 등 별도 개선을 커밋(`jinu-rpi5-restore` 브랜치)했고, 그 과정에서 **`amr_bridge_node.py` 파일이 실수로 `mission_orchestrator_node.py` 내용으로 통째로 덮어써지는 사고**가 있었다 — 커밋 이력(`b7e1f84`→`2a643f8`) 대조로 확인, 직전 정상 커밋 기준으로 복구하고 RETURN 릴레이(`/amr/return_request`→`<RETURN>`, `<RETDONE>`→`/amr/return_complete`)를 얹어서 다시 전달함. 상세는 `amr_bridge_복구_진우_2026-08-29.md`.

### 2.2 DRIVE 펌웨어 — `DETECT`/`RETURN`/`RETDONE` 프로토콜

`firmware/esp32_drive_tcp/esp32_drive_tcp.ino`에 추가:
- `<DETECT,CS>` — 정지 마커 도달마다 1회 송신(비전 캡처 트리거)
- `<RETURN,CS>` 수신 → 개루프 후진 시작(`RETURN_SPEED`/`RETURN_DURATION_MS` 잠정값, 실측 필요)
- `<RETDONE,CS>` — 후진 완료 시 1회 송신
- 시리얼 `r`/`R` 키로 RPi 없이 벤치에서 후진 거리 실측 가능

상세는 `RETURN프로토콜_구현안_진우_2026-08-28.md`.

### 2.3 `arm_act_node.py` — 최종 버전 (실물로 끝까지 검증됨)

아래 코드가 RPi에서 실제로 파지 에피소드를 끝까지(정상 종료) 실행한 버전이다. 첫 버전(`tools/run_lerobot_record_patched.py` 서브프로세스 방식)은 RPi의 lerobot 버전이 달라 `AttributeError`로 죽어서 전면 재작성했다 — 자세한 경위는 §3.

```python
"""
ACT 정책으로 "파지 → 이동 → 격리함에 넣기 → 뚜껑 닫기" 전체를 실행하는 노드.

2026-08-29 두 번째 재작성 — `lerobot-rollout`(lerobot 0.6.2)로 갈아탐.

🔴 왜 바꿨는가 — RPi 실물 테스트에서 발견한 것
    첫 버전은 `tools/run_lerobot_record_patched.py`(=`lerobot_record.py` 몽키패치)를
    서브프로세스로 불렀는데, RPi 의 lerobot 0.6.2 에서 `AttributeError:
    module 'lerobot.scripts.lerobot_record' has no attribute 'predict_action'`
    로 죽었다. 노트북(30회 검증)에서 쓴 lerobot 버전과 달리, 0.6.2 는 정책 실행을
    `lerobot_record.py`(=`record_loop`, teleop 전용으로 축소됨)에서 완전히 분리해
    별도 CLI `lerobot-rollout`(`lerobot/rollout/` 패키지)으로 옮겼다.

🔵 `--strategy.type=base` 로 간다 — "Autonomous rollout, no recording"
    - 녹화가 아예 없어서 `lerobot.datasets`(→ `datasets` 패키지) 의존성 자체가 없다.
      RPi 에 `datasets` 미설치라 막혔던 문제가 이 경로에선 발생하지 않는다.
    - 조기종료·홈복귀를 직접 짤 필요가 없다 — `--return_to_initial_position=true`
      (기본값)가 에피소드 종료 시 선형 보간(3초/50fps)으로 부드럽게 홈으로 돌아간
      뒤 `robot.disconnect()`한다(`lerobot/rollout/strategies/core.py:
      _teardown_hardware`, 실물 실행 전 소스 직접 확인함). 순간이동 위험 없음.
    - `tools/go_home.py`/`run_lerobot_record_patched.py`는 이제 이 노드에서 안 쓴다
      (여전히 벤치 단독 테스트용으로는 유효 — rollout_act.ps1 경로).

🔴 이 정책은 "파지"만 하지 않는다
    태스크 지시문 자체가 "집기→이동→격리함에 넣기→뚜껑 닫기"를 한 에피소드로 묶어
    학습됐다. 그래서 이 노드가 끝나면 `arm_controller`의 별도 "놓기" 프리셋 이동은
    **건너뛰어야 한다** — mission_orchestrator.py 의 GRIP→REPORT 직결이 그래서 필요.

🔴 자동 성공/실패 판정이 없다
    30회 검증 때도 사람이 영상을 보고 판정했다. 이 노드는 "에피소드가 정상
    종료됐는가"만 `/arm/act_result` 로 보고한다. completed=True 를 "파지 성공"으로
    오해하지 말 것.

🔲 전제 — 아직 실물로 끝까지 못 돌려봄
    이 버전은 RPi 에서 에러 로그를 보고 원인만 확정한 상태다. 실제로
    `lerobot-rollout --strategy.type=base` 명령이 이 인자 조합으로 끝까지 도는지는
    처음 실행이다 — 반드시 옆에서 지켜볼 것.
"""
import json
import subprocess
import threading
from pathlib import Path

import rclpy
from rclpy.node import Node
from std_msgs.msg import String


class ArmActNode(Node):
    def __init__(self):
        super().__init__('arm_act_node')

        # ── 파라미터 — 코드 수정 없이 launch 인자/`ros2 param`으로 바꿀 수 있다 ──
        # 🔲 기본값은 전부 추정치다. RPi 의 실제 경로·포트로 launch 인자에서 덮어쓸 것.
        self.declare_parameter('project_root', str(Path.home() / 'HazardBot'))
        self.declare_parameter('python_path', 'python3')
        # 🔵 비워두면 python_path 와 같은 bin/ 디렉터리의 lerobot-rollout 콘솔
        # 스크립트를 자동으로 쓴다(venv pip install 이 만들어주는 실행파일).
        # 다른 위치에 있으면 여기 직접 지정.
        self.declare_parameter('lerobot_rollout_path', '')
        self.declare_parameter('policy_path',
                                str(Path.home() / 'act_checkpoint' / 'pretrained_model'))
        self.declare_parameter('robot_port', '/dev/ttyACM0')
        # 2026-08-29 추가 — 체크포인트 config.json 에 device:"cuda" 가 박혀 있어도
        # lerobot 이 cuda 없으면 자동으로 cpu 로 폴백하긴 하지만(경고 로그만 찍음),
        # 매번 체크포인트를 새로 받을 때마다 JSON 을 손으로 고칠 필요 없게
        # 여기서 명시적으로 override 한다. RPi 에 GPU 가 생기면 이 파라미터만 바꾸면 됨.
        self.declare_parameter('policy_device', 'cpu')
        # 🔵 2026-08-29 — RPi 실측: lerobot-find-cameras opencv 결과 /dev/video8 만
        # 실제로 프레임을 준다(나머지는 같은 장치의 부가 노드). 정수 인덱스가 아니라
        # 경로 문자열이라 파라미터 타입도 문자열로 바꿨다.
        self.declare_parameter('camera_index', '/dev/video8')
        self.declare_parameter('camera_backend', 200)   # cv2.CAP_V4L2 — RPi(Linux) 값
        self.declare_parameter('episode_time_s', 20.0)  # → --duration
        self.declare_parameter('display_data', False)   # 헤드리스 RPi 기본값

        # 🔵 2026-08-29 추가 — RPi 실측: 케이던스 로그 확인 결과 평균은 23ms(예산
        # 33.3ms 안)인데, chunk_size=100(≈3.3초)마다 새 청크를 계산하는 그 한 틱만
        # RPi CPU 에서 ~1초 걸려서 20초 에피소드 중 4번 정지가 생겼다(끊김의 원인).
        # `--inference.type=rtc` 는 lerobot-rollout 문서에 "느린 모델을 위한
        # Real-Time Chunking"이라고 명시된 옵션 — 다음 청크를 미리 계산해서 경계에서
        # 안 멈추게 하는 것으로 보인다. 기본은 sync(기존 방식, 검증된 쪽) 유지하고
        # rtc 는 옵트인 — 이 정책에 맞는 튜닝값이 검증된 적 없어서 실험 단계다.
        self.declare_parameter('inference_type', 'sync')  # 'sync' 또는 'rtc'
        self.declare_parameter('rtc_execution_horizon', 10)
        self.declare_parameter('rtc_max_guidance_weight', 10.0)

        self._busy_lock = threading.Lock()
        self._busy = False

        self.create_subscription(String, '/arm/grip_request', self.grip_request_cb, 10)
        self.pub_result = self.create_publisher(String, '/arm/act_result', 10)

        self.get_logger().info('Arm ACT Node 시작함 (lerobot-rollout --strategy.type=base)')

    # ════════════════════════════════════════════
    # mission_orchestrator 의 GRIP 진입 신호
    # ════════════════════════════════════════════
    def grip_request_cb(self, msg: String):
        with self._busy_lock:
            if self._busy:
                self.get_logger().warn('이미 ACT 에피소드 실행 중 — 이번 요청은 무시함')
                return
            self._busy = True
        threading.Thread(target=self._run_episode_guarded, daemon=True).start()

    def _run_episode_guarded(self):
        # 🔴 스레드 안에서 발생한 예외는 조용히 사라진다 — 반드시 여기서 잡는다
        try:
            self.run_episode()
        except Exception as e:
            self.get_logger().error(f'ACT 에피소드 실행 중 예외: {type(e).__name__}: {e}')
            self.publish_result(completed=False, error=f'{type(e).__name__}: {e}')
        finally:
            with self._busy_lock:
                self._busy = False

    # ════════════════════════════════════════════
    # 실제 롤아웃 — lerobot-rollout(base 전략) 호출
    # ════════════════════════════════════════════
    def run_episode(self):
        g = lambda name: self.get_parameter(name).value
        project_root = Path(g('project_root'))
        python_path = g('python_path')
        policy_path = g('policy_path')
        robot_port = g('robot_port')

        if not Path(policy_path).exists():
            self.get_logger().error(f'정책 체크포인트 없음: {policy_path} — 에피소드 실행 안 함')
            self.publish_result(completed=False, error='policy_path 없음')
            return

        # ① 실행 전 안전점검 — check_goal --fix 로 194°급 순간이동 위험을 미리 잡는다.
        #    이게 실패하면 절대 정책을 돌리지 않는다.
        goal_check = [python_path, str(project_root / 'tools' / 'check_goal.py'),
                      '--port', robot_port, '--fix']
        r = subprocess.run(goal_check, cwd=str(project_root))
        if r.returncode != 0:
            self.get_logger().error('check_goal --fix 실패 — 팔 자세 확인 필요, 에피소드 중단')
            self.publish_result(completed=False, error='check_goal 실패')
            return

        # ② lerobot-rollout — 콘솔 스크립트 경로: python_path 와 같은 bin/ 디렉터리
        rollout_path = g('lerobot_rollout_path') or str(Path(python_path).parent / 'lerobot-rollout')

        camera_cfg = (f"{{wrist: {{type: opencv, index_or_path: {g('camera_index')}, "
                       f"width: 640, height: 480, fps: 30, backend: {g('camera_backend')}}}}}")
        task = 'Pick up the hazardous object, place it in the isolation bin, and close the lid.'
        episode_time_s = float(g('episode_time_s'))
        args = [
            rollout_path,
            '--strategy.type=base',
            f'--policy.path={policy_path}',
            f"--policy.device={g('policy_device')}",
            '--robot.type=so101_follower',
            f'--robot.port={robot_port}',
            '--robot.id=follower_arm',
            f'--robot.cameras={camera_cfg}',
            f'--task={task}',
            f'--duration={episode_time_s}',
            '--fps=30',
            '--return_to_initial_position=true',
            f"--display_data={'true' if g('display_data') else 'false'}",
        ]
        inference_type = g('inference_type')
        if inference_type == 'rtc':
            args += [
                '--inference.type=rtc',
                f"--inference.rtc.execution_horizon={g('rtc_execution_horizon')}",
                f"--inference.rtc.max_guidance_weight={g('rtc_max_guidance_weight')}",
            ]

        # 홈 복귀(3초 고정, core.py 기본값) + 여유
        timeout_s = episode_time_s + 3.0 + 30.0
        self.get_logger().info(f'ACT 에피소드 시작 — 최대 {timeout_s:.0f}초까지 기다림')
        try:
            r = subprocess.run(args, cwd=str(project_root), timeout=timeout_s)
        except subprocess.TimeoutExpired:
            self.get_logger().error('ACT 에피소드 타임아웃 — 팔 상태를 직접 확인할 것')
            self.publish_result(completed=False, error='timeout')
            return
        except FileNotFoundError:
            self.get_logger().error(
                f'lerobot-rollout 실행 파일을 못 찾음: {rollout_path} — '
                f'lerobot_rollout_path 파라미터로 직접 지정할 것'
            )
            self.publish_result(completed=False, error='lerobot-rollout 없음')
            return

        if r.returncode != 0:
            self.get_logger().error(f'ACT 에피소드 비정상 종료 (exit {r.returncode})')
            self.publish_result(completed=False, error=f'exit {r.returncode}')
            return

        self.get_logger().info('ACT 에피소드 정상 종료 — 파지/격리 성공 여부는 사람이 확인할 것')
        self.publish_result(completed=True)

    def publish_result(self, completed: bool, error: str | None = None):
        msg = String()
        msg.data = json.dumps({'completed': completed, 'error': error})
        self.pub_result.publish(msg)


def main(args=None):
    rclpy.init(args=args)
    node = ArmActNode()
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    finally:
        node.destroy_node()
        if rclpy.ok():
            rclpy.shutdown()


if __name__ == '__main__':
    main()
```

## 3. RPi 실물 디버깅 시행착오 (시간순, 8/29)

한 번에 다 되지 않았다 — 실물에서만 나오는 문제를 하나씩 잡은 기록. 나중에 같은 종류의 통합을 다시 시도할 때 참고용으로 남긴다.

| # | 증상 | 원인 | 조치 |
|---|---|---|---|
| 1 | `ImportError: 'datasets' is required` | `lerobot_record.py`(=당시 쓰던 서브프로세스)가 `lerobot.datasets`를 임포트 시점에 강제 요구. RPi는 hostapd AP라 인터넷 없음 | 노트북에서 aarch64/cp311 wheel 32개(72MB) 오프라인 다운로드, USB/scp로 전달·오프라인 설치 준비(결과적으로 이 경로 자체를 안 쓰게 되며 불필요해짐) |
| 2 | `AttributeError: ... has no attribute 'predict_action'` | **결정적 발견** — RPi의 lerobot 0.6.2는 정책 실행을 `lerobot_record.py`에서 완전히 분리해 `lerobot-rollout`(별도 CLI)로 옮겼다. 노트북 검증 버전과 아키텍처가 다름 | `arm_act_node.py` 전면 재작성 — `lerobot-rollout --strategy.type=base` 채택. 녹화가 없어서 `datasets` 문제도 같이 해소됨 |
| 3 | `robot.connect()`가 대화형 캘리브레이션 마법사를 켜고 크래시 | `--robot.id=follower_arm`에 대응하는 캘리브레이션 파일이 RPi에 없음. 헤드리스라 아무도 관절을 안 움직여서 min=max로 기록되며 실패 | `calibration/follower_arm.json`을 `~/.cache/huggingface/lerobot/calibration/robots/so_follower/follower_arm.json`으로 scp (id=파일명 규칙) |
| 4 | `ConnectionError: Failed to open OpenCVCamera(0)` | `camera_backend=700`(Windows MSMF)이 Linux에 없는 백엔드. 인덱스도 Windows 기준값 | `lerobot-find-cameras opencv`로 실측 → `/dev/video8`만 실제 프레임 줌. `camera_index`를 문자열 파라미터로 변경, `camera_backend=200`(V4L2)으로 교체 |
| 5 | ResNet18 ImageNet 가중치를 `download.pytorch.org`에서 받으려다 인터넷 없어서 실패 | `config.json`의 `pretrained_backbone_weights`가 항상 다운로드를 트리거. 어차피 `model.safetensors`가 그 값을 바로 덮어써서 의미 없는 다운로드였음 | 로컬 체크포인트와 RPi 사본 둘 다 `pretrained_backbone_weights: null`로 수정 |
| 6 | 파지 성공, 그러나 "굼뜨고 끊기고 방향도 이상함" | **RPi CPU 추론 속도 한계.** 케이던스 로그 실측: 평균 23ms(예산 내)지만 `chunk_size=100`(≈3.3초)마다 새 청크 계산하는 틱만 최대 1023ms — 20초 에피소드 중 4번 정지. 정지 동안 관측이 stale해져 재개 시 방향도 어긋남 | `--inference.type=rtc` 옵션을 파라미터로 추가(옵트인, 기본은 sync 유지) — 튜닝값 미검증 상태로 시간 문제 때문에 여기서 중단 |

**핵심 한 줄 요약**: 노트북에서 30회 검증한 것과 **완전히 동일한 체크포인트**가 RPi에서는 **완전히 다른 lerobot 아키텍처(0.6.2, rollout 분리)** 위에서, **완전히 다른 하드웨어(CPU vs GPU)** 로 도는 상황이었다 — 소프트웨어 이슈는 전부 해결했지만, 마지막 하드웨어 성능 이슈는 시간 안에 못 풀었다.

## 5. 추가 시도 — GPU 오프로드 (`lerobot.async_inference`)

### 5.1 구조

`lerobot`에 정확히 이 용도로 만든 모듈이 이미 있었다 — 직접 FastAPI/WebSocket을 짤 필요가 없었다.

```
RPi(robot_client) — 카메라·서보 I/O, 관측을 gRPC로 송신
        ↕ gRPC
노트북(policy_server) — RTX 4060 GPU로 실제 정책 추론, 액션 반환
```

`--strategy.type=base`(lerobot-rollout)와 달리 이건 진짜 폐루프다 — RPi는 계산을 전혀 안 하니 청크 경계 스톨(§3의 문제 6) 자체가 구조적으로 없다.

### 5.2 무선 인프라 구축 (본 작업의 절반 이상을 차지함)

- WSL2 + Ubuntu 24.04 + ROS2 Jazzy를 이 노트북에 설치(RPi와 동일 Python 3.12) — `docs/02_schedule/RPi_ACT_ROS2통합_시도기록_2026-08-29.md` §2 참고할 코드 자산과는 별개로, 이 세션(Claude)이 RPi에 SSH로 직접 붙어 작업할 수 있는 환경도 같이 만듦(SSH 키 등록, `pi@hazardbot.local`)
- **네트워크가 계속 발목을 잡았다**: RPi 자체 AP(HazardBot)는 인터넷이 없어서 노트북이 거기 붙으면 Claude Code 세션 자체가 끊김 → 랜선 직결(link-local) → 재부팅으로 IP 초기화 → 강희 핫스팟(클라이언트 격리로 기기 간 통신 차단) → 결국 RPi를 다시 AP 모드로 돌리고 노트북이 그 AP에 DHCP로 붙는 구성으로 정착(`dnsmasq`가 `wlan0`에 IP가 없어 DHCP 응답을 못 하던 버그도 발견·수정: `sudo ip addr add 192.168.4.1/24 dev wlan0`)
- **재부팅 시 초기화되는 것**: `ip addr add`로 준 IP(이더넷 168.77.1, wlan0 192.168.4.1)는 런타임 명령이라 영구 설정이 아니다 — 재부팅마다 다시 잡아줘야 한다(추후 systemd-networkd 설정 파일로 영구화 필요, 이번엔 안 함)

### 5.3 실물 테스트 3회 — 시도한 수정들

| # | 증상 | 원인/조치 |
|---|---|---|
| 1 | `Repo id must be in the form...`: 체크포인트 경로 에러 | `--pretrained_name_or_path`는 **서버(노트북)가 자기 파일시스템에서 찾는 값**이다. RPi 경로(`/home/pi/...`)를 넘겼던 게 원인 — 노트북 경로(`C:/ACT_data/...`)로 교체 |
| 2 | 로봇·카메라·gRPC 연결 전부 성공, 팔이 움직이긴 하나 **제자리에서 조금씩만, 파지 시도 자체를 안 함** | 가설 A: `aggregate_fn_name` 기본값 `weighted_average`(이전 청크 30% 블렌딩)가 결정적 동작(파지)을 흐린다 → `latest_only`(블렌딩 없음)로 교체 |
| 3 | 같은 증상 지속 | 가설 B(실제로 발견됨): **`calibration/follower_home.json`의 `wrist_flex`가 학습 시 홈 자세와 8단위(정규화 기준) 어긋나 있었다.** 학습 데이터셋 100개 에피소드의 첫 프레임 `observation.state`를 직접 집계(평균 50.20, 표준편차 4.22)해서 검증 → 기존 값(41.89 상당)은 분포 최솟값보다도 낮았음 → `2567`→`2664`로 수정(역변환 공식 round-trip 검산까지 완료) |
| 4 | **①②를 모두 고친 뒤 재시도 — 그래도 동일 증상** | 색상 채널(RGB/BGR) 불일치도 의심해 확인했으나, `lerobot`의 `OpenCVCameraConfig` 기본값(`color_mode=RGB`)이 학습 경로·현재 경로 양쪽에 동일하게 적용됨을 코드로 확인 — 원인 아님으로 배제 |

### 5.4 미해결로 남긴 것

원인 후보 두 가지(청크 블렌딩, 홈 자세 오차)를 실측 근거를 가지고 각각 고쳤음에도 증상이 그대로였다 — **진짜 원인은 못 찾았다.** 다음에 이어서 볼 만한 후보 하나를 적어둔다: 이번 테스트는 전부 `--actions_per_chunk=50`을 썼는데, 체크포인트의 `config.json`엔 `chunk_size: 100, n_action_steps: 100`으로 돼 있다 — **학습된 청크 크기의 절반만 요청**하고 있었다는 뜻이다. 이게 서버 쪽 청크 슬라이싱 로직과 어떻게 상호작용하는지는 확인 못 했다. 시간 관계상 여기서 중단.

## 6. 최종 결정

**시연·제출 영상**: 검증된 노트북 경로(`rollout_act.ps1`, COM3 직결, RTX 4060) 그대로 사용. 86.7%(근거리 100%) 검증치가 그대로 유효하다.

**ROS2/RPi 통합 + GPU 오프로드**: 둘 다 이 문서 + 코드가 실물로 연결까지는 성공한 증거다(§3 RPi 로컬은 파지까지 성공, §5 GPU 오프로드는 연결·제어는 성공했으나 파지 동작 자체가 재현 안 됨). 개발완료보고서·PPT에서 "ROS2 오케스트레이션 + 원격 GPU 추론 아키텍처까지 구현·실물 검증을 시도했다"는 근거로 쓸 수 있다. 시연 영상에는 둘 다 넣지 않는다.

**나중에 시간이 남으면** — §5.4의 `actions_per_chunk` 불일치부터 확인, 그다음 `--inference.type=rtc` 튜닝(RPi 로컬 경로) 순으로 이어가는 게 좋다. 네트워크 인프라(WSL·SSH·AP 고정 IP)는 이미 구축돼 있어 재시도 비용은 낮다 — 단, wlan0/이더넷 IP는 RPi 재부팅마다 다시 잡아야 한다는 것만 기억할 것.
