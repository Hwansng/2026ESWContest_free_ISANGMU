2. 🔴 **강희는 「급전점 정리 → 통전 → 예열」을 아침 제일 먼저.** MQ 예열이 임계값 실측 전체를 막고 있다.

   8/24 에 **유효 에피소드 0개**로 끝난 원인이 정확히 이 단계다.
4. 🟠 **진우의 NoIR 색분리 결과가 오늘 나온다.** 실패면 대책 리드타임(필터 조달·카메라 교체)이 없으므로
   **그 자리에서 대책 ④(형상 특징 병용)으로 확정**한다. 조명·카메라를 다시 만지는 선택지는 오늘 없다.
5. 🔴 **ESP_Drive 는 「고쳐본다」가 아니라 「부수 피해를 확정하고 조달 결정을 내린다」가 오늘의 목표다.**
   🔵 유력 원인은 **GND 누락 상태의 반복 업로드 → 발열 → 사망**이라 **설계가 아니라 조립 실수**다 (§3.6).
   🔴 **그래서 새 보드를 꽂기 전 GND 도통 전수 확인이 필수다** — 같은 조건이면 새 보드도 몇 분이다.

| **성격** | 🔵 **설계 결함이 아니라 조립 실수.** 배선 정본은 그대로 유효, 고치는 건 **선 한 가닥** |

| **주변부** | 🔵 **TB6612·라인센서는 생존 가능성 높음** (그쪽엔 정상 동작 전류였다). 확인은 한다 |
| **노트북 USB** | 🔵 **걱정 대상 아님** — 60~90mA 는 포트 정격 안이고, 모터 전류는 ESP32 를 거치지 않는다 |
| **재발 방지** | 🔴 통전 전 **ESP32 GND ↔ 스타포인트 도통 필수** · GND 핀 **2개 이상** · 12V 인가 중 USB 업로드 금지 · 장착 후 OTA · **뜨거우면 즉시 분리** |
| **일정 영향** | 🔴 **DRIVE 작업 전면 중단** → §6-B.2 이월. 🔵 **ACT 수집과 ENV 는 무관** |

| | 확정 |
|---|---|

| 🔵 **시연 성립 조건** | 마커 정지(3mm) + ACT 로 **VGR 없이도 선다.** VGR 은 **폴백 좌표원 + 발표 근거** |

## 3.3-B ✅ 정지 산포 · 차체 통과 — 판단으로 종결 〔8/25〕

| 항목 | 결정 | 근거 |
|---|---|---|
| **정지 산포 ×10** | 🔵 **측정 생략** — 3mm 이하로 예상 | 8/21 판정 기준이 **±3cm 이하 = 양호**다. 예상값이 그 10분의 1이다 |
| **차체 통과 10/10** | 🔵 **충분히 통과** | 세트·바퀴가 최종 상태다 |

🔵 **어차피 둘 다 DRIVE 종속이라 오늘은 잴 수도 없었다.** 기다리지 않는 쪽이 맞다.

### 🔴 다만 이 결정이 소비되는 곳이 하나 있다 — 프로토콜 ③

산포의 유일한 소비처가 **「물체 배치 범위 = 의도 변동 + 실측 산포 × 1.3」**이었다.
산포를 3mm 로 두면 그 항이 사실상 사라지고, **배치 범위는 의도 변동만으로 결정된다.**

🔵 **그래서 바꿀 것이 없다.** 확정된 수집 설계(**5위치 = 중앙/앞좌/앞우/뒤좌/뒤우**)가
이미 의도 변동 그 자체다. **위치 간격을 좁힐 이유도, 넓힐 이유도 없다** — 설계 그대로 간다.

- [ ] 🔴 **자로 정렬하지 말 것.** 손으로 놓는 자연 오차가 **차체 yaw 를 흡수하는 여유**다 (8/18 확정)
- [ ] 🟠 **θ(yaw)는 x·y 3mm 로 보증되지 않는다.** 8/21 이 **「θ 우선」**이라고 적은 이유는
      **적색이 정방향 배치라 각도 여유가 좁기** 때문이다. 🔵 위 「자로 정렬 금지」가 그 대비책이고,
      그것으로 충분하다고 보고 간다. 🔴 **판정 후 적색만 미달하면 이 가정을 첫 번째로 의심한다**
- [x] ✅ **프로토콜 ⑦ 조작 인원 = 승환 1인, 100 에피소드 전부** 〔8/25 확정〕
      🔵 **시연 스타일이 섞이지 않는다** — CVAE 다중성이 커져 수렴이 늦어지는 경로가 닫혔다

> 🔵 **이로써 수집 프로토콜 ①~⑦ 이 전부 닫혔다.** ① 시작·종료(홈 → 뚜껑 닫고 1초) · ② ACT 담당 구간 ·
> ③ 배치 범위(5위치 · 자로 정렬 금지) · ④ 실패 처리 · ⑤ 속도(20~30초, 급가속 없이 일정하게) ·
> ⑥ `episode_time_s`=35 · ⑦ **1인 고정**. 🔴 **8/21 에 「가장 큰 구멍」이었던 항목이 오늘 메워졌다.**

### 🟠 1인 고정의 대가 — 리듬 드리프트

**교대가 없어진 대신, 위험이 「사람이 바뀐다」에서 「같은 사람이 지친다」로 옮겨간다.**
4~5시간이면 배치 1과 배치 10 의 조작 리듬이 달라질 수 있고, 그건 ⑤ 위반이라 **⑦로 막으려던
문제가 다른 문으로 들어온 것**이다.

- [ ] 🔵 **배치(10개) 사이에 반드시 쉰다.** 배치 경계가 이미 휴식 지점이다 — 새 규칙이 아니라 쓰는 것뿐
- [ ] 🔴 **리듬이 흐트러진 느낌이 들면 `R`(재촬영)을 쓴다.** 실패 에피소드는 저장하지 않고 다시 찍으면 되고,
      **비용은 그 에피소드 하나뿐**이다. 지친 채로 밀어붙여 저장하는 것이 훨씬 비싸다
- [ ] 🔵 **사후 확인이 공짜다** — `check_act_dataset.py` 가 에피소드별 `length` 를 읽는다.

## 3.6 🔴 대기 시간에 붙는 것 — ESP_Drive 고장 대응

**보드: DOIT ESP32 DEVKIT V1 (ESP32-D0WD-V3) · COM4.**
🔴 **원인 — 🔴 ESP32 자신의 GND 가 빠진 상태로 업로드를 반복했고, 그 과정에서 심하게 발열한 뒤 사망** 〔승환 확인, 8/25〕.

### ⓪ 왜 그게 칩을 죽이는가 — 그리고 왜 안 보였는가

```
  ESP32 는 USB 로 급전·접지된다          USB 가 자기 5V·GND 를 들고 오기 때문
        ↓                              🔵 그래서 GND 가 빠져도 업로드는 계속 성공한다
  ESP32 3V3 ──→ 라인센서 VCC · TB6612 로직 VCC        (약 60~90mA)
                       ↓
                 주변부 GND ──→ (−) 레일 ──→ 12V (−)
                       ↓
  🔴 ESP32 GND 가 (−) 레일에서 빠져 있다 = 이 전류가 돌아올 길이 없다
        ↓
  🔴 전류 전량이 신호선(S1~S5 · PWMA · AIN · BIN · STBY)을 타고
     GPIO 의 ESD 클램프 다이오드를 통해 칩 안으로 되돌아온다
        ↓
  클램프 다이오드는 수 mA 용이다. 60~90mA 면 10~30배 과부하가 상시로 걸린다 → 발열
        ↓
  🔴 래치업(기생 SCR 도통 → VDD-GND 저저항 경로)까지 가면 그 자리에서 영구 파괴
```

🔴 **「주변부 GND 가 빠진 경우」보다 이쪽이 나쁘다.** 주변부 하나가 빠지면 그 하나의 전류만 새지만,
**ESP32 GND 가 빠지면 3V3 에 매달린 전류가 100% 전부 GPIO 로 돌아온다.** 우회로가 아예 없다.

🔵 **「업로드는 계속 됐는데 보드가 죽었다」가 이 고장의 전형적인 겉모습이다.**
업로드 경로(USB)와 죽은 경로(주변부 귀환)가 **서로 다른 회로**라 정상으로 보였던 것이다.
🔴 **발열은 마지막 경고였다** — 뜨겁다고 느낀 시점에 이미 정격 밖 전류가 칩을 지나고 있었다.

🔵 **좋은 소식 두 가지.**
① **설계 결함이 아니라 조립 실수다.** `docs/06_firmware/README.md` 의 스타 그라운드 정본은 **그대로 유효**하고,
   고치는 것은 **선 한 가닥**이다.
② 🔵 **주변부는 살아 있을 가능성이 높다** (§3.6 ③) — 라인센서·TB6612 입장에서는 **정상 동작 전류**였다.
   이상 응력이 집중된 곳은 **ESP32 의 핀뿐**이다.

### ① 5분 판정 — 어디까지 죽었나 (🔴 12V·모터 분리, USB 만)

- [ ] **COM4 로 인식되는가** (장치관리자)
      🔴 **인식돼도 안심하지 말 것** — USB-UART 브리지(CP2102/CH340)는 ESP32 와 별개 칩이라
      **ESP32 가 죽어도 COM 포트는 그대로 뜬다.** 이 고장에서 가장 흔한 오독이다
- [ ] 업로드 시도 → 🔴 **`Connecting.....___` 에서 실패하면 ESP32 사망 쪽**(브리지는 살아 있다는 뜻)
- [ ] 시리얼 모니터 115200 — 부팅 로그 / `rst cause` / `Brownout detector was triggered`
- [ ] `esp32_ota_test/` 최소 스케치가 올라가면 → 🔵 **MCU 는 살아 있고 주변 회로·특정 GPIO 문제**
- [ ] **3V3 · 5V 핀 전압** 측정 — AMS1117 레귤레이터가 같이 갔을 수 있다 (귀환 전류가 3V3 레일을 지났다)
- [ ] 🔴 **꽂자마자 뜨거워지면 즉시 뽑는다** — 래치업이 남아 있다는 뜻. 그 보드는 폐기 판정

### ② 🔴 이 보드는 폐기가 기본값이다 — 「일부 핀은 살았다」로 끌고 가지 않는다

**ESP32 GND 가 빠진 경우 용의선상은 일부 핀이 아니라 I/O 링 전체다.**
3V3 에 매달린 전류가 **연결된 모든 신호선으로 갈라져** 돌아왔기 때문이다 — 라인센서 5핀
(G13·G18·G19·G23·G32)과 TB6612 7핀(G25·G26·G27·G14·G16·G17·G4)이 **전부** 그 경로다.
사실상 **쓰는 I/O 전부**다.

- [ ] MCU 가 살아 있으면 위 12핀을 하나씩 토글·읽기로 확인은 해본다 (기록용)
- [ ] 🔴 **그러나 「멀쩡한 핀으로 핀 배정을 옮겨 살려 쓰기」는 하지 않는다.**
      과전류를 맞은 다이는 **지금 통과해도 나중에 간헐 고장**을 낸다.
      D-10 에 주행 경로에 시한폭탄을 두는 선택이다. **판정은 폐기, 보드는 교체**
- [ ] 🔵 폐기 판정한 보드는 **버리지 말고 표시해서 보관** — 벤치 시험·목업용으로는 쓸 수 있다

### ③ 🔵 부수 피해 — 이번 경우는 주변부가 살아 있을 가능성이 높다

**라인센서와 TB6612 입장에서는 정상 동작 전류였다.** 비정상이었던 것은 「귀환 경로」이고,

## 4.1 아침 제일 먼저 — 급전점 · 통전 · 예열

### ⚠ MQ 5V 급전점 — 실배선이 정본과 다르다

**현재 MQ 센서가 ESP_Env 의 5V/VIN 에서 급전되고 있다.** 정본은 🔴 **XL4015 #B 출력에서 별도 한 쌍**이다.
🔴 **지금 만능기판을 뜨고 있으므로 지금이 고칠 수 있는 마지막 시점이다.**

| # | 왜 정본이 그렇게 정했는가 |
|---|---|
| ① | MQ 히터 합산 **상시 ~330mA**. ESP32 VIN 경유 시 250+330 = **580mA** → devkit 폴리퓨즈(통상 500mA)·노트북 USB 포트에서 **브라운아웃·리셋** |
| ② | 히터 리턴이 ADC GND 와 같은 레일이면 **MQ 를 읽는 그 자리에 히터 전류가 그라운드 바운스를 얹는다** |

🔵 **전력 계통 자체는 승환 담당이지만 급전선을 실제로 붙이는 것은 강희다.**
🔴 **애매하면 혼자 정하지 말고 승환에게 넘긴다** — 오늘은 옆에 있다.

### 🔴 통전 전 5항목 (되돌릴 수 없는 것)

- [ ] ① **MQ 5V 급전점 = XL4015 #B 별도 한 쌍** (데이지체인 금지)
- [ ] ② **MQ AO 가 분압을 거치는가** — 직결 금지 · **10k / 10k = 2.50V** (10k/20k 는 3.33V, ADC 초과)
- [ ] ③ **히터 GND 는 벅 GND 직결** — ADC GND 와는 **스타포인트에서만** 만난다
- [ ] ④ **KY-026 · 부저 VCC = 3V3** (5V 아님)
- [ ] ⑤ **MQ-2 = G35** (G33 아님)
- [ ] 🔴 ⑥ **`ESP_Env` 의 GND 도통부터 확인** 〔8/25 추가 — **ESP_Drive 를 죽인 것이 정확히 이것이다**〕
      🔴 **ESP32 자신의 GND 가 빠진 채 USB 를 꽂으면, 3V3 에 매달린 센서 전류 전량이
      GPIO 의 보호 다이오드를 타고 칩으로 돌아와 칩을 태운다** (§3.6 ⓪).

**(나) 🔴 트리거 소스가 정말 ToF 인가 — 이건 시나리오를 다시 봐야 한다**

| | |
|---|---|
| 🔴 **위험** | 로봇은 **정지마커에서 서고 그다음 판정**한다. 그런데 ToF 로 트리거하면 **거리 안에 뭐가 들어오든** 검출이 돈다 |

### ③ H 계산 — 4점이면 정확히 결정된다

자유도가 8이고 대응점 한 쌍이 방정식 2개를 주므로 **4쌍 = 8개 방정식으로 딱 떨어진다.**

```python
# tools/ 아무 데서나 python 으로 실행
import cv2, numpy as np, json

# ① 픽셀 좌표 (u, v) — ② 에서 읽은 값
src = np.float32([
    [___, ___],   # 앞좌
    [___, ___],   # 앞우
    [___, ___],   # 뒤좌
    [___, ___],   # 뒤우
])
# ② 팔 베이스 기준 (x, y) mm — ① 에서 잰 값. 🔴 순서가 src 와 같아야 한다
dst = np.float32([
    [___, ___],
    [___, ___],
    [___, ___],
    [___, ___],
])

H = cv2.getPerspectiveTransform(src, dst)   # 4점이면 이것. 5점 이상이면 cv2.findHomography

def px_to_mm(u, v):
    p = np.float32([[[u, v]]])
    return cv2.perspectiveTransform(p, H)[0][0]

print(H)
json.dump({"H": H.tolist(), "note": "2026-08-25 측정, 75mm 바퀴 기준"},
          open("calibration/homography.json", "w"), indent=2)
```

- [ ] 🔴 **측정 조건을 같이 적는다** — 날짜 · **바퀴 75mm** · 조명 상태. 조건이 바뀌면 이 값은 무효다

### ④ 5번째 점 검증 — 🔴 이걸 빼면 정확도를 모르는 채로 끝난다

🔴 **4점으로 풀면 그 4점은 항상 완벽히 맞는다.** 4점에서의 오차는 정확도가 아니라 산수 확인일 뿐이다.

- 🔵 **그 오차를 없앨 필요가 없다.** VGR 은 「그 앞까지」 데려다주고 **마지막 수 cm 는 ACT 가 폐루프로** 접는다.
  🔵 이 구조가 발표의 주장 그 자체다 — *"접근 오차는 산업 표준 비전 보정이 접고,
  마지막 폐루프 파지만 학습이 맡는다."* VGR 을 빼면 ±30mm 전 범위를 데이터로 덮어야 해
  에피소드가 몇 배로 뛴다

## 5.7 오늘 순서

```

  1. last_recv_time · 포트          한 줄 2건, 아침에
  2. NoIR 색 분리 (승환과)          오전 중 결론 — 실패면 대책 ④ 확정
```
