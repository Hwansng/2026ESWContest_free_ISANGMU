# 확인 요청 — DRIVE(ESP_Drive) ↔ amr_bridge 연동

| | |
|---|---|
| 작성 | 2026-08-28 · 승환 |
| 대상 | `jinu-rpi5-restore` 브랜치 `19fe096`("EMERGENCY 체인 완전 복구 및 env 토픽 정합성 수정") |
| 성격 | 🔴 **이 커밋은 확인했다. `main`엔 아직 없다.** ESP_Drive 새 보드를 다시 붙이기 전에 3건만 확인·수정 부탁 |

## 0. 먼저 — 잘된 것

- 🔵 **EMERGENCY 체인 복구 판단 맞음.** `mission_orchestrator`→`/amr/emergency`→`amr_bridge.emergency_cb`→DRIVE로 STOP. 예전엔 `emergency_stop()`을 아무도 안 불러서 죽은 코드였는데 이제 실제로 연결됨
- 🔵 **가스/화염 판정 정상화 판단 맞음.** `hazard_detector`·`dashboard`가 DRIVE의 가짜 `/amr/gas`·`/amr/temp`(항상 0)를 버리고 `sensor_bridge`(ENV 보드, 포트 8765)의 `/env/gas`·`/env/flame`·`/env/distance`로 갈아탄 것 확인함
- 🔵 `sensor_bridge.parse_msg`에서 `last_recv_time`을 매 수신마다 갱신하는 것도 확인함 — 이게 맞는 패턴이고, 아래 1번은 이걸 `amr_bridge`에도 그대로 옮기면 되는 문제

---

## 1. 🔴 `amr_bridge`의 `last_recv_time`이 갱신되지 않는다

`amr_bridge_node.py:32` — `__init__`에서 한 번 찍고 이후 갱신되는 곳이 없음.
`recv_loop`(73행)·`parse_msg`(103행) 어디에도 `self.last_recv_time = time.time()`이 없다.

```python
def check_timeout(self):        # 212행
    elapsed = time.time() - self.last_recv_time
    if self.conn and elapsed > 2.0:
        ...
        self.conn = None
```

`sensor_bridge_node.py`는 `parse_msg` 맨 위에서 이걸 갱신하도록 고쳐놨던데, 같은 수정이 `amr_bridge`에는 안 옮겨진 것 같음. 이대로면 **DRIVE가 접속해도 2초 뒤부터 무조건 연결 끊김 판정** → MOVE/HB/STOP이 전혀 안 나감. 8/25에 한 번 지적됐던 그 버그가 이번 커밋에서도 그대로 남아있음.

## 2. 🔴 DRIVE의 SENS 블록, 네가 직접 남긴 의심 코멘트 확인함

`amr_bridge_node.py:4`
> "센서 데이터(가스/화염/거리)는 sensor_bridge(포트 8765)가 담당함, 이 노드는 죽은 SENS 파싱이 남아있음."

확인해보니 DRIVE(`firmware/esp32_drive_tcp/esp32_drive_tcp.ino`)는 지금도 포트 5000으로

```
<SENS,gas,flame,battCv,state,action,fault,dist,stopIdx,CS>
```

를 300ms마다 그대로 보내고 있음 — 이 경로 자체는 죽지 않았다. 다만 받는 쪽(`amr_bridge_node.py:122`, `if cmd == 'SENS' and len(parts) >= 8:`)에서 실제로 쓰는 필드는 `battCv` 하나뿐(3번 참고). `gas`·`flame`·`state`·`action`·`fault`·`stopIdx`는 `dashboard`·`hazard_detector`가 전부 `/env/*`로 옮겨간 뒤로 받는 곳이 없어졌음 — 이 부분 정리(publish 제거)해도 됨. **단, 파싱 자체(필드 개수·체크섬)는 건드리지 말 것** — DRIVE가 보내는 프레임 포맷이 바뀌는 게 아니라 RPi가 그중 일부만 버리면 되는 문제라서.

## 3. 🔴 `battCv`·`dist`는 실제로 필요한데 배관이 비어있다

- **`battCv`** — `mission_orchestrator.battery_cb`가 **9.9V 미만이면 EMERGENCY 전환**하는 유일하게 살아있는 소비처. `/amr/battery`는 `amr_bridge`의 SENS 블록에서만 나오므로, 1번(`last_recv_time`)이 고쳐지지 않으면 이 저전압 안전정지가 조용히 죽어있는 상태가 됨
- **`dist`** — `vision_node`가 `/amr/object_near`(Bool)를 구독해서 ACT 비전 트리거로 쓰는데, `amr_bridge_node.py:26`의 `pub_near`는 선언만 되고 실제 `.publish()` 호출이 코드 어디에도 없음. `dist ≤ 임계값`(또는 `fault == HAZARD`)일 때 `Bool(True)`를 publish하는 코드 추가 필요

---

## 4. 정리 — `amr_bridge_node.py`에서 할 것

| # | 내용 | 우선순위 |
|---|---|---|
| ① | `recv_loop`(또는 `parse_msg` 진입 시)에 `self.last_recv_time = time.time()` 추가 | 🔴 제일 먼저 — 이게 안 되면 나머지가 다 무의미 |
| ② | `dist` 기준 `/amr/object_near` 실제 publish 구현 | 🔴 |
| ③ | `gas`/`flame`/`state`/`action`/`fault`/`stopIdx` 관련 publish 정리(죽은 코드, 삭제 가능) | 🔵 급하지 않음 |
| ④ | `battCv` → `/amr/battery` publish는 그대로 유지 | — 건드릴 필요 없음 |

①②만 되면 DRIVE 새 보드 붙이고 바로 실통신 검증 들어갈 수 있음. 되는대로 `main`에 머지 부탁.
