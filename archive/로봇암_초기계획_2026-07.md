## 3. 배포 토폴로지 검토 — "USB 직결이 무선 운용을 막는가?"

**결론: 막지 않는다.** 다만 이 검토에서 리스크 2건이 새로 드러났다.

### 3-1. 무선성이 문제가 아닌 이유

혼동의 원인은 **"USB 직결"의 호스트를 노트북으로 고정해 생각하는 것**이다. 단계마다 호스트가 다르다.

| 단계 | 호스트 | 리더암 | 무선 필요? |
|---|---|---|---|
| 데이터 수집 | 노트북 (GPU) | 사람이 조작 | ❌ 애초에 유선일 수밖에 없는 실험실 작업 |
| 배포 (미션) | **온보드 RPi 5** | **없음** (정책이 대체) | ✅ 완전 무선 |

배포 경로 `RPi 5 ─USB─▶ 버스 서보 어댑터 ─▶ STS3215` 는 **전부 로봇 내부 배선**이다.
기존 v4 의 `ESP32 ─UART2─▶ 서보 버스` 와 마찬가지로 로봇 밖으로 나가는 선은 **양쪽 모두 0개**다.

전원도 별개다 — USB 어댑터는 **데이터(TTL)만** 나르고, 서보 구동 전력은 어댑터 **VIN 단자**로 로봇 12V 레일에서 공급한다.

### 3-2. 🔴 리스크 ① — 수집·배포 간 장착 상태 불일치 (판단 번복)

시각운동 정책은 **카메라가 보는 장면**을 입력으로 받는다.
책상 클램프에 고정한 팔에서 데이터를 모으고 섀시 위의 팔에 배포하면
카메라↔팔 베이스 상대 위치가 달라져 **관측 분포가 어긋나고 정책이 무너진다.**

> **Base 어댑터 플레이트는 "나중"이 아니라 데이터 수집의 선행 조건이다.**

→ 이 판단은 현재도 유효하며 v5 §5.7 「섀시 완성이 크리티컬 패스」로 이어진다.

### 3-3. 🔴 리스크 ② — RPi 5 가 ACT 추론을 감당하는가

학습은 RTX 4060, **추론은 RPi 5 (GPU·NPU 없는 순수 CPU)** 다.
8월에 학습을 다 끝내고 "RPi 에서 5Hz 밖에 안 나온다"를 발견하면 손쓸 시간이 없다.

**추론 속도는 가중치 값이 아니라 모델 구조가 결정한다 → 랜덤 가중치로 미리 측정 가능하다.**

ACT 는 액션 청킹을 하므로(`chunk_size=100`) 매 스텝 추론하지 않는다. 필요 조건은:

```
추론 지연 < n_action_steps / 제어 주파수
```

| `n_action_steps` | 30Hz 기준 예산 | 성격 |
|---|---|---|
| 100 (기본) | 3,300 ms | 여유롭지만 3.3초간 open-loop |
| 25 | 833 ms | **현실적 목표** |
| 10 | 333 ms | 반응적 |
| 1 (+temporal ensemble) | 33 ms | RPi5 CPU 로는 사실상 불가 |

**너무 느릴 경우 대안 3안** (현행 문서에 없는 내용 — 보존)

| 대안 | 무선성 | 비고 |
|---|---|---|
| ONNX 변환·양자화, 제어 주파수 하향, 카메라 수 축소 | ✅ 유지 | **가장 먼저 시도. 비용 0** |
| Hailo AI HAT / Jetson Orin Nano 컴퓨트 승급 | ✅ 유지 | 비용·리드타임 발생 |
| 노트북 추론 → Wi-Fi 로 관절 명령 전송 | ⚠️ **취약** | 지연·지터가 제어 루프에 직격 |

> **지금 방식이 무선을 막는 게 아니라, RPi 추론이 실패했을 때의 도피처가 무선에 의존하게 되고 그게 위험하다.**

## 4. 관문 구조 G0~G5 (로드맵)

```
[G0] 환경·팔로워      ✅ 완료 (6/8)
   │
   ├─ 크리티컬 패스 ──▶ [G1] 리더 전원 → [G2] 텔레옵 ★M1 ─┐
   │                                                       ├──▶ [G4] ACT 학습 ──▶ [G5] 실기 배포 ★M2
   └─ 병렬 (전원 무관) ▶ [G3] 섀시 장착 + RPi5 벤치마크 ───┘
```

| 관문 | 내용 | 결과 |
|---|---|---|
| **G0** | GPU 학습 환경 · 팔로워 ID·통신·캘리브레이션 | ✅ 완료 (6/8) |
| **G1** | 리더 7.4V 전원 · ID · 캘리브레이션 | ✅ 완료 (7/11) |
| **G2** | 리더-팔로워 텔레옵 **★M1** | ✅ 달성 (7/16, 60Hz) |
| **G3** | 섀시 장착 · 카메라 고정 · RPi5 벤치마크 | 🔲 섀시 대기 / RPi 미도착 |
| **G4** | 데이터 수집 · ACT 학습 | 🔲 W3~W4 |
| **G5** | 실기 배포 **★M2** | 🔲 W7 |

### G2 의 설계 의도 — 안전망 조기 확보

> **이 관문이 프로젝트의 안전망이다.** 이후 학습이 전혀 안 풀리더라도
> **텔레옵 시연만으로 제출물이 성립한다.** 성공 즉시 영상으로 기록할 것.

텔레옵은 **리더 관절 각도를 팔로워에 그대로 쓰는 것**이라 카메라도 정책도 관여하지 않는다.
팔이 책상에 있든 섀시 위에 있든 동작이 같으므로 **섀시를 기다릴 이유가 없었다.**
섀시가 필요해지는 시점은 **G4 데이터 수집부터**다 — 그때부터 카메라 영상이 데이터셋에 기록되기 때문.
(데이터 수집도 텔레옵으로 하므로 혼동하기 쉽다. **차이는 카메라 녹화 여부**다.)

**캘리브레이션은 팔을 섀시로 옮겨도 유지된다** — 관절 단위 값이라 베이스 위치와 무관하다.

## 6. 2026-06-08 세션의 교훈

> 요지는 `로봇암_구축기록.md` §3·§4 에 이미 인용돼 있다. 아래는 전문이다.

### 6-1. 노션 기록을 사실로 믿지 말 것 — 하루를 통째로 날릴 뻔했다

노션에 **"6축 전체 데이지 체인 통신 검증 완료"** 로 기록돼 있었다. 이것을 사실로 전제하고
전원 → 배선 → GND → ESP32 간섭 → 어댑터 → 케이블 접촉 순으로 **몇 시간을 헛짚었다.**

**진실: 팔로워 서보 6개가 전부 공장 출하 기본값(ID=1) 이었다.**
여섯 개가 같은 ID 로 동시에 응답하며 신호가 뭉개져 **버스가 통째로 죽어 있었다.**

**증상 패턴**: *"가끔 ID 1 하나만 잡혔다가 대부분 무응답"* = **ID 충돌**의 전형.
서보를 **하나만** 연결해 스캔하면 즉시 판별된다.

DB 불일치는 이때가 세 번째였다 (리더암 3D프린팅 "대기"→실제 완료 / USB 어댑터 행 누락 / ID 부여 미완).

### 6-2. 캘리브레이션의 "중간 자세"는 팔의 자연스러운 자세가 아니다

캘리브레이션을 **4번 실패**했다. 원인은 전부 같았다.

**팔이 쉬는 자세(어깨 처짐·팔꿈치 접힘)는 사실상 그 관절의 기계적 한계다.**
거기서 영점을 잡으면 한쪽 방향으로 갈 데가 없어 **반쪽만 기록**되거나,
중심이 치우쳐 반대로 훑을 때 **엔코더 경계(0/4095)를 넘어 래핑**된다.

**올바른 절차**
1. `tools/watch_positions.py --free` 로 각 관절의 실제 가동 범위를 **먼저 측정**
2. 관측된 `MIN~MAX` 의 **한가운데**를 계산 → 그 자세로 맞춤
3. 그 자세를 **유지한 채** 캘리브레이션 실행
4. 훑을 때는 반드시 **양방향**

**합격 기준: 전 축 `MIN < 2048 < MAX`, 0/4095 미접촉.**

### 6-3. 리더 서보는 7.4V

보유 전원은 12V 하나뿐이라 **XL4015 강압 7.4V 레일이 필수**였다.
⚠️ XL4015 는 출고 시 출력이 임의값이다. **반드시 무부하에서 7.4V 로 조정한 뒤 서보를 연결할 것.**

## 7. 카메라 선정 경위 — 왜 그 두 대인가

> 현행 카메라 구성은 `로봇암_카메라_구성정리.md` 가 정본이다 (물리 3대).
> 아래는 **초기에 무엇을 배제했는지**의 기록이다.

### 배제한 것

| 배제 | 이유 |
|---|---|
| ❌ 깊이 카메라 (RealSense·OAK-D) | **ACT 는 RGB 만 쓴다.** `modeling_act.py` 가 `config.image_features` 만 읽는다. Phase 5 용인데 Phase 5 는 이월 → ₩200,000~400,000 절약 |
| ❌ RPi CSI 카메라를 ACT 입력으로 | **데이터 수집은 노트북에서 하는데 CSI 는 RPi 에만 꽂힌다.** 녹화 카메라 ≠ 추론 카메라 → 도메인 갭 |
| ❌ 동일 모델 2대 | USB 경로가 무작위 재할당되어 손목/작업공간이 뒤바뀐다. **뒤바뀐 줄 모르고 오염된 데이터를 수집**하게 된다. 이 노트북은 USB 컨트롤러가 1개라 분산 우회도 불가 |

### 선정

| 위치 | 제품 | 근거 |
|---|---|---|
| 손목 | wowrobo 2MP USB (SO-ARM100/101 전용, $28) | 전용 마운트 설계 + **3m 케이블**이 팔 움직임을 감당 |
| 작업공간 | InnoMaker 720P UVC 32×32, 120° DFOV | **오버헤드 마운트 STL 이 이 모델 기준으로 설계됨** → 규격 리스크 0 |

- **640×480 @30fps 면 충분하다.** ACT 가 내부에서 리사이즈한다. 고해상도는 RPi 추론만 느리게 한다
- **MJPEG 필수** — 비압축(YUYV)이면 640×480@30 이 한 대당 ~150 Mbps → USB 2.0 대역폭 충돌

> 두 항목 모두 도착 후 검증 완료됐다 (`로봇암_카메라_구성정리.md` §10.1 — 2대 동시 드롭 0).

## 8. arm_bridge 재사용 구조 (진우 인터페이스, 6/9)

v5 §2.1 이 결론만 담고 있어 **구조 다이어그램은 이 문서가 유일한 기록**이다.

### 핵심 — 진우가 만든 노드는 하나도 안 버린다

`arm_bridge` 의 **TCP:5001 서버 + `<CMD,...,체크섬>` 프로토콜을 그대로 쓰고,
ESP32 #2 자리에 ACT 정책 프로세스가 TCP 클라이언트로 붙는다.**

```
[기존] mission_orchestrator ──/arm/grip_cmd──▶ arm_bridge ──TCP:5001──▶ ESP32 #2 ──UART──▶ 서보
[변경] mission_orchestrator ──/arm/grip_cmd──▶ arm_bridge ──TCP:5001──▶ arm_act_node ──USB──▶ 서보
                                                (동일)                   (RPi 내부 프로세스)
```

| 진우 입장에서 | |
|---|---|
| `arm_bridge` 코드 · TCP 5001 · `<GRIP,CLOSE,80,CS>` · `<SFBACK,...>` · `/arm/servo_feedback` · FSM | **전부 변경 없음** |
| TCP:5001 에 접속하는 클라이언트 | ESP32 #2 → **`arm_act_node`** |

**`arm_bridge` 는 반대편이 ESP32 인지 파이썬 프로세스인지 알 필요가 없다.**

### 왜 ROS2 노드가 아니라 TCP 클라이언트인가

**Ubuntu 24.04 + ROS2 Jazzy 환경을 오염시키지 않기 위해서다.**
LeRobot 은 격리 venv 에 깔아야 하는데 그러면 `rclpy` 를 못 쓴다.
→ TCP 로 붙으면 이 문제가 통째로 사라진다. 진우 프로토콜이 이미 있어서 가능한 선택이었다.

### `arm_controller` 는 폴백으로 보존

ACT 성능이 안 나올 경우를 대비해 **IK + 포즈테이블 경로를 살려둔다.**
런치파일에서 노드만 바꿔 끼우면 된다.

⚠️ **ACT 검증 중에는 `arm_controller` 를 런치하지 말 것** — `/arm/command` 로 6축 각도가 날아오면 ACT 와 겹친다.

→ v5 §5.2 에서 이 폴백이 **정형 블록용 프리셋 경로로 정식 채택**됐다 (하이브리드 데모).
